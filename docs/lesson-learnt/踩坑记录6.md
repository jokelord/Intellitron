# 问题 1：Voice 长时间等待后触发迟钝并出现音频积压

## 1. 问题现象

Voice mode 刚开启时基本正常，但长时间停在 listening/buffering 后，start 会变迟钝：用户已经喊了几秒，才进入 recording；说完后也需要比配置值更长的静音，才进入 finalizing。有时还会出现：`[ASR] Voice input paused because audio capture could not keep up.`

关键特征是 start 和 end 一起延迟，且等待越久越明显。这不像 VAD 阈值错误，而像音频帧排队。`audio capture could not keep up` 指向 AudioWorklet 到主线程积压；`ASR connection could not keep up` 才指向 WebSocket 缓冲。

同时出现的 `-webkit-text-size-adjust` 解析警告来自 Tailwind Preflight。Firefox 不支持该声明时会忽略它，不会阻塞 JavaScript、AudioWorklet、WebSocket 或 ASR，与 Voice 变慢无关。

## 2. 根本原因

AudioWorklet 每 `20 ms` 产生一帧 320-sample PCM。原处理路径除了 ACK、编码和发送 PCM，还计算本地音量、执行 `dispatch({ type: "level" })` 并创建 waveform。`useVoiceInput` 位于 Text 和 Vision 顶层页面，level 更新可能重跑整个聊天页面；历史内容越多，单次更新越重。

主线程处理速度低于每秒 50 帧时，MessagePort 就积压旧音频。用户开始讲话时，后端先收到旧静音；停止后也要等待积压帧，所以 start、end 都变慢。`max_buffered_frames: 250` 约等于 5 秒，达到上限后发出 `transport_overflow`。

后端环形缓冲、Silero pending PCM 和状态机没有无界增长，也没有主动延长 end silence。提高缓冲上限只会推迟报错并积压更多过期音频。

## 3. 解决方案

移除不应放在 20 ms 热路径中的 UI 工作，但保留音频传输必需部分：

- 保留 AudioWorklet 固定帧、transferable buffer 和即时 `frame_ack`，避免占满 in-flight 计数。
- 保留 PCM little-endian 编码、WebSocket `bufferedAmount` 检查和 overflow 保护，不能为了减少 React 更新而取消背压。
- 删除前端逐帧 `estimatePostGainLevel()` 与本地 `dispatch(level)`。浏览器只负责采集和传输，不再每 20 ms 驱动顶层页面重渲染。
- 音量、clipping ratio 和 waveform 改由后端 level 事件驱动。后端按 `level_event_interval_ms: 100` 限流，UI 约每秒更新 10 次；gain、clip 和 RMS 仍只在后端计算一次。
- Text 和 Vision 共用 `useVoiceInput`，两页继续通过 Voice panel 消费 level/state 事件。

复测关注长时间 listening 后的 start/end 延迟、in-flight 帧、后端 level、PCM 发送和背压错误。不要用增大缓冲区或修改 VAD 静音时长掩盖积压；排障记录错误文字、帧时长、`bufferedAmount`、ACK 延迟和后端时间戳。CSS 警告忽略即可。

# 问题 2：SM110 flashinfer 打 gate 补丁

## 1. 问题现象

Jetson Thor (SM110a) 上启动带 `--attention-backend flashinfer` 的 SGLang 时，注意力后端注册表的白名单校验不通过，flashinfer 无法启用。

## 2. 根本原因

`attention_registry.py` 用 `is_sm120_supported()` 决定 allowed 后端集合；该判定不覆盖 SM110a，落入 else 分支后 allowed 中没有 flashinfer。

## 3. 解决方案

打开 `.sglang/lib/python3.12/site-packages/sglang/srt/layers/attention/attention_registry.py`。

找到这段：

```python
if is_sm120_supported():
    allowed = {"triton", "trtllm_mha", "flashinfer"}
else:
    allowed = {"triton", "trtllm_mha", "fa4"}
```

改成：

```python
major, minor = get_device_capability()

if is_sm120_supported() or (major == 11 and minor == 0):
    allowed = {"triton", "trtllm_mha", "flashinfer"}
else:
    allowed = {"triton", "trtllm_mha", "fa4"}
```

# 问题 3：使用基于 FP8 训练的 DSPARK speculative 模型时需调整 dspark.py
# 注意：此步改了依赖库
## 1. 问题现象

DSpark 的 draft 解码阶段对 NVFP4 打包后的 lm_head 权重直接做 matmul：logical hidden size 5120 被当成物理宽度使用（实际物理宽度 2560），形状不匹配直接报错。

## 2. 根本原因

根因：DSpark 的 `compute_base_logits()` 直接拿 NVFP4 打包后的 `lm_head.weight` 做 `torch.matmul` 了。

当时的形状：

```text
hidden      = 126 x 5120
weight.T    = 2560 x 248320
```

`5120 → 2560` 正好符合 FP4 两个 4-bit 值打包后的物理宽度。Qwen3.8-27B 的真实 hidden size 是 5120。

而 SGLang 正常的 LogitsProcessor 对 ModelOpt FP4 不会直接 matmul packed weight，而是调用 `quant_method.apply()`。但 DSpark 当前 `compute_base_logits()` 仍然直接 `torch.matmul(hidden, weight.T)`，所以撞上这个错误。

## 3. 解决方案

直接改 `.sglang/lib/python3.12/site-packages/sglang/srt/models/dspark.py`。

找到：

```python
def compute_base_logits(
    self, hidden: torch.Tensor
) -> tuple[torch.Tensor, Optional[torch.Tensor]]:
    if self.lm_head is None:
        raise ValueError(
            "DSpark dense draft requires the target lm_head "
            "(call attach_shared_modules first)."
        )

    weight = self.lm_head.weight
    if hidden.dtype != weight.dtype:
        hidden = hidden.to(weight.dtype)

    local_logits = torch.matmul(hidden, weight.T)
    base_logits = gather_and_crop_vocab(local_logits, self.lm_head)
    return base_logits, None
```

完整替换为：

```python
def compute_base_logits(
    self, hidden: torch.Tensor
) -> tuple[torch.Tensor, Optional[torch.Tensor]]:
    if self.lm_head is None:
        raise ValueError(
            "DSpark dense draft requires the target lm_head "
            "(call attach_shared_modules first)."
        )

    lm_head = self.lm_head
    quant_method = getattr(lm_head, "quant_method", None)

    # NVFP4 / FP8 quantized target lm_head must go through its
    # quantization method. The physical FP4 weight is packed,
    # e.g. logical K=5120 appears as physical K=2560.
    if quant_method is not None and callable(getattr(quant_method, "apply", None)):
        from sglang.srt.layers.logits_processor import (
            should_apply_lm_head_quant_method,
        )

        if should_apply_lm_head_quant_method(lm_head, quant_method):
            local_logits = quant_method.apply(lm_head, hidden, None)
        else:
            weight = lm_head.weight
            if hidden.dtype != weight.dtype:
                hidden = hidden.to(weight.dtype)
            local_logits = torch.matmul(hidden, weight.T)
    else:
        weight = lm_head.weight
        if hidden.dtype != weight.dtype:
            hidden = hidden.to(weight.dtype)
        local_logits = torch.matmul(hidden, weight.T)

    base_logits = gather_and_crop_vocab(local_logits, lm_head)
    return base_logits, None
```

这实际上是把 DSpark 的 LM-head 计算逻辑对齐到 SGLang 自己正常 inference 使用的 quant-aware 路径。SGLang 的 `should_apply_lm_head_quant_method()` 已专门识别 ModelOptFp4LinearMethod 的 packed uint8 权重及对应 scale/runtime attributes。

# 问题 4：context length 设 262144 实际却缩水到约 81k（长输入 400 报错）

## 1. 问题现象

前端报错：

```text
抱歉，Agent 执行出错: Error while generating output: SGLang 服务响应错误: 400 -
{"object":"error",
 "message":"Input length (87549 tokens) exceeds the maximum allowed length (80964 tokens).
 Use a shorter input or enable --allow-auto-truncate.",
 "type":"BadRequestError","param":null,"code":400}
```

`--context-length 262144` 明确传给了 `sglang.launch_server`，服务也正常启动、没有任何启动期告警；直到某个长 prompt（87,549 token）进入 Agent 会话才爆 400。用户观察到的现象是"context length 从 262144 缩水到 87549"，实际缩水的是服务端允许的上限 80964。

## 2. 根本原因

一句话结论：**`--context-length` 只是"请求值"。SGLang 启动时按"当前实际空闲内存"动态计算 KV cache 能容纳多少 token（`max_total_num_tokens`），出错那次只算出 80,970，于是把单请求上限钳制到 `80970 − 1 − 5 = 80964`。那次启动时 Jetson Thor 的 UMA 只剩 44.66 GB 可用内存（其他共存进程占了约 66 GB），这部分预算又被 hybrid GDN 的 Mamba 状态池 + DSPARK 中间缓冲分走约 86%，full-attention KV pool 只剩约 2.5 GB ≈ 8 万 token。**

### 2.1 报错数字的精确出处

出错的那次启动日志：`logs/sglang_20260819_040714.log`（`mem_fraction_static=0.55`、`max_running_requests=48`、`chunked_prefill_size=4096`）：

- 第 78 行：`max_total_num_tokens=80970, ..., context_len=262144`
- 第 967 行：`Input length (87549 tokens) exceeds the maximum allowed length (80964 tokens)...`

单请求上限的计算链（`.sglang/lib/python3.12/site-packages/sglang/srt/managers/tp_worker.py:509-521`）：

```text
max_req_len       = min(model_config.context_len - 1, effective_max_total_num_tokens - 1)
max_req_input_len = max_req_len - 5
```

**80970 − 6 = 80964**，与报错完全吻合。输入 87,549 ≥ 80,964 时，由 `managers/utils.py::validate_input_length`（`:216-220`，本项目 `allow_auto_truncate=False`）生成错误文本，HTTP 层包装成 400 BadRequestError。

### 2.2 KV pool 为什么只有 80,970 token —— 三层挤压

KV 池预算公式（`.sglang/lib/python3.12/site-packages/sglang/srt/mem_cache/kv_cache_configurator.py:1614-1637`）：

```text
KV预算 = 当前空闲显存 − pre_model_load × (1 − mem_fraction_static)
```

两次启动的对账（同模型 Qwen3.8-27B-NVFP4，同样请求 262144）：

| 项目 | 失败那次 (logs/sglang_20260819_040714.log) | 正常对照 (logs/sglang_20260823_014502.log) |
|---|---|---|
| 启动时可用内存（`Load weight begin` 行） | **44.66 GB ← 第一诱因** | 110.65 GB |
| mem_fraction_static | 0.55 → slack ≈ 20.1 GB | 0.58 → slack ≈ 46.5 GB |
| 总池预算 rest_memory | ~24 GB | ~39 GB |
| `mamba_full_memory_ratio=6.08` 分给 Mamba 池 | **~86%（≈19.4 GB）** | 同样 ~86%，但绝对量小 |
| DSPARK intermediate_ssm 缓存（∝ max_running_requests） | 48 并发 → cap 20 reqs → **12.0 GB** | 4 并发 → cap 4 reqs → 2.86 GB |
| 剩给 full-attention KV | **~2.5 GB ÷ 32.8 KB/token ≈ 80,970 token** | 22.5 GB = 561,320 token |

关键点：

1. **UMA 内存竞争是第一诱因**：同一配置下，启动时空闲 110.65 GB vs 44.66 GB，结果差近 7 倍。浏览器 / VS Code / ASR / PaddleOCR 等共存进程的占用量直接决定当次的实际 context 长度。
2. **`mamba_full_memory_ratio=6.08` 的真实语义是"Mamba 池拿走 ratio/(1+ratio) ≈ 86%"**（`kv_cache_configurator.py:1922-1927`），而不是"KV 是 Mamba 的 6 倍"。Qwen3.8 hybrid GDN + fp8_e4m3 KV 下每 token 全注意力 KV 成本高达 ~32 KB。
3. **DSPARK 投机解码的 `intermediate_ssm_state_cache` 按 `min(max_running_requests, mamba_slots/5)` 缩放**：当时 `max_running_requests=48`，白白多占约 9 GB。
4. **SGLang 不报错、只静默钳制**：有效 context 被压到 `max_total_num_tokens` 后照常对外服务，直到长 prompt 进来才以 400 形式暴露——"启动没有告警 ≠ context 够用"。

### 2.3 当前配置状态

当前 `config/qwen3.8-radixArk-NVFP4-config-infer.yaml`（`mem_fraction_static: 0.58`、`max_running_requests: 4`）在干净内存下实测 `max_total_num_tokens=561320 > 262144`，即配置本身足以撑满 262k；风险仅在于"带着内存压力二次启动时静默缩水"。

## 3. 解决措施

1. **重启 SGLang 前必须先清理 UMA 内存**：运行 `scripts/0_force_cleanup_uma.sh`（或人工确认空闲显存充裕）后再执行 `scripts/1a_start_sglang.sh`。本次 2026-08-19 事故的直接诱因就是二次启动前未清空 UMA 内存。
2. **保持 `max_running_requests: 4`，不要回到 48**：DSPARK intermediate 缓存从 ~12 GB 降到 ~2.9 GB。
3. **每次启动后核对一次实际值**：在启动日志中 grep `max_total_num_tokens`，确认其 ≥ `max_context_length`（262144）；若小于则说明当次启动时内存不足，应清内存后重启，不要带着缩水的 context 继续跑 Agent 长会话。
4. **不要用 `--allow-auto-truncate` 兜底**：它会静默截断历史输入，破坏多轮上下文与 prefix-cache 契约。低内存下要么清内存重启，要么接受更低的有效 context 并让 backend 对该 400 触发 compact 后重试（未实施）。
5. 可选加固（未实施）：在 `scripts/1a_start_sglang.sh` 加启动前预检——估算 `(free_GB − slack) × 14% ÷ 32.8 KB` 得到预期 KV token 数，低于 `MAX_CONTEXT_LENGTH` 时拒绝启动并提示先释放内存。

# 问题 5：Vision Automation 推理期间全系统节奏性卡顿（Firefox 的 X11 捕获路径）

## 1. 问题现象

在 Vision Automation arm 后发送自动化轮次，SGLang 推理/流式期间整个桌面出现有节奏的停顿：OS 鼠标、Web UI “+”按钮旁的状态环和流式文字会一起顿挫。对照实验显示：

- 空闲时保持同一条捕获流，不卡；
- 不 arm、只手动上传图片推理，不卡；
- 捕获 **Firefox 自己的窗口**，基本不卡；
- 捕获 **其他应用窗口**（Obsidian、Evince），才出现约 1.5 Hz 的卡顿。

由于 OS 鼠标也同步停顿，这不是单纯的 backend Hub/SSE 文本批量刷新问题；后端和前端只是一起受到桌面调度阻塞的影响。

把视觉自动化面板的截图间隔改为 10 秒，卡顿频率仍没有下降。这一结果很关键：面板间隔并不是浏览器底层桌面捕获器的帧率控制。

## 2. 根本原因（证据与边界）

1. **X11 下 Firefox 走的是本地桌面捕获路径，而不是本次观测到的 portal/PipeWire 路径。** 在出问题的 X11 会话中，arm 期间 `pw-dump` 没有出现 Mutter screencast 节点；Firefox 使用 WebRTC 的 X11 capturer（包含 XDamage/XShmGetImage 等读回路径）。捕获外部窗口时，需要把 X11 窗口的像素从合成器/GPU 侧读回到 CPU 可处理的缓冲区，这类同步读回会阻塞 X11/桌面合成。
2. **视觉自动化的 `intervalSeconds` 只控制“何时从已有 MediaStream 取一帧并上传”。** 当前前端调用的是 `getDisplayMedia({ video: true, audio: false })`，并未把该面板间隔传给浏览器的 `frameRate` 约束。因此把间隔改成 10 秒，并不会可靠地暂停或降频 Firefox 已经 arm 的底层捕获循环。
3. **推理负载放大了 X11 读回的代价。** Jetson 的 GPU/UMA 带宽同时被 SGLang 推理占用时，外部窗口的同步读回会与渲染、合成和 Xorg 调度争用资源，最终表现为整个桌面按节奏停顿，而不只是 SSE 文本刷新变慢。空闲时 GPU 竞争较小；捕获 Firefox 自身窗口时读回路径和缓冲共享方式不同，所以这两个对照可以不卡。这里的“GPU/UMA 竞争 → X11 读回阻塞”是与观测和进程采样一致的高置信机制，不把某个未被直接 tracing 的内核调用误写成已证明的唯一原因。

因此，观察到的约 1.5 Hz 不能再写成“必然等于 `1 / intervalSeconds`”。它更可能是 X11 捕获器的实际调度、同步读回和系统负载共同形成的节奏；0.6 秒面板间隔只是当时的相关变量。

另外，`MediaStreamTrack.enabled = false` 只会让轨道输出黑帧，并不保证底层屏幕捕获线程停止；在 arm 后再调用 `applyConstraints` 也不能作为可靠的停采方案。若未来确实要修改约束，应传递完整的分辨率/帧率约束，避免部分约束触发浏览器重新协商出意外的原生分辨率和更大的读回量。

## 3. 解决方案（已验证）

**切换到 Ubuntu on Wayland。** 在 GDM 登录界面注销后选择用户，点击右下角齿轮，选择 **Ubuntu on Wayland**，再登录。用下面的命令确认会话：

```bash
echo "$XDG_SESSION_TYPE"   # 应输出 wayland
```

Firefox 在 Wayland 会话下可以通过桌面 portal/PipeWire 获取窗口/屏幕流，视觉自动化仍使用原有的浏览器窗口选择器、缩略图和上传链路，不需要新增后端端口，也不需要手工填写矩形区域。实测切换后，外部应用窗口截图导致的全系统卡顿消失，中文窗口名也能正常显示。

如果必须留在 X11，捕获 Firefox 自身窗口或降低负载只能算规避/缓解，不能保证外部窗口捕获不再卡顿。`pw-dump` 可用来判断是否建立了 PipeWire screencast 节点；`top -b -d 0.25` 配合 `tegrastats` 可继续用于确认 Xorg、Firefox 与 SGLang 的资源争用。

# 问题 6：agent 流式期间 React "Maximum update depth exceeded"（GlassJellySurface 振荡）

## 1. 问题现象

Vision 页自动化轮次 AGENT 模式流式期间，Console 反复打印 `Warning: Maximum update depth exceeded...`（Firefox 分组计数 4、11 等）。真机堆栈落在 `addStep → setMessages(page.tsx)`，极具误导性——流式 setMessages 本身无辜，只是"触发打印的那次 dispatch"。

## 2. 根本原因

装饰组件 `GlassJellySurface`（text/vision 两页页眉页脚各挂一个）的两个缺陷叠加：

1. `getGlassJellyConfig()`（web-ui-config.ts）每次调用返回**新对象字面量**；组件内 `glassConfig` 未 memo → effect deps `[glassConfig, zone]` 每 render 恒变 → 每个流式 chunk / automation tick 的提交都重跑 effect。
2. `hasWebGLSupport()` 探针每次 `createElement('canvas').getContext('webgl2')` 创建 WebGL context 且**从不释放**；浏览器 ~16 context 上限耗尽后 probe 间歇失败 → `setCanRender(false/true)` 在 passive effect flush 内调度 → R3F 卸载（释放槽位）→ 下轮 probe 成功再挂载 → **振荡**，每轮 flush React 嵌套更新计数 +1，50 轮后打印警告。

React 语义要点：同一离散事件内 50 次 setState 会被批处理为一次 render，**不会**触发此警告；该警告意味着更新发生在 render/commit 级联内部——排查方向应是"哪个 effect 链每轮再 setState"，而不是高频事件处理器本身。

## 3. 解决方案

- `glassConfig` 改 `useMemo(() => getGlassJellyConfig(config), [config])`（两页传入的 config 来自 useState，引用稳定），effect 仅在真实配置变化时重跑；
- 探针创建后立即 `getExtension('WEBGL_lose_context')?.loseContext()` 释放，切断"槽位耗尽 → canRender 振荡"链；
- 新增 `GlassJellySurface.test.mts` 三个回归锁：探针立即释放；同 config 引用 5 次 re-render 不重跑 effect/probe（旧代码上必失败）；config 引用变化仍重跑（防过度 memo 成 deps=[]）。
- 遗留：`api.test.mts` 存在 2 个与本修复无关的存量失败（Hub 流 duplicate event_sequence 后 done 不派发；stream cancel 抛错后 done 回调丢失），待另开任务。
