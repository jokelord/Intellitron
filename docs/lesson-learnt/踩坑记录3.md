## 0. 适用范围

本文记录的是 v1（`/compact` 命令 + 自动 compact）从"popup 完全不显示"到"端到端跑通"的全过程：
- 共 6 个独立的 bug
- 跨越前端（Next.js / React）、后端（FastAPI / SGLang 代理）、SGLang 推理服务（chat template）三层
- 涉及 chat template、HTTP routing、消息类型契约、SSE 流消费、Qwen3 多步工具调用等基础设施

**核心结论**：每一个 bug 的真正根因都不在用户描述的那个层面。要么在更早的层、要么在更晚的层、要么在跨层契约的某个隐含假设上。

## 1. Bug 链：症状 → 真因 → 修复

### Bug 1：popup 完全不显示

**用户描述**：输入 `/compact`，右侧的 command popup 没出现。

**调查路径**：
1. 检查 onChange 是不是更新了 `slashMenu.visible`
2. 发现 `setSlashMenu((prev) => ({ ...prev, ...detected }))` 这一行
3. 发现 `detected` 是 `{active: true, query: ''}`，但 `prev` 是 `{visible: false, query: '', selectedIndex: 0}`
4. spread 之后 `visible: false` 仍然在 state 里（因为 spread 不会更新字段名不同的字段），`active: true` 是个孤儿字段

**真正根因**：**字段名命名错位**。`detectSlashCommand()` 纯函数返回 `active`，但 React state 用 `visible`。spread 合并默默丢弃了 `visible` 的更新。

**修法**：新增 `mergeSlashCommandState(prev, detected)` 类型化桥接函数，显式做字段映射：
```ts
return {
  visible: detected.active,   // 显式映射
  query: detected.query,
  selectedIndex: prev.selectedIndex,
};
```

**教训**：
- **spread 隐式合并是命名错位 bug 的温床**。永远用显式桥接函数做字段映射。
- 纯函数测试通过 ≠ 集成正确。`detectSlashCommand` 的 6 个测试都过，但 popup 仍然不显示 —— 因为纯函数没消费 React state。
- 写一个 `mergeSlashCommandState` 类型的 regression 测试（8 个用例），把集成契约**显式锁定**。

### Bug 2：Tab+Enter 把 `/compact ` 当普通消息发给 LLM

**用户描述**：按 Tab 补全到 `/compact `（带尾空格），按 Enter，结果 `/compact ` 被当成普通聊天消息发给了 LLM，LLM 回了一段 "用户要求/compact，这是系统命令..." 的回复。

**调查路径**：
1. 看了 Tab handler —— 它确实设了 `input="/compact "`，关了 popup
2. 看了 Enter handler —— `if (slashMenu.visible && filteredSlashCommands.length > 0)` 守卫意味着 popup 关了就走另一个分支
3. 那个分支的逻辑是 `handleSend()`，把 input 当普通消息发

**真正根因**：Enter handler 写了"popup 可见时走 slash command 处理路径"，但 popup 关闭后它没考虑"input 里是完整 slash command"的情况。

**修法**：在 Enter handler 关闭 popup 后加一个 `isCompleteSlashCommand(input)` 检查，命中就调 `handleSelectSlashCommand(matched)`，否则才 `handleSend()`。

**教训**：
- **守卫条件的"happy path vs 其他路径"是 bug 高发区**。"如果 X 则 A，否则 B"中，B 路径经常缺少 X 之外的其他合法情况。
- 用户行为不一定要通过 popup 才能触发。键盘快捷键 / 直接输入完整命令 / 鼠标点击应该都收敛到同一个 handler。

### Bug 3：点击 / 完整输入 + Enter 完全没反应

**用户描述**：点击 popup 中的 compact 条目，或者完整输入 `/compact` 不带空格 + Enter，没有任何反应。前端和后端都没有 debug 信息。

**调查路径**：
1. 加了 verbose console.log
2. 发现 handleSelectSlashCommand 确实被调用了
3. 看它内部 —— 调了 `fetch + .catch(() => {})` 完全吞掉错误
4. 看后端日志 —— 完全没有请求记录

**真正根因**：**`fetch + .catch(() => {})` 是经典静默失败模式**。错误被吞掉，response body 没被读，SSE 流的事件全部丢失。

**修法**：新增 `runCompactSSE({url, body, onEvent, signal})` 真正迭代 `response.body.getReader()`：
```ts
const reader = res.body.getReader();
const decoder = new TextDecoder();
let buffer = '';
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  // 按 \n\n 切块，提取 data: 行，JSON.parse，调 onEvent
}
```

并在 LLMClient 里加 `runCompact(body, onEvent, signal?)` 包装（和所有其他端点一样用 `${this.baseUrl}/v1/...`）。

**教训**：
- **`fetch().catch(() => {})` 不是错误处理，是错误丢弃**。SSE 端点必须流式消费才能工作。
- 端到端测试必须验证"response body 真的被消费"，而不是只验证"请求被发出"。

### Bug 4：HTTP 404

**用户描述**：Bug 3 修完后，按 Enter 出现：
```
Compact crashed: compact SSE failed: status=404
```

**调查路径**：
1. 检查后端路由注册 —— `POST /v1/compact/run` 已注册（在 `backend/api/compact.py:49`）
2. 检查 `main.py:238` —— `if config.compact.enabled: app.include_router(compact_router)` 也执行了
3. 直接 curl 打 `http://127.0.0.1:8090/v1/compact/run` —— 200 OK
4. **但前端打的就是 404**！

**真正根因**：**前端用了相对路径 `/v1/compact/run`，后端在 8090，前端 dev server 在 3000**。浏览器把 `/v1/compact/run` 解析成 `http://localhost:3000/v1/compact/run`，Next.js dev server 没有这个路由，404。

**修法**：
1. `compact-client.ts` 文档明确警告 `url` 必须是绝对 URL
2. 新增 `LLMClient.runCompact(body, onEvent)` 用 `${this.baseUrl}/v1/compact/run`
3. 两个页面都改用 `llmClient.runCompact()`
4. 加 regression test `test_compact_client_llmclient.test.mts` 锁住绝对 URL 契约

**教训**：
- **`api.ts` 里的所有端点都用 `${this.baseUrl}/v1/...`，新加端点必须同样**。偏离既有约定 = bug。
- 状态码 404 = 路由不存在，几乎总是 URL 路径问题，不是 server-side 错误。5xx 才是 server problem。
- 端到端测试要包括"从浏览器 origin 出发"，不只是"在 backend 测试 client"。

### Bug 5：404 → 200 OK，但 compact 仍失败：`AttributeError: 'dict' object has no attribute 'role'`

**用户描述**：点击 🧪 按钮出现
```
Compact failed (llm_unreachable): AttributeError: 'dict' object has no attribute 'role'
```

**调查路径**：
1. 看 `llm_service.py:1782`：
   ```python
   self._last_stream_request = {
       "messages": [{"role": m.role, "content": m.content} for m in messages],  # ← 属性访问
       ...
   }
   ```
2. 看 `compact/prompt_builder.py` —— 返回 `[{"role": "system", "content": "..."}]`（**dict 列表**）
3. 看其他调用方（普通 chat、agent）—— 都先包装成 `Message` 对象再传
4. **compact 是唯一绕过 `Message` 包装层的调用方**

**真正根因**：**跨层消息对象类型契约不一致**。`llm_service.chat()` 用 `m.role` / `m.content` 属性访问，调用方必须传 `Message` 对象。compact 传 dict，每次属性访问都 raise。

**修法**：在 `CompactOrchestrator.run_compact` 入口处把 dict 转成 `Message` 对象：
```python
normalized_messages: List[Message] = [
    Message(
        role=str(m.get("role", "user")) if isinstance(m, dict) else m.role,
        content=m.get("content") if isinstance(m, dict) else m.content,
    )
    for m in prompt_messages
]
```

**教训**：
- **每个调用方对同一契约的"各自实现"是 bug 滋生地**。统一入口比"每个调用方各自保证"更安全。理想情况下 `chat_stream_async` 内部就该 `[Message(**m) if isinstance(m, dict) else m for m in messages]` 做一次 normalize，但会改变其他调用方行为，blast radius 大。最小修法是先在 orchestrator 入口处 normalize。
- **buggy 行为会被测试反向固化**。`test_compact_chat_auto_trigger._TriggeringLLM` 用 `messages[0].get("role")`（dict 访问），和真实 LLM service 的 `messages[0].role`（属性访问）契约不一致 —— 它依赖了 buggy 行为通过测试。修真实 bug 时这个 mock 立刻暴露了不一致。**测试 mock 必须用和真实代码相同的字段访问方式**。
- 必须同步更新 mock：把 `messages[0].get("role")` 改成 `messages[0].role`。

### Bug 6：AttributeError 修了，但 compact 仍 400

**用户描述**：重启后端，输入 `/compact`，看到：
```
[compact] SSE event: { kind: "compact_started", ... }
[compact] SSE event: {
  kind: "compact_delta",
  text: '\n[流式生成错误] RuntimeError: SGLang 服务响应错误:
    400 - {"object":"error","message":"No user query found in messages.",...}\n'
}
[compact] SSE event: { kind: "compact_completed", text: '[流式生成错误]...', ... }
```

**调查路径**：
1. **关键观察**：错误的 `kind` 是 `"compact_delta"` —— 错误发生在 **compact 自己的 LLM 调用**里，不是后续 chat！
2. 我之前几轮都假设错误在 chat 路径（因为用户的叙述是"压缩后下一步 chat 报错"），完全没看 `kind` 字段
3. 搜索 SGLang 错误源 —— 在 `chat_template.jinja:79`：
   ```jinja
   {%- if ns.multi_step_tool %}
       {{- raise_exception('No user query found in messages.') }}
   {%- endif %}
   ```
4. 看 `multi_step_tool` 检测的循环：反向扫描 messages，找**非 `<tool_response>` 的 user 消息**
5. compact 的 prompt 是**单个 system 消息**（v1 设计），**没有 user 行** → `multi_step_tool` 永远 True → raise

**真正根因**：**Qwen3 chat template 假设 chat 调用至少有一条 user 消息**。Compact 路径发送了单 system 消息（v1 设计），触发了 `multi_step_tool` 错误。

**修法**：`build_compact_messages` 改成返回 `[system, user]` 形状：
```python
return [
    {"role": "system", "content": system_content},     # 格式约束 + main_prompt + trailer
    {"role": "user", "content": user_content},         # "Conversation to summarize:\n\n" + body
]
```

**端到端验证**：curl 打 `[system, user]` 形状到真实 SGLang → 200 OK，正确产出 `<analysis>`/`<summary>` 块。

**教训**：
- **错误位置在事件字段里，不在用户叙述里**。`kind: "compact_delta"` + `text` 以 `\n[流式生成错误]` 开头 = 错误发生在 compact 调用里，不是后续 chat。**永远读 `kind` 字段 + `text` 头部**。
- **跨组件契约测试要覆盖完整的 stack**。Mock LLM service 的单元测试都通过，但 chat template（连同它的所有隐含假设）只有真实跑一遍才能验证。新增 `tests/test_compact_prompt_builder_template_compat.py::test_build_compact_messages_passes_qwen3_chat_template` 渲染了真实的 chat template 才捕获了 v1 的 single-system 形状 bug。
- **当 v1 设计与 v2 实际约束不兼容时，必须在 v2 这边改，不要假设 v1 是对的**。v1 "单 system 消息" 看起来很自然，但 Qwen3 chat template 不接受。
- 任何发给 Qwen3 的 chat 调用都不能只有单条 system 消息。

## 2. 跨 Bug 的横向教训

### 2.1 调试方法论

- **不要被用户叙述带偏**。用户说"压缩后下一步 chat 报错"，但错误实际发生在 compact 调用里（`kind: "compact_delta"`）。
- **错误位置在结构化字段里**。SSE 事件有 `kind` 字段，决定错误发生在哪一层；不要只看 `text`。
- **错误位置 → 真因 → 修复**。每次重写代码前，问"如果这是真因，console 应该打什么？" 看 console 是否打了那个东西，**再来一遍**。
- **升级诊断密度，而不是重写实现**。当 bug 修不好时，加更多 verbose 日志（多行 + 完整内容 + 字段名），不要换实现。

### 2.2 端到端测试方法论

- **每个调用方对同一契约的"各自实现"是 bug 滋生地**。统一入口比"每个调用方各自保证"更安全。
- **buggy 行为会被测试反向固化**。测试 mock 必须用和真实代码相同的字段访问方式，否则测试通过但真实代码早就坏了。
- **跨组件契约测试要覆盖完整的 stack**。Mock LLM service 的单元测试都通过，但 chat template（连同它的所有隐含假设）只有真实跑一遍才能验证。
- **回归测试要写"反向锁定"**。每修一个 bug，写一个测试断言"如果有人 revert 这个修复，这个测试会失败"。

### 2.3 错误处理方法论

- **`fetch().catch(() => {})` 是错误丢弃，不是错误处理**。SSE 端点必须流式消费才能工作。
- **错误元数据要 verbose，不要只暴露 reason**。`compact_failed(reason="llm_unreachable", error=str(exc))` 应该用 `f"{type(exc).__name__}: {exc}"` 让前端能直接告诉用户 actionable 错误。
- **always-visible status 指示器是诊断工具**。当一个端到端流程可能失败于多个不可见位置（如网络、序列化、模板、projection），在 UI 上始终显示一个 status badge 比"fail silently"好得多。

### 2.4 URL / 路由方法论

- **状态码语义**：404 = 路由不存在（路径问题），5xx = server-side error，2xx + 流内错误 chunk = 业务异常。**先用状态码分类再深入**。
- **URL 路径必须用绝对 baseUrl**。Dev frontend on 3000, backend on 8090。相对路径会被解析到 dev server 404。
- **`api.ts` 里的所有端点都用 `${this.baseUrl}/v1/...`，新加端点必须同样**。

### 2.5 Qwen3 / SGLang 集成方法论

- **Qwen3 chat template 假设消息里至少有 user 行**。`chat_template.jinja:79` 的 `multi_step_tool` 检测，反向扫描找不到非 `<tool_response>` 的 user 消息就 raise。
- **任何发给 Qwen3 的 chat 调用都不能只有单条 system 消息**。`build_compact_messages` 必须返回 `[system, user]` 形状。
- **测试要覆盖完整的 stack，包括 chat template**。Mock LLM service 的测试可以通过，但 chat template 只有真实跑一遍才能验证。

## 4. 反思：哪些"修法"其实是噪音，哪些是真正修

### 真正修（必须保留）

1. **mergeSlashCommandState 显式桥接**（Bug 1）—— 锁定命名契约
2. **isCompleteSlashCommand 完整性检查**（Bug 2）—— Enter handler 的"关闭 popup 后"分支
3. **runCompactSSE 真读 response body**（Bug 3）—— SSE 消费
4. **LLMClient.runCompact 用绝对 URL**（Bug 4）—— 跨 origin 路由
5. **前端 body 加 `messages` 字段**（Bug 3b）—— backend `_collect_messages` 要求
6. **CompactOrchestrator 入口处 dict→Message**（Bug 5）—— 跨层契约统一
7. **build_compact_messages 返回 [system, user]**（Bug 6）—— Qwen3 chat template 兼容
8. **metadata.error 透出 f"{type}: {msg}"**（贯穿多轮）—— verbose 错误
9. **always-visible compactStatus**（贯穿多轮）—— 状态诊断

### 修对了但是诊断噪音（必要时可去掉）

- 加 verbose diagnostic log（如果保留就保持简洁；如果去掉，至少保留 1-2 个关键点）

### 噪音/可去掉的

- 无

## 5. 未来的"不知情 AI"工作清单

如果你（未来的 AI / 工程师）要改 `backend/compact/` 或 `/compact` 相关的任何代码，请：

1. **先看 AGENTS.md trap #20 的简短规则**（10 条核心规则）
2. **改 prompt builder** 时，跑 `tests/test_compact_prompt_builder_template_compat.py` 确认仍能通过 Qwen3 chat template
3. **改 orchestrator** 时，**同时更新**对应的 `_TriggeringLLM` mock（属性访问 vs dict 访问）
4. **改 SSE 流** 时，**必须真读** response body（不能用 `.catch(() => undefined)`）
5. **加新端点** 时，用 `LLMClient` 的 `${this.baseUrl}/v1/...` 模式，不要用相对路径
6. **改错误处理** 时，verbose metadata（`f"{type}: {msg}"`），不要只暴露 reason
7. **改消息类型契约** 时，**所有调用方**统一一次（不要"这个调用方传 dict，那个传 Message"）
8. **写新测试** 时，mock 必须用和真实代码**完全一致**的字段访问方式

不遵守这些会导致**完全相同的 bug 序列**重新出现。

    """把 session.agent.memory.steps 扁平化成 LLM Message 列表。

    smolagents 用 TaskStep (user query) 和 ActionStep (model_output + 工具 observation)。

    from ..llm_service import Message

### 7.6 横向教训

#### 7.6.1 "症状匹配"不是"根因匹配"

trap #21 描述的症状（compact 后下一轮 chat 仍 40k）和本次报告的症状**字面一致**。但根因在完全不同的层：trap #21 是 wire metadata 翻译错误（前端 React state 没到 backend），本次是 mode 路由错误（前端 page glue 的 wire body 字段名错）。**不要让"症状相同"就 skip 重新分析**——每次都要重新从症状反推 chain。

#### 7.6.2 用户叙述里的"找不到某端点"是金信号

trap #21 之前用户都说"chat 不工作了"；这次用户特别说"Network 标签里找不到 POST /v1/chat/completions"。这个细节是**金信号**——它直接说明用户根本没在 chat 路径上。trap #21 整套 fix 都是 chat 路径的，所以**金信号直接排除了 trap #21**。下一个"不知情"AI 看到类似报告时，**第一件事是问"用户在哪个路径"，不是"trap #21 改过没"**。

#### 7.6.3 trap #1 的"两页同步"规则要扩展到"runtime context 同步"

trap #1 说的是"compact 摘要气泡、slash command 弹窗"等 UI 在两页要一致。本次 bug 是同一份"按运行时上下文选 mode"逻辑在两页分别写——trap #1 没明说 wire body 也要共享。**下一个"不知情"AI 加新 wire body 字段时，必须用共享 helper（不要两页各写一份）**。

#### 7.6.4 错误消息的实现和接口必须一致

`orchestrator._collect_messages` 错误消息写 "requires either messages or session_id"，**但代码只 check `messages is not None`**。这意味着 agent 路径在错误消息上是"合法的"，运行时却会 raise。**任何"或"语义出现在 docstring / 错误消息 / type hint 里，代码必须真的处理两个分支**——不要让错误消息许诺的能力在实现里缺席。

#### 7.6.5 silent raise + silent return = 双重隐形

`_run_compact_then_continue` 把 `transient.run_compact(req)` 里的 raise 转化为 `CompactEvent.failed`，再被 `if ev.kind == CompactEventKind.FAILED: return` 静默 return。**两层 silent 让 auto-compact 在 agent 模式下完全无任何可见信号**——用户不报错，UI 不显示，后端 stdout 没有 diagnostic（`[chat] pre-filter` 不在 chat 路径）。**任何"或 raise 或 yield failed"的链都必须保留**至少**一层可见的 diagnostic**（log / counter / status badge）。

#### 7.6.6 单测覆盖了"被修好的部分"≠ 覆盖了"链路"

`test_compact_agent_apply.py` 测了 `_replace_agent_memory`（已被修好的 unit）和 `_compact_event_to_sse`（已被修好的格式），但**完全没测** `_run_compact_then_continue` 这条端到端链。所以 ValueError 一直没被测试发现。**写"功能已实现"的测试时要测"完整功能链"，不是测"链里每个被修过的 unit"**。

#### 7.6.7 前端硬编码字段名 = 后端实现细节暴露

`mode: 'chat'` 在 wire body 里硬编码，**意味着前端被迫了解后端有几个编排器**。一旦后端加 agent/cycle 编排器，前端就出错。**所有"按后端路由分叉"的选择都不应在前端硬编码，而应由共享 helper 封装**（`buildCompactRequestBody({ agentMode })`）。**frontend 不应该知道后端有几种 mode**——它只需要声明"我是 agent 还是 chat"。

## 8. v3 回归：post-compact 2nd turn 仍 "I don't remember"（2026-06-06）

写在 trap #22 落地（agent 模式 /compact 路由到 agent runner，session.agent.memory.steps 真的被 envelope 替换）后。修完 #22 之后用户实测：full context 真的变小了，**但** 用户问"你还记得选了哪个角色吗"时，agent 依然回复"我每次对话都是全新开始"。

### 8.2 trap #22 留下的诊断盲点

trap #22（上一轮）修的是"`mode='agent'` 时 /v1/compact/run 路由到 agent runner、session.agent.memory.steps 真的被 envelope 替换"。修完那一步后，`session.agent.memory.steps` **确实**变成了 `[TaskStep(task=envelope)]`（被 `_replace_agent_memory` 写入）。

### 8.3 诊断路径

#### 8.3.1 先证 envelope 在 run() 前还在

`tests/test_compact_envelope_preserved_on_next_run.py::test_post_compact_llm_call_actually_sees_envelope`（red phase）模拟完整链路：先 `_replace_agent_memory` 写 envelope，然后 capture `agent.write_memory_to_messages()` 的输出，断言 envelope 文本在里面。这一步**确实通过**——说明 envelope 在 run() 之前确实在 memory 里、确实会被序列化成 LLM message。

#### 8.3.2 隔了一层：smolagents `agent.run(reset=True)` 调 `self.memory.reset()`

`_run_basic_stream` 第 3806-3807 行：

```python
_should_reset = not session.has_run
session.has_run = True
```

`reset=True` → smolagents `Memory.reset()` → `memory.steps = []` → envelope 没了。

#### 8.3.3 为什么 `_replace_agent_memory` 让 `has_run = False`？

读 `backend/agent/agent_runner.py:4499`（修 bug 之前）：

```python
session.agent.memory.steps = [TaskStep(task=envelope, task_images=None)]
# Reset routing: next user message goes through coordinator_1
session.has_run = False
session.current_agent_name = cfg.agent.entry_agent_name
session.active_agent = None
```

注释"Reset routing"的真实意图是**让下一轮重新走 coordinator_1 路由**。但这个意图**不需要通过 `has_run = False` 实现**——已经有 `current_agent_name = entry_agent_name` 和 `active_agent = None` 在做这件事。

**`has_run = False` 是一个副作用 bug**。它本意是"路由重置"，但实际触发了下一轮 `_run_basic_stream` 的 `_should_reset = True`，进而 smolagents 抹 envelope。

#### 8.3.4 三个症状为何都是同一个 bug

- **40k → 4k → 40k 中的"4k"**：compact LLM 调用里 envelope 出现、summary 真的生成（4k 是合理，因为 prompt 里只有 envelope 文本没历史）。trap #22 fix 后这一段是对的。
- **第二轮 40k**：smolagents `memory.reset()` 抹 envelope → agent memory 空 → 用户新问题进来 → LLM 看到空历史 → 编出"全新开始"。
- **agent 行为像失忆**：因为 envelope 真的没在 LLM context 里。

### 8.4 修复

`backend/agent/agent_runner.py::_replace_agent_memory`：

```python
# 改前：
session.has_run = False

# 改后：
# CRITICAL: keep has_run=True. The envelope IS the result of
# the just-completed compact, so semantically the agent has
# "run" (and produced this state). If we set has_run=False
# here, the next _run_basic_stream call will set
# reset=True and smolagents will call self.memory.reset(),
# which wipes the very envelope we just wrote.
#
# The re-route (so the next user message goes through
# coordinator_1) is achieved separately below by
# current_agent_name + active_agent reset, NOT by has_run.
session.has_run = True
```

**核心思路**：
- **envelope 本身就是"刚跑完的 compact run"的产物**，所以 `has_run` 在语义上就是 `True`
- **重路由**靠 `current_agent_name = entry_agent_name` + `active_agent = None`，**与 `has_run` 完全无关**

`tests/test_compact_agent_apply.py::test_replace_agent_memory_archives_old_steps`（已存在）原本断言 `session.has_run is False`，**这个断言本身就是 bug 的化石**——更新成 `True` + 注释说明。

### 8.5 横向教训

#### 8.5.1 "链上每段都正确"≠"端到端正确"

trap #22 测的是"`_replace_agent_memory` 之后 memory.steps 有 envelope"——单步断言通过。但**下一步** `agent.run(reset=True)` 会清空 steps。trap #22 没测这一段，所以 envelope 进 LLM 之前就被抹了，trap #22 的测试却全绿。

**写"功能已实现"的测试时要测"完整功能链"，不是测"链里每个被修过的 unit"**。`_replace_agent_memory` 是 unit，下一调用 `agent.run` 是链的下一节；test 应该贯通"compact → run → LLM 看到 envelope"。

#### 8.5.2 "重置"语义在多层都有别名，要选对层

`session.has_run` 这个 flag 在三处被读：
- `_run_basic_stream` 和 `_run_basic_sync` 用来决定 `reset=` 参数
- `_commit_direct_answer_to_shared_memory` 用来跳过 commit
- `_replace_agent_memory` 用来"重置路由"

**一个 flag 三个语义**——这种 overloading 必然会有至少一个语义用错时机。当 7.5.1 (trap #22) 决定让 `_replace_agent_memory` 共享"重置路由"职责给 `has_run` 时，它**无意识地**继承了 `_run_basic_stream` 的 `reset=` 决策。

教训：**任何"重置"语义都应该用独立 flag**，不要复用 `has_run` 这种看似 boolean 实际承载三层职责的字段。如果非要共用，至少要明确文档化"这个 flag 改值时，X 行为会变"。

#### 8.5.3 silent reset 路径 = silent bug 路径

`smolagents.Memory.reset()` 不 raise、不 log、不返回任何信息——它**静默清空** `steps`。这条路径在 smolagents 是 by design（"新一轮"语义），但**对 /compact 后的 envelope 是 hostile**。任何"上游注入 state、下游静默清空 state"的组合都要警惕——尤其当下游 reset 参数是由上游某个非显然的 flag 决定时。

**缓解**：
- 在 `agent.run(reset=True)` 之前，**assert** memory.steps 有 envelope（如果期望有）
- 或者在 `_replace_agent_memory` 时把 envelope 备份到 session 字段（`session.last_envelope`），run() 后校验"memory 里没 envelope 时报错"
- 至少在 `_run_basic_stream` 加一行 `logger.info(f"post-compact run, reset={_should_reset}, has_envelope={any(s.task.startswith(preface) for s in agent.memory.steps if isinstance(s, TaskStep))}")` —— 让 silent reset 留下日志痕迹

#### 8.5.4 "routing reset" 用错 flag

`session.has_run = False` 想做"重置路由"的事——但 smolagents 的 `reset=` 参数恰好读同一个 flag。这是**flag 命名跨层歧义**：`has_run` 在 smolagents 视角是"是否需要重置 memory"，在 agent runner 视角是"是否要重置路由"。两个 reset 是不同的事，但用了同一个 flag。

正确做法：拆成两个 flag。
```python
@dataclass
class AgentSession:
    has_run: bool = False              # smolagents memory.reset 用
    force_reroute: bool = False        # routing 重置用
```

或在 `AgentSession` 之外用一个更明确的"compaction_pending" flag，路由逻辑查这个 flag 而不是 `has_run`。

#### 8.5.5 写完 fix 之后，把"被 fix 改变语义的旧测试"也改了

`tests/test_compact_agent_apply.py::test_replace_agent_memory_archives_old_steps` 旧断言 `has_run is False`。这个断言**本身就是 bug 的化石**——它把"has_run = False"当成了正常行为固化下来，导致任何修这个 bug 的尝试都会先撞上"测试红了"。**改完代码后，回头看每个相关测试断言是否还反映真因；如果断言本身就是 bug 的一部分，连带改**。

## 9. v4 regression：lifespan wiring 顺序错位 → agent 模式 auto-compact 永远不触发（2026-06-07）

trap #20 ~ #23 全部修完、用户验证 manual /compact 和 post-compact envelope 都正常之后，用户**实测第 N 轮对话**：

> "我都累积到 44k tokens 了，第 n 轮对话还是出现"任务调度"卡片（for coordinator_1）。没有任何自动压缩被 triggered."

manual /compact 完美工作、post-compact 上下文变小、envelope 保留 —— 但 **auto-compact 永远不触发**。这是和 trap #20 ~ #23 完全不同的 bug 链。

### 9.1 调查路径

第一直觉是 TokenCounter 数错了（之前 fix 过 heuristic 4x 偏小、BatchEncoding `len()` = 2）。我先验证了：

- 端到端模拟 200 个长 step（每个 3200 字符） → TokenCounter 报 ~50k 真实 token（用真的 AutoTokenizer，`apply_chat_template(tokenize=True, return_tensors=None, return_dict=False)`），threshold 45k → `should_compact=True` ✅
- 真实 SGLang `#full token: 44k` → 阈值应该早就过

TokenCounter 修对了，那 auto-compact 为什么不进 `_run_compact_then_continue`？

直接 print：
```python
print(runner.compact_orchestrator)  # None
print(app.state.compact_orchestrator)  # <CompactOrchestrator>
```

`agent_runner.compact_orchestrator` **永远是 None**。`app.state.compact_orchestrator` 是有的。**两条路径不指向同一个对象**。

### 9.2 真因：lifespan 启动顺序错位

`backend/main.py` 里这段 wiring 代码（`dab5aae` commit 2026-06-06 引入）：

```python
# 1. AgentRunner 实例化（此时 compact_orchestrator=None）
agent_runner = AgentRunner(llm_service=service, config=config)

# 2. Wiring 块（在 compact_orchestrator 之前就跑）
if app.state.compact_orchestrator is not None:  # ← 永远是 None!
    agent_runner.compact_orchestrator = app.state.compact_orchestrator

# 3. CompactOrchestrator 实例化（太晚了）
app.state.compact_orchestrator = CompactOrchestrator(...)
```

`if A and B is not None: wire(A, B)` 这种"两个都已就绪就 wire"的模式在 `A` 和 `B` 有 init 顺序依赖时**会静默跳过**。`A = agent_runner`（先就绪），`B = compact_orchestrator`（后就绪）—— wiring 块在 B 就绪**之前**跑，guard 永远 False，wiring 永远不发生。

**这个 bug 从 2026-06-06 dab5aae commit 埋下，到 2026-06-07 用户实测才暴露 —— 整整一天。**

### 9.3 为什么 trap #20 / #22 / #23 都没抓到

| trap | 关注点 | 为什么不抓 lifespan wiring bug |
|------|--------|------------------------|
| #20 (compact API endpoint) | `/v1/compact/run` 端点 | 该端点用 `app.state.compact_orchestrator`（已正确初始化），**绕开了 agent_runner**。manual /compact 走的就是这条独立路径，**完全不受 wiring bug 影响** |
| #22 (agent mode 路由到 runner) | mode='agent' 时 `/v1/compact/run` 路由到 `agent_runner.run_compact_for_session` | 同上，是 manual 路径的路由，不经过 `_should_auto_compact_session` |
| #23 (post-compact has_run) | `_replace_agent_memory` 后的 flag 设置 | 该方法只在 auto-compact 触发后才被调用，wiring bug 让它永远不被调用 |

**manual /compact 三层都 work → 用户不知道 agent_runner 那个 wiring 块有问题**。

### 9.4 为什么 unit test 全绿但 production 坏

`test_compact_agent_apply.py::test_should_auto_compact_returns_false_without_orchestrator`：
```python
runner = AgentRunner(llm_service=_StubLLM(), config=cfg, compact_orchestrator=None)
session = _make_session_with_steps(["hi"])
assert runner._should_auto_compact_session(session) is False  # ← bug 的化石
```

这个测试**正面断言**了"如果 `compact_orchestrator` 是 None，auto-compact 不触发"。它**记录了 bug 行为而不是契约**。如果有人写成 `runner = AgentRunner(..., compact_orchestrator=object())` 然后断言 `True`，他必须 mock 整个 TokenCounter + LLM service + threshold chain，**没人这么干**，因为 `_should_auto_compact_session` 的 unit test 都集中在"无 orchestrator 时返回 False"这一个负面 case。

**没有一条测试**覆盖"lifespan 启动后 `app.state.agent_runner.compact_orchestrator` 是非 None"。这是 trap #16 反复警告的"lifespan 集成契约"真空。

### 9.5 修复

把 wiring 块从 agent_runner 实例化**之后**移到 compact_orchestrator 实例化**之后**：

```python

# 1. AgentRunner 实例化（无 compact_orchestrator）
agent_runner = AgentRunner(llm_service=service, config=config)

# 2. CompactOrchestrator 实例化
app.state.compact_orchestrator = CompactOrchestrator(...)

# 3. Wiring（现在 B 已就绪，guard 通过）
if app.state.compact_orchestrator is not None:
    agent_runner.compact_orchestrator = app.state.compact_orchestrator
```

加注释明示"必须先就绪被赋值方再 wire"。

### 9.7 横向教训

#### 9.7.1 "manual 路径能 work" 永远会蒙混测试

`/v1/compact/run`（manual）走 `app.state.compact_orchestrator` —— **完全独立于** `agent_runner.compact_orchestrator`。前者正常初始化、后者 wiring 顺序错位。**任何"端到端 manual 工作"都不能证明"auto-trigger 工作"**。

教训：**当一个系统有 manual + auto 两条触发路径时，必须有测试分别验证两条路径都能走通。manual 通过 ≠ auto 通过**。本 bug 是这条原则最干净的实例。

#### 9.7.2 `if A and B is not None: wire(A, B)` 是 silent failure 温床

guard 模式"两个都已就绪才 wire"在**任一**未就绪时静默跳过。`A` 和 `B` 有 init 顺序依赖时这是必然 bug：

- 没有 error log
- 没有 warning
- 没有 metric
- 任何后续使用方只会看到 `None` / "missing dependency"，**完全不知道是 init 顺序问题**

缓解（按优先级）：
1. **顺序保证**：被赋值方先就绪，wiring 块最后。`main.py` 顶部画依赖图、按拓扑序写 lifespan。
2. **集中 wiring**：所有 `app.state.X` 的 wiring 集中到 lifespan 末尾、**显式顺序**的函数里写，不要散落在不同 init 块之间。
3. **post-wire assertion**：`assert X.attribute is not None`，让 production 启动时立即 fail。
4. **failure log**：guard 跳过时打 `logger.error("wiring skipped: A={...}, B={...}")`，至少留下"曾经试图 wire 但失败了"的痕迹。

#### 9.7.3 "没破坏 unit test" ≠ "没破坏 production"

14 个 compact unit test 全绿、`npm run build` 干净 —— 整个 2026-06-06 ~ 2026-06-07 之间没人发现 agent mode auto-compact 不工作。原因：所有 AgentRunner 的测试都 `AgentRunner(llm_service=stub, config=cfg, compact_orchestrator=object())` 直接传参，**没有人 run 过 lifespan**。

教训：**集成契约必须有 lifespan 集成测试**。Unit test 验证"如果 wiring 正确，A 行为是这样"；lifespan 集成测试验证"wiring **真的发生了**"。两者缺一不可。

#### 9.7.4 "记录 bug 行为" vs "记录正确契约" 的测试化石

`test_should_auto_compact_returns_false_without_orchestrator` 的断言 `runner._should_auto_compact_session(session) is False` **正确地记录了当 orchestrator 是 None 时的行为** —— 但因为没有"lifespan 必须 wire" 的配套断言，**它把"无 orchestrator = 无 auto-compact"这条真实契约当成唯一契约**记录下来，让"wiring 错了也没事"被测试"合法化"。

教训：**写负面 case 测试时，配套一条正面 case + 集成契约**。否则负面 case 会变成 bug 化石，永久锁定 buggy 行为。
