## 1. Cycle + share_context 多轮视觉写文件问题复盘

### 1.0. 适用范围

本文记录的是本项目 `cycle` 模式下、`share_context=true` 时，视觉 Agent 在多轮对话里逐轮观察画面并调用 `write_file` / `edit_file` 写文件时暴露出的真实问题、错误修复路线、有效修复路线，以及基于用户实测反馈得到的经验教训。

重点场景：

- 第 1 轮：看图并 `write_file`
- 后续轮：继续看图并 `edit_file` append 变化点
- `share_context=true` 时需要复用历史上下文
- 模型是本地弱工具调用 VLM，因此对历史消息的“形状”极其敏感

### 1.1. 最初症状

用户最初反馈：

- `share_context=false` 时，cycle 多轮调用工具基本正常
- `share_context=true` 时，第 2 轮开始就可能不再调用工具
- 具体表现为：
  - 不调用 `edit_file`
  - 直接口头说“已完成”
  - 或直接输出一段“变化点”文本，但没有真正写入文件
  - 还会伴随明显视觉幻觉

这说明问题不在“普通聊天链路”，而在“多轮记忆重建 + 本地 VLM 工具调用行为”这条链路上。

---

### 1.2. 整体排障时间线

#### 阶段 A：最早怀疑是历史 observation 中的工具转录稿污染

最开始注意到，某些历史 observation 不是纯工具结果，而是带着类似如下包装：

- `Called the Read tool with the following input: ...`
- `<path>...</path>`
- `<type>...</type>`
- `<content>...</content>`

于是加入了 `_strip_historical_tool_transcript_text()`，把这类 XML/转录稿外壳剥掉，只保留真正内容。

结论：

- 这是一个**有价值但不是根因**的修复
- 它能降低历史噪音，但不能解决“第 2 轮开始不调工具”的主问题

#### 阶段 B：用户新日志显示，历史里保留的主要是“成功回执”

用户贴出新日志后，发现模型下一轮看到的历史更像：

- `文件已写入成功。`
- `已追加变化信息到 /path/...`

而不是“真正写进文件的内容”。

于是加入两类修复：

1. `_historical_tool_artifact_text()`
   - 对 `write_file` 保留 `arguments.content`
   - 对 `edit_file` append 保留 `replace_text`
   - 对 `edit_file` replace 也保留替换后的正文

2. `_historical_final_answer_text()`
   - 过滤掉泛化的文件操作成功回执
   - 避免历史里充满“写入成功 / 已追加完成”之类短句

结论：

- 这是**方向正确的关键修复**
- 它让历史重新保留“真正写了什么”，而不只是“写成功了”
- 但它还没有解决“历史工具调用模式本身被抹平”的问题

#### 阶段 C：为了保留轮次边界，加入了通用 assistant 边界 `已完成。`

当我们压缩历史消息时，发现如果一个历史轮次末尾没有 assistant 文本，那么就会出现连续两个 USER 消息：

- 上一轮 observation
- 下一轮 `New task:`

而 smolagents / `get_clean_message_list()` 会把连续同角色消息合并，这会破坏轮次边界。

于是加入了一个中性边界文本：

- `已完成。`

结论：

- 这一步**本身是必要的**
- 但如果历史里除了 observation 就只剩一串 `已完成。`，又会把模型诱导成“任务来了就说已完成”
- 所以 `已完成。` 只能作为**边界补丁**，不能成为历史主体

#### 阶段 D：第一次错误路线，把历史工具轮次改写成普通 assistant 摘要

后来为了避免历史里出现过多 `已完成。`，做了一个错误尝试：

- 如果历史工具步的 `model_output` 被清洗为空，就从 `tool_calls.arguments` 生成动作摘要，例如：
  - `获取时间。`
  - `写入文件 /path/...。`
  - `追加到文件 /path/...。`

这在表面上看起来更“自然”，但用户马上实测发现：

- 效果反而明显变差
- 本地模型在第 2 轮就开始“摆烂”
- 直接模仿这些摘要
- 输出 `获取当前时间。`
- 或直接输出一整段 `变化点`
- 完全不再调用 `edit_file`

这是本轮排障里**最明确的负优化**。

#### 阶段 E：最终回到正确路线，保留“清洗后的工具调用模式”

最终的有效方案不是“让历史更像自然对话”，而是让历史继续像“工具执行过的痕迹”，只是把噪音去掉。

最终策略：

- 历史轮次不再保留真实 `TOOL_CALL` / `TOOL_RESPONSE` 角色消息
- 但保留它们的**文本化、清洗版结构**：
  - assistant: `Calling tools: [...]`
  - user: `Observation:\n...`
  - assistant: `已完成。` 或过滤后的最终边界

同时：

- Observation 优先保留真实 artifact 内容
- 文件成功回执型 final answer 尽量压成 `已完成。`
- 像 `已将画面信息写入文件。` 这类口头汇报也不再喂回模型

这条路线是当前用户反馈“效果好了很多”的版本。

---

### 1.3. 为什么前几个修复会失败

#### 1.3.1 失败原因一：只清理 observation 噪音，不足以恢复工具调用行为

仅仅去掉 XML 包装、工具转录稿外壳，最多只能让 observation 更干净。

但真正决定模型下一轮是否继续调工具的，是：

- 历史看起来像不像“工具调用完成任务”
- 还是看起来像“普通 assistant 已经口头答完了”

前者会诱导模型继续走工具协议，后者会诱导模型直接输出文本。

#### 1.3.2 失败原因二：只保留成功回执，会让模型学会“汇报完成”

如果历史里主要是：

- `文件已写入成功。`
- `已追加变化信息到 ...`

那么模型学到的模式不是“调用 edit_file”，而是“写一句完成说明”。

#### 1.3.3 失败原因三：把历史工具轮次自然语言摘要化，会把工具协议抹平

这次最大的教训：

对于本地弱工具调用模型，**历史消息过于自然语言化是有害的**。

把历史改写成：

- `获取时间。`
- `写入文件 /...`
- `获取当前时间。`

看起来“语义更清楚”，但实际上等于把“工具调用轨迹”改写成了“assistant 普通叙事”。

模型下一轮最容易模仿的，不是底层 schema，而是最近的文本模式。

于是它就不调工具了。

#### 1.3.4 失败原因四：保留“已将画面信息写入文件。”这类口头总结也会继续误导

这类 final answer 虽然比 `已完成。` 更具体，但本质上仍然是“口头汇报”。

如果历史里反复出现：

- `已将画面信息写入文件。`
- `获取当前时间。`
- `2026-... **变化点：** ...`

那么模型会越来越认为：

- 自己的任务是“口头总结已经做了什么”
- 而不是“继续输出合法 tool call”

---

### 1.4. 这轮调试里哪些修改是好的

#### 1.4.1 好修改：`_strip_historical_tool_transcript_text()`

作用：

- 清洗历史 observation 中的工具转录稿包装
- 保留真正事实内容

评价：

- 不是根因修复
- 但属于长期保留的辅助优化

#### 1.4.2 好修改：`_historical_tool_artifact_text()`

作用：

- 对 `write_file`：保留 `file_path + content`
- 对 `edit_file` append：保留 `file_path + replace_text`
- 对 `edit_file` replace：保留替换后的正文内容

评价：

- 这是本轮排障中的核心正向修复之一
- 它避免历史只剩“成功回执”
- 让后续轮次还能真正“看到上一轮写了什么”

#### 1.4.3 好修改：`_historical_final_answer_text()` 对文件成功回执进行过滤

作用：

- 过滤：
  - `文件已写入成功。`
  - `已追加变化信息到 ...`
  - `已将画面信息写入文件。`
  - 其他类似“只说明完成、没有新事实”的 final answer

评价：

- 非常重要
- 否则模型会被历史里的口头汇报强烈带偏

#### 1.4.4 好修改 😍 ：只把历史轮次保留成“清洗版 Calling tools / Observation 文本”

这是当前最关键、效果最好的方案。

原则：

- 历史轮次保留工具使用模式
- 但不保留真实的 smolagents `TOOL_CALL` / `TOOL_RESPONSE` role
- 形式上改成纯文本：
  - assistant: `Calling tools: [...]`
  - user: `Observation:\n...`

评价：

- 对本地工具调用模型更友好
- 它既保留“我是通过工具完成任务的”模式提示
- 又避免真实 role 消息重新污染整个历史结构

#### 1.4.5 好修改：当前轮依旧保留完整 TOOL_CALL / TOOL_RESPONSE

原则：

- 历史轮次：文本化、清洗版工具轨迹
- 当前轮次：完整原始 tool trace

评价：

- 这是当前最平衡的策略
- 历史用来提示模式
- 当前轮用来真正执行多步推理

#### 1.4.6 好修改：把 `tests/test_cycle_executor.py` 的异步标记改成 `@pytest.mark.anyio`

这不是业务根因，但它很重要：

- 原来这些测试在当前环境里根本跑不起来
- 改成 `anyio` 后，`share_context=true/false` 的路径才能真的回归验证

---

### 1.5. 这轮调试里哪些修改是坏的

#### 1.5.1 坏修改：把问题误判成“仅仅是 observation 转录稿污染”

表现：

- 只做了 observation 包装清洗
- 没有解决工具调用模式丢失

结论：

- 这是一个有用的局部优化
- 但如果把它当成根因，就会误导后续修复

#### 1.5.2 坏修改：历史工具轮次自然语言摘要化

表现：

- assistant 历史里出现：
  - `获取时间。`
  - `写入文件 /...。`
  - `追加到文件 /...。`

用户实测反馈：

- “这次效果差了很多”
- “local llm 在第二轮就直接摆烂了”

结论：

- 这是本轮明确的错误路线
- 必须避免再次回到这个方向

#### 1.5.3 坏修改：让 `已完成。` 成为历史主体

表现：

- 历史轮次里反复出现：
  - assistant: `已完成。`
  - user: observation
  - assistant: `已完成。`

用户实测反馈：

- “第 3 轮或第 4 轮时模型直接偷懒，不遵循命令而是直接说‘已完成’”

结论：

- `已完成。` 只能作为边界补丁
- 绝不能让它取代真正的工具轨迹

#### 1.5.4 坏修改：保留“已将画面信息写入文件。”这类口头 final answer

表现：

- 这类回复虽然不像 `已完成。` 那么空
- 但仍然会让模型继续学习“口头汇报已经写了文件”

结论：

- 仍然属于坏信号
- 应作为回执过滤掉，而不是继续保留在历史里

---

### 1.6. 用户效果反馈总结（最重要）

下面这张表是本轮排障里最值得保留的部分，因为它直接反映“哪种方案对本地模型是好方案，哪种是坏方案”。

| 阶段 | 修改方案 | 用户反馈 | 结论 |
|---|---|---|---|
| A | 仅清理 observation 包装噪音 | `还是不行` | 有帮助，但不是主因 |
| B | 保留 file artifact，过滤 success receipt | `好一点了`，但后续轮次仍会偷懒 | 正确方向，但还不够 |
| C | 大量使用 `已完成。` 作为历史边界 | 第 3/4 轮开始直接说 `已完成。` | 只能少量使用，不能成为主体 |
| D | 用 `获取时间。/写入文件...` 等摘要替代历史工具轨迹 | `效果差了很多`，第 2 轮就摆烂 | 明确负优化，必须避免 |
| E | 保留清洗版 `Calling tools:` / `Observation:` 文本模式，同时保留 artifact、过滤回执 | `经过简单测试，效果好了很多` | 当前最优方案 |

这张表的意义很大：

- 它说明本地模型不是“摘要越自然越好”
- 相反，**越接近工具轨迹的历史形状，越稳定**

---

### 1.7. 当前结论：本地弱工具调用模型最怕“历史被改写成普通对话”

这一轮最大的总经验：

> 对本地弱工具调用 VLM 而言，`share_context` 历史消息不能被过度自然语言化。

更具体地说：

#### 应保留的东西

- 历史轮次里“曾经发生过工具调用”这一模式
- 真实写入/追加到文件的 artifact 内容
- 必要的轮次边界

#### 应过滤的东西

- 成功回执短句
- 口头汇报型 final answer
- observation 包装噪音

#### 绝对不要做的事

- 把历史工具轮次改写成普通 assistant 摘要
- 让模型看到一串“获取时间 / 写入文件 / 获取当前时间”
- 让历史看起来像自然聊天，而不是工具工作流

---

### 1.8. 当前推荐的历史压缩规则

对于 `share_context=true` 的 cycle 多轮工具调用场景，推荐遵守以下规则：

1. 当前轮次保留完整 `TOOL_CALL / TOOL_RESPONSE`
2. 历史轮次不要保留真正的 TOOL role 消息
3. 历史轮次保留成清洗后的文本模式：
   - assistant: `Calling tools: [...]`
   - user: `Observation:\n...`
4. 对文件类工具，Observation 优先保留真实 artifact 内容
5. 文件成功回执型 final answer 尽量压成 `已完成。` 或直接不保留具体口头总结
6. `已完成。` 只能用于轮次边界，不能成为历史主体
7. 每次修改记忆压缩逻辑后，都必须对照真实 `[MSG-DUMP]` 复核

---

### 1.9. 本轮新增/修复的测试

本轮围绕 `write_memory_to_messages()` 和 cycle 运行链路，新增或修正了以下测试方向：

#### 1.9.1 memory 相关

- 历史 observation 去包装测试
- 历史 `write_file` 保留正文而不是成功回执
- 历史 `edit_file` append 保留追加内容而不是成功回执

### 1.10. 本轮排障中真正起决定作用的证据

这次不是靠猜修出来的，真正起决定作用的是下面这些证据：

1. 用户连续多轮真实测试反馈
2. `[MSG-DUMP]` 中每轮发给 SGLang 的最终消息结构
3. 手工重放 `write_memory_to_messages()` 的输出，直接看 reconstructed history 长什么样
4. 回归测试逐步从“误判行为”迁移到“真实目标行为”

特别重要的一点：

> 这类问题不能只靠单元测试判断，必须结合真实多轮日志看“模型到底看到了什么”。

### 1.11. 后续排障建议

如果以后再改 `write_memory_to_messages()`，建议按下面顺序验证：

1. 先跑单测
2. 再做最小 memory replay，直接打印 history 消息
3. 再跑真实 cycle 多轮测试
4. 对照 `[MSG-DUMP]` 检查：
   - 有没有历史 assistant 摘要化
   - 有没有 success receipt 残留
   - 有没有连续 USER 消息被合并的风险
   - 有没有把当前轮工具 trace 弄丢

建议重点观察的坏信号：

- 历史里出现大量：
  - `获取时间。`
  - `写入文件 ...`
  - `获取当前时间。`
  - `已将画面信息写入文件。`
  - `已完成。`（高密度出现）

如果看到这些，基本说明又在朝错误方向走。

---

### 1.12. 一句话总结

本轮最大的经验教训不是“怎样把历史写得更自然”，而是：

> 对本地弱工具调用模型，`share_context` 历史必须保留“工具调用发生过”的清洗版结构；一旦把历史改写成普通 assistant 摘要，模型就会迅速停止调工具，转而直接口头摆烂。

## 2. vLLM Container 上下文预算 400 问题复盘

### 2.0. 适用范围

本文记录的是本项目在 `vLLM` container 模式下暴露出来的“请求上下文预算收敛”问题。

它不是单独某一个页面、某一个接口、或某一个 streaming 分支的问题，而是同时影响以下链路：

- text 页面 `/`
- vision 页面 `/vision`
- 普通聊天 `/v1/chat/completions`
- agent 聊天 `/v1/agent/chat`
- streaming 与 non-streaming

需要特别强调：

- text 与 vision 仍然是两套独立前端页面
- 普通聊天与 agent 仍然是两条独立后端 API 链路
- 但这次报错的根因位于它们更下层共用的“推理请求 token budget 收敛层”

---

### 2.1. 最初症状

用户在 container + `vLLM` 模式下反复遇到如下错误：

- `vllm.exceptions.VLLMValidationError: max_tokens=262144 cannot be greater than max_model_len=max_total_tokens=160000. Please request fewer output tokens.`
- `vllm.exceptions.VLLMValidationError: You passed 10133 input characters and requested 160000 output tokens. However, the model's context length is only 160000 tokens ...`

前端表象是：

- 流式请求直接 `400`
- 前端出现“流式生成错误”
- 看起来像是 streaming 出错
- 某些场景下会误以为是 agent/tool calling 或 vision 页面的问题

但从报错内容本身可以看到，错误是在 `vLLM` 预处理阶段就已经触发了，还没进入真正的生成阶段。

---

### 2.2. 这次最容易误判成什么

这次问题非常容易被误判成下面几类：

#### 2.2.1 误判一：这是前端页面问题

因为用户首先是在页面上看到报错，所以很容易先怀疑：

- text 页与 vision 页逻辑不同步
- 前端把 `maxTokens` 发错了
- 某个页面初始化配置异常

结论：

- 前端确实参与了问题放大
- 但不是根因
- 根因在后端没有把“真实可用上下文”和“请求输出上限”统一收口

#### 2.2.2 误判二：这是 agent / streaming 特有问题

因为项目里确实已经踩过：

- `Qwen3-VL` 在 `SGLang auto + stream` 下空增量
- agent 链路与普通聊天链路不同
- vision 页面与 text 页面不同

所以很容易把这次问题继续往：

- `backend/agent/local_llm_model.py`
- SSE 事件流
- tool call 解析

这些方向上怀疑。

结论：

- 这次真正报错来自 `vLLM` 对请求 token budget 的校验
- 不是这类上层解析逻辑先出错

#### 2.2.3 误判三：只要处理 `max_tokens > max_model_len` 就够了

最开始看第一条报错时，很容易以为只要把：

- `max_tokens <= max_model_len`

保证住就行。

结论：

- 这只解决了一半
- 另一半是：`prompt_tokens + output_tokens` 的总预算也不能超过上下文窗口
- 所以即使 `max_tokens` 没有单独超过 `max_model_len`，仍然可能因为“输入 + 输出总和超限”而被 `400`

---

### 2.3. 根因拆解

这次问题的根因不是一个点，而是多个“看起来都合理、但叠在一起就会出错”的因素同时存在。

#### 2.3.1 根因一：`inference.max_tokens` 被错误地配置成接近总上下文长度

项目里 `inference.max_tokens` 的真实语义应该是：

- 单次请求允许生成的最大输出 token 数

但历史配置把它写成了：

- `262144`

这会导致系统误以为“默认每次都可以请求一个接近整窗的输出长度”。

问题在于：

- 它不是模型理论总上下文长度字段
- 更不是当前活跃后端在当前部署方式下的安全输出默认值

#### 2.3.2 根因二：container 启动脚本把 `--max-model-len` 硬编码成了 `160000`

`scripts/run_vllm_container.sh` 历史上直接写死了：

- `--max-model-len 160000`

这会带来一个非常危险的错位：

- YAML / 前端 / 模型配置层面看起来像是 `262144`
- 实际 container 里跑起来的 `vLLM` 上限却是 `160000`

于是：

- 用户界面看到的是一个偏大的安全错觉
- 真正服务端执行时却按更小的窗口校验

#### 2.3.3 根因三：`/config` 与 `/v1/models` 暴露的是“模型理论值”，不是“活跃后端真实值”

历史上前端初始化拿到的 `max_context_length` 更接近：

- `config.model.max_context_length`

它代表的是模型理论能力或配置静态值，而不是：

- 当前正在运行的后端是谁
- 当前后端到底用了多大的上下文窗口
- 当前 container / 本地服务真实限制是多少

这导致前端会把一个“理论上限”继续当成“当前运行时安全值”使用。

#### 2.3.4 根因四：前端会沿用 `localStorage` 中旧的 `maxTokens`

即使后端后来返回了更安全的默认值，如果前端仍然保留历史 `localStorage` 中的大值：

- 旧设置仍可能继续被发送

于是问题不会因为单纯修改 YAML 就自然消失。

#### 2.3.5 根因五：`VLLMProvider` 发送前只防了“单字段超限”，没有防“总预算超限”

历史实现里更偏向于处理：

- `max_tokens > max_model_len`

但没有在发送前统一计算：

- 预计 prompt token
- 剩余上下文预算
- 安全余量
- 最终应该发给后端的 `max_tokens`

因此许多请求会在 `vLLM` 侧才第一次发现自己非法，然后直接 `400`。

---

### 2.4. 这次真正有效的修复

这次修复的关键，不是单点打补丁，而是把“真实上下文上限”和“请求输出预算”统一收口。

#### 2.4.1 修复一：新增统一收口函数

在 `backend/llm_service.py` 中新增并统一使用：

- `resolve_backend_context_length()`
- `resolve_effective_max_tokens()`

它们负责把：

- 活跃后端是谁
- 当前后端真实上下文上限是多少
- 当前请求的目标输出上限是多少

统一折叠成一个运行时安全值。

#### 2.4.2 修复二：对 `vLLM` / `openai_proxy` 请求在发送前主动裁剪 `max_tokens`

新增逻辑会先粗估 prompt token，再基于：

- 后端真实上下文长度
- prompt 估算长度
- safety margin

主动把 `max_tokens` 收敛到剩余预算内。

这一步非常关键，因为它把错误从：

- “发出去后被服务端 400 拒绝”

提前变成了：

- “发送前就在本项目后端内部完成自动收口”

#### 2.4.3 修复三：对两类 `vLLM` 400 报错做自动重试

这次补了两种自动修复路径：

1. `max_tokens` 自身超过服务端限制
2. `prompt + output` 总预算超过服务端上下文限制

也就是说，不再只处理第一种报错文本，而是把第二种“总预算超限”的情况也补齐了。

#### 2.4.4 修复四：`/config` 与 `/v1/models` 改为暴露“活跃后端真实上限”

现在前端初始化时拿到的：

- `model.max_context_length`
- `inference.max_tokens`

已经不再是模型理论静态值，而是根据当前活跃后端实时收敛后的安全值。

这一步解决的是“系统说能用，实际又不让用”的错位问题。

#### 2.4.5 修复五：vllm container 启动脚本改为从 YAML 读取 `vllm.max_model_len`

`scripts/run_vllm_container.sh` 不再硬编码：

- `160000`

而是改为读取：

- `config/*.yaml` 中的 `vllm.max_model_len`

这使得：

- 配置文件
- 实际启动命令
- 运行时服务上限

终于回到同一个事实来源。

#### 2.4.6 修复六：前端启动时钳制历史 `localStorage.maxTokens`

text 页和 vision 页都补了同样的初始化逻辑：

- 先读取后端返回的安全 `max_tokens`
- 再把 `localStorage` 中旧的 `maxTokens` 钳制到这个上限之内

这一步解决的是“后端已经修了，但浏览器还在带着历史危险值继续发”的问题。

#### 2.4.7 修复七：配置默认值回归到“输出上限”语义

当前项目已经把：

- `inference.max_tokens`

默认值收回到：

- `4096`

并且把：

- `inference.max_new_tokens`

保留为与其同步的兼容字段，而不是另一套独立配置源。

### 2.5. 这次调试里哪些判断是错的

| 错误判断 | 为什么错 | 正确结论 |
|---|---|---|
| 这是某个前端页面独有问题 | text / vision 页面确实独立，但二者共用同一套后端预算收敛逻辑 | 页面只是症状暴露点，根因在后端 budget 层 |
| 这是 agent / stream 独有问题 | 报错发生在 `vLLM` 请求校验阶段，普通聊天同样会中招 | agent 与普通聊天只是不同入口，底层同样会触发 |
| 只要限制 `max_tokens <= max_model_len` 就够了 | 还存在 `prompt + output > context` 的总预算超限 | 必须同时处理“单字段超限”和“总预算超限” |
| `model.max_context_length` 可以直接暴露给前端 | 这通常更像模型理论值，不一定等于当前运行后端真实上限 | 前端应拿运行时活跃后端的真实上限 |
| 改 YAML 就能彻底修好 | 浏览器里旧 `localStorage.maxTokens` 仍可能继续污染请求 | 前端必须在启动时钳制历史值 |
| container 脚本里写死一个经验值问题不大 | 一旦与 YAML/后端返回值不一致，就会形成新的隐性错位 | 运行脚本也必须跟随配置读取 |

### 2.6. 本次 container 链路最重要的经验教训

#### 2.6.1 教训一：运行时上限必须只有一个“事实来源”

如果以下几处不一致：

- 模型理论配置
- YAML 配置
- container 启动参数
- `/config` 暴露值
- 前端本地持久化值

那最终一定会出现“前端以为能发，后端实际上不接”的错位。

#### 2.6.2 教训二：模型理论上下文长度不等于当前部署真实可用长度

尤其在 container、量化、GPU 内存约束、显式 `--max-model-len` 等条件下：

- 模型卡上写的最大上下文
- 当前服务实例真正开放给请求的上下文

经常不是同一个数。

#### 2.6.3 教训三：前端默认值必须来自运行时，而不是静态配置想象

前端初始化参数如果不从运行时 `/config` 拿安全值，而是依赖：

- 旧缓存
- 静态默认值
- 模型理论值

就会持续制造错误请求。

#### 2.6.4 教训四：发送前收口比失败后补救更重要

只在收到 `400` 之后再修正，虽然比完全不修要好，但仍然会：

- 增加一次失败请求
- 增加流式错误感知
- 让前端用户看到不必要的异常

更好的策略是：

- 发送前先算剩余预算
- 再把 `max_tokens` 收敛到安全区间

#### 2.6.5 教训五：历史命名兼容可以保留，但必须统一语义

本项目内部仍然保留了一些历史命名，例如：

- 函数参数名 `max_new_tokens`
- 配置兼容字段 `inference.max_new_tokens`

这些名字可以暂时不动，但语义上必须明确：

- 它们不再代表另一套独立配置
- 都应统一指向“单次请求输出上限”这一件事

### 2.7. 截至补写当天的最新版官方参数区分表

下面这张表只聚焦本次问题真正需要区分的三类上限。

| 类别 | SGLang 官方参数名 | vLLM 官方参数名 | 正确语义 |
|---|---|---|---|
| 整个上下文 token 上限 | 服务端 `--context-length` | 服务端 `--max-model-len` | 单请求可用的总上下文窗口，上限作用于“输入 + 输出”的总和 |
| 单次输出 token 上限 | 原生 `/generate` 用 `sampling_params.max_new_tokens`；OpenAI 兼容接口通常传 `max_tokens` | Chat Completions 新版更推荐 `max_completion_tokens`，`max_tokens` 仍兼容但已 deprecated；Completions 用 `max_tokens`；此外 `generation_config.max_new_tokens` 可形成服务端统一输出上限 | 这次请求最多生成多少 token，不表示整窗大小 |
| 单次输入 / prefill / batch 相关限制 | `--max-prefill-tokens`、`--chunked-prefill-size`、`--prefill-max-requests`、`--max-total-tokens` | `truncate_prompt_tokens`、`--max-num-batched-tokens`、`--enable-chunked-prefill`、`--max-num-partial-prefills`、`--long-prefill-token-threshold` | 它们是输入裁剪、prefill batch、chunk 调度或内存池相关限制，不等于“单请求总上下文长度”，也不等于“单次输出上限” |

这张表最重要的结论是：

- `context-length` / `max-model-len` 管的是总窗口
- `max_new_tokens` / `max_tokens` / `max_completion_tokens` 管的是输出
- prefill / batched / chunked 参数管的是调度、裁剪或内存，不应拿来替代前两类参数

### 2.8. 最容易混淆的官方参数说明

#### 2.8.1 `SGLang --max-prefill-tokens` 不是“单请求输入上限”

截至补写当天，SGLang 官方文档对它的描述是：

- `The maximum number of tokens in a prefill batch.`

它强调的是：

- prefill batch
- batch 级 token 总量

而不是：

- 单个请求的总上下文窗口
- 单个请求本轮允许新增多少输出 token

#### 2.8.2 `SGLang --chunked-prefill-size` 不是上下文窗口

官方描述是：

- `The maximum number of tokens in a chunk for the chunked prefill.`

也就是“每个 prefill chunk 的大小”，不是单请求总预算。

#### 2.8.3 `SGLang --max-total-tokens` 更像内存池/KV cache 总预算

官方描述是：

- `The maximum number of tokens in the memory pool.`

因此它更接近：

- 服务端整体资源池上限

而不是“单次请求上下文上限”。

#### 2.8.4 `vLLM truncate_prompt_tokens` 不是总窗口，也不是输出上限

它的语义更接近：

- 对输入 prompt 做截断

所以它不是：

- `max_model_len`
- `max_tokens`
- `max_completion_tokens`

#### 2.8.5 `vLLM --max-num-batched-tokens` 是调度迭代上限，不是单请求窗口

官方描述是：

- `Maximum number of tokens that can be processed in a single iteration.`

它是调度/吞吐参数，不表示单个请求能占满多少上下文。

#### 2.8.6 `vLLM --enable-chunked-prefill` 只是 prefill 分块开关

官方描述里明确提到：

- prefill requests can be chunked based on the remaining `max_num_batched_tokens`

所以它与：

- 单请求总上下文长度
- 单请求输出上限

都不是一个概念。

#### 2.8.7 “模型接受用户一次输入的新增 token 上限”这件事，官方并没有给出一一对应的统一参数

截至补写当天，无论是 SGLang 还是 vLLM，官方文档里都没有一个与下面概念完全一一对应、并且独立于总窗口/输出上限的统一参数名：

- “模型接受用户一次输入的新增 token 上限数”

更接近它的参数往往是：

- 输入截断参数
- prefill batch 上限
- chunk 大小
- batched tokens 上限

但这些参数的真实语义都不同，不能混写成“单次输入上限”。

### 2.9. 本项目当前字段映射（官方名 vs 项目名）

这是本次最容易再次混淆的地方：本项目 YAML 字段名不完全等于官方 CLI / API 字段名。

| 本项目字段 / 代码名 | 对应的官方概念 | 当前应如何理解 |
|---|---|---|
| `model.max_context_length` | 模型理论上下文长度 | 更像静态模型能力或默认值，不应直接当作当前运行后端真实上限 |
| `sglang.max_context_length` | SGLang `--context-length` | 项目对 SGLang 总上下文上限的 YAML 命名 |
| `vllm.max_model_len` | vLLM `--max-model-len` | 项目对 vLLM 总上下文上限的 YAML 命名 |
| `inference.max_tokens` | 单次请求输出上限 | 本项目当前统一对外暴露的安全默认输出上限 |
| `inference.max_new_tokens` | SGLang 原生 `max_new_tokens` 的兼容映射 | 现在与 `inference.max_tokens` 同步，不应被当作第二套独立开关 |
| 函数形参 `max_new_tokens` | 跨后端统一接口里的“目标输出上限” | 这是历史内部命名；最终会映射到 vLLM 请求 `max_tokens` 或 SGLang 原生 `max_new_tokens` |

这里最重要的统一语义是：

- `inference.max_tokens` 才是本项目对“单次请求最大输出 token 数”的统一配置入口
- `inference.max_new_tokens` 只是为了兼容 SGLang 原生接口而保留的同步字段
- 代码里历史形参名 `max_new_tokens` 不代表它现在只服务于 SGLang

也就是说：

- 现在项目内部允许“名字暂时不完全统一”
- 但绝不允许“语义再次分叉”

### 2.10. 本次修复后，系统现在怎样避免再次踩坑

当前系统已经形成了下面这条安全链路：

1. `resolve_backend_context_length()` 先拿到当前活跃后端真实上下文上限
2. `resolve_effective_max_tokens()` 再收敛安全默认输出上限

7. container 脚本从 YAML 读取 `vllm.max_model_len`，不再写死另一个世界的值

这一整套链路的目的不是“多打一层补丁”，而是让：

- 配置
- 启动脚本
- 运行时服务
- 前端显示
- 实际请求

围绕同一个上限说同一种话。

## 3. Answer-Now 流式返回踩坑记录

### 3.1. 现象

- 点击 `answer-now` 后，旧回复会立刻停住
- 前端也会新开一个 assistant 气泡
- 但新气泡长时间只有“思考中...”或空光标，没有流式文字
- 同时 `answer-now` 按钮还能被连续点击

### 3.2. 真实根因

这次最关键的根因不在前端样式，也不在按钮状态本身，而在 **后端流式链路写法不一致**。

项目正常的流式基础设施已经在 `backend/llm_service.py` 里写明：

- 同步 generator 不能直接在 async SSE 里迭代
- 正确做法是：`后台线程 + asyncio.Queue + async generator` 转发

但新加的 `answer-now` 流式链路一开始偷懒写成了：

- `run_answer_now_stream()` 里直接 `for event in model.generate_stream(...)`

结果：

- 表面上是 SSE
- 实际上 worker 会被同步 generator 卡住或交付节奏异常
- 前端虽然拿到了新气泡，但 token 没有稳定、持续地流到浏览器里

一句话总结：

> **SSE 接口“看起来是 async”不等于真的能边生成边推送；底层如果是同步流，必须走线程转发。**

### 3.3. 正确修复

后端修复：

- 新的 `answer-now` 流式接口继续保留 SSE 语义
- 但内部改成与现有正常流式路径一致：
  - 后台线程消费同步 `generate_stream()`
  - 通过 `asyncio.Queue` 把 chunk 转发回 async SSE
- 这样前端才能真正按 token 实时收到 `content`

前端修复：

- `answer-now` 不继续旧气泡，而是：
  - finalize 旧气泡
  - 新开一个 assistant 气泡
  - 将新的 final answer token-by-token 追加到新气泡
- `answer-now` 期间单独维护 `isAnswerNowLoading`
- 按钮禁用不能只靠 React state，还要加 ref 级防抖

### 3.4. 第二个坑：只靠 state 禁用按钮不够

一开始虽然加了 `isAnswerNowLoading`，但仍有极短窗口可连续点击。

原因：

- React state 更新不是同步生效
- 用户连续点两次时，第二次点击可能发生在 state 还没刷新之前

正确做法：

- `state` 负责渲染禁用态
- `ref` 负责同步级防抖

也就是：

- UI 上 `disabled`
- 逻辑里再判断 `answerNowWasClickedRef.current`

### 3.5. 第三个坑：stop 和 answer-now 的错误语义不能混用

如果用户在 `answer-now` 重新生成过程中点击 `stop`：

- 应该静默结束
- 不应在新气泡里追加 `Request timeout or aborted`
- 不应显示“立即返回答案失败”这种误导性文案

结论：

- `answer-now` 自己失败，才显示失败文案
- 用户主动 `stop`，必须静默

### 3.6. 第四个坑：answer-now 不应继续工具链

这次语义必须严格区分：

- `stop` 后继续原 agent 任务，不对
- 基于当前 session 已有上下文，重新生成 final answer，才对

所以后端 `answer-now` 新流应明确：

- 复用当前 session memory
- 重新构造一条内部 prompt
- **禁用工具调用**
- 只流式输出纯文本 final answer

否则用户会感知成“只是继续上一轮慢推理”，而不是“快速重新回答”。

### 3.7. 这轮最重要的经验教训

1. 新接口不要只抄表层 API 形状，要抄到项目里真正可工作的底层流式模式。
2. 复杂代码库里，看到已有 `chat_stream_async()` / `Queue` / worker 这种成熟路径时，优先复用其设计，不要自造“看似更简单”的同步迭代版本。
3. 前端防重复点击，`state` 只能负责渲染，真正防抖还要靠 `ref`。
4. `answer-now` 的用户语义是“停止当前链路并重新给 final answer”，不是“继续原链路”。
5. 涉及 stop / abort / SSE / 多状态按钮的功能，必须做真实联调；只靠静态读代码和单元测试，很容易漏掉运行时交付节奏问题。

## 4. 本地搜索工具 glob / grep / ripgrep 踩坑记录

### 4.1. 现象

这次问题最初表现为两类：

- 用户让 Agent 读取本地 `NH4NO3` 文档时，`glob({"pattern": "**/NH4NO3*"})` 明明应该能在 `~/Documents` 里找到文件，却返回 0 或只返回 `/tmp` 下的一堆残留测试文件。
- 后续 `grep({"pattern": "NH4NO3", "output_mode": "files_with_matches"})` 会长时间卡住，甚至 40 分钟都不返回。

表面上看像是：

- `config/config-misc.yaml` 里的 `agent.search_whitelist_paths` 没生效
- 或 `rg` 没装好 / 不能用

但实际都不是。

### 4.2. 真实根因一：配置白名单其实是生效的，问题出在搜索执行链路

实际检查运行时配置后确认：

- `config.agent.search_whitelist_paths` 确实是 `['~/Documents', '/tmp']`
- `search_ops._resolve_search_targets(None, ...)` 解析出的目标根目录也确实同时包含：
  - `~/Documents`
  - `/tmp`

所以问题不是“配置没读到”，而是“搜索执行时某一条路径把正确结果覆盖 / 冲掉了”。

### 4.3. 真实根因二：Python fallback 的 glob 语义和 ripgrep 不一致

旧实现中一旦 `rg` 这条路径被判定为失败，就会整体回退到 Python fallback。

但 Python fallback 里使用的 `fnmatch` 对这种模式：

- `**/NH4NO3*`

并不能像 `ripgrep` 那样匹配白名单根目录下的顶层文件：

- `~/Documents/NH4NO3.md`

结果就是：

- 同样的 pattern，在 `rg` 下能命中顶层文件
- 一旦退回 Python fallback，顶层文件反而匹配不到

这正是“明明 `Documents` 里有文件，但结果里只剩 `/tmp` 一堆东西”的关键原因之一。

有效修复：

- 给 Python fallback 增加 `globstar` 语义展开
- 让 `**/foo` 同时能覆盖零层目录深度的情况
- 使 fallback 的匹配结果尽量与 `rg` 对齐，而不是两套不同语义

### 4.4. 真实根因三：symlink 路径在旧代码里会被错误 resolve，导致“白名单内文件看起来跑到别处去了”

旧代码里，Python fallback 遍历文件时会对候选路径做：

- `resolve(strict=False)`

这会把白名单目录里的 symlink 文件直接展开成源文件真实路径。

后果：

- `~/Documents/NH4NO3.md` 如果是一个链接文件
- 搜索结果里显示的可能不是 `~/Documents/NH4NO3.md`
- 而是它真实指向的其他路径

从用户视角看，就会误以为：

- `glob` 没找到 `Documents` 里的文件
- 或工具“把路径搜错了”

有效修复：

- 搜索结果保留白名单内的可见路径，不再对候选文件路径做强制 `resolve()`
- 去重时使用 `abspath` 级别的稳定规范化，而不是把 symlink 展开成真实源路径
- 同时 `rg --files` 路径增加 `-L`，允许 ripgrep 跟随 symlink

### 4.5. 真实根因四：`/tmp` 下的 Permission denied 不是 rg 没装，而是系统私有目录天然不可读

实际检查后确认：

- 机器上已经装了 `rg`
- 路径在 `~/.cargo/bin/rg`
- 版本是 `ripgrep 15.1.0`

所以“`rg` 一直没成功”不是因为没安装，也不是因为缺少 Rust。

真正的问题是：

- `/tmp` 下存在很多 root-only 目录，例如：
  - `/tmp/snap-private-tmp`
  - `/tmp/systemd-private-*`
- 普通用户扫描 `/tmp` 时，`rg` 进入这些目录自然会报：
  - `Permission denied (os error 13)`

这属于环境事实，不是 `rg` 自身损坏。

### 4.6. 真实根因五：旧代码把 ripgrep 的“部分成功”误判成“整体失败”

这是这轮里最关键的底层 bug。

旧实现下，`rg` 在 `--no-messages` 模式扫描 `/tmp` 时，常出现这种结果：

- `returncode == 2`
- `stderr == ""`
- 但 `stdout` 里其实已经有大量有效结果

也就是说：

- `rg` 并不是没工作
- 它只是扫到少数不可读目录时，用返回码 2 表示“存在错误”
- 但同时把能读到的大量结果正常输出到了 stdout

旧代码的问题在于：

- 把 `returncode == 2` 且 `stderr` 为空粗暴地当成 permission issue
- 或直接当成 ripgrep 失败
- 然后整体回退到 Python fallback，甚至直接报错

于是用户体感上就变成：

- `rg` 好像总失败
- 搜索很慢
- 搜索结果还不稳定

有效修复：

- 新增“partial success”判定：
  - 只要 `returncode == 2` 但 `stdout` 非空，就把它视为**部分成功**
- 继续消费 `rg` 已产出的结果
- 不再因为 `/tmp` 下少量权限噪声就整体退回 Python fallback

这一步修完后，`rg` 才真正重新成为默认主路径，而不是“名义上优先，实际上经常被旧错误处理打掉”。

### 4.7. 真实根因六：grep 卡死不是单点 bug，而是“大范围白名单 + 无超时 + 慢回退”叠加

旧代码里 `grep_search()` 的问题不是单独一个 if 写错，而是多个因素叠加：

- 省略 `path` 时会搜索整个白名单
- 白名单里包含 `/tmp`
- `/tmp` 噪声很多、目录很大、还夹杂权限受限目录
- 底层 `rg` 调用没有超时保护
- 一旦旧逻辑误判 `rg` 失败，又会回退到更慢的 Python 内容扫描

所以最终才会出现：

- `grep({"pattern": "NH4NO3", ...})` 卡很久
- 甚至几十分钟不返回

有效修复：

- 新增配置项：`agent.ripgrep_timeout_seconds`
- 底层 `rg` 子进程统一加 timeout
- 超时后返回明确错误，不再继续退到更慢的 Python 全盘内容扫描

这一步的经验教训是：

> 大白名单搜索工具如果没有明确的 timeout 边界，哪怕主路径是 `rg`，一旦命中坏目录 / 大目录 / 慢目录，也迟早会把 Agent 拖死。

### 4.8. 真实根因七：工具参数兼容性也会放大搜索链路问题

这轮排障里还顺手发现一个小坑：

- `grep` 的合法输出模式原本只有：
  - `files_with_matches`
  - `content`
  - `count`
- 但模型实际有可能传：
  - `output_mode="files"`

旧代码会直接报参数错误。

这虽然不是导致 `NH4NO3` 主问题的核心根因，但会放大 Agent 在搜索阶段的失败概率。

有效修复：

- 给 `files` / `file` / `matches` / `lines` 这类常见别名做兼容映射
- 让模型即使传了自然化简写，也不会直接死在参数校验层

### 4.9. 这轮最重要的经验教训

1. 搜索问题先不要怀疑“配置没生效”，先验证运行时配置和真实 target roots。
2. `rg returncode != 0` 不等于“没有任何有效结果”；`stdout` 是否非空必须纳入判定。
3. `/tmp` 这种白名单目录天然是高噪声目录，权限受限目录、测试残留、编译缓存都会混在一起；搜索工具不能把它当成普通干净目录处理。
4. Python fallback 不是“能跑就行”，它的 glob 语义、路径语义必须尽量与主路径 `rg` 对齐，否则一旦发生 fallback，结果就会突然变形。
5. 对用户可见的搜索结果，路径展示必须保留白名单内可见路径；不要因为内部 `resolve()` 把 symlink 展开成用户根本没请求的真实源路径。
6. 本地搜索工具只要允许大范围搜索，就必须配置化 timeout，不能假设 `rg` 永远又快又稳。
7. 如果默认白名单里保留 `/tmp`，那工具层就必须把“部分成功 + 权限噪声”视为正常环境现实，而不是异常路径。
