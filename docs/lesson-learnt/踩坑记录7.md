# 踩坑记录 7：Wayland Computer Use、归一化坐标与 Codex sandbox 排障

## 记录范围与当前状态

本记录整理本轮 Computer Use 实现与真机排查、Stage‑1 模型探针、坐标语义纠正，以及用户在 Linux 桌面版 Codex 中遇到的 bubblewrap / nsfs 环境问题。Codex 版本 `26.917.62051` 是用户报告值。每项都按“问题现象—根本原因—解决方案”记录；对尚未获得端到端证据的原因明确标注推测或未验证，不把推断写成事实。

截至本记录：Wayland Portal/PipeWire/EIS、Native helper/IPC 和按 Agent context 延迟创建的 runtime 已实现；图形登录用户的 live monitor frame、EIS mapping 和隔离测试 surface 的 pointer press/release + wheel 曾连续三次验证成功。几何与 Computer Use 相关 Python 测试为 `216 passed, 2 skipped`。VLM calibration、真实 Agent 的完整 Stage‑1→Stage‑2→目标交互验收仍未通过；`computer_use.enabled`、desktop capture 和 input 默认均为关闭。X11 后端仍未实现。

## 问题 1：把缺失的 live native 实现误诊为缺系统包、uinput 或权限

### 问题现象

用户最初看到 `desktop_disabled`，另一份 AI 分析又指出 Portal、PipeWire、libei 等多个实现缺口。容易据此先安装包、加 `uinput`、放开内核权限或改 Linux capability。

### 根本原因

当时至少有三个不同层次的问题：配置中的 `allow_desktop_capture`、`allow_desktop_input` 默认是 `false`；放开配置后，`executable_backend=None` 仍会返回不可用；native `portal.c`、`capture.c`、`ei_input.c` 是 stub，`wayland_probe.c` 只探测 D-Bus 属性，`control.c` 只支持 hello/status/close。`doctor.py` 也曾硬编码为未实现。接口可发现、代码可编译，都没有真实桌面通路。

### 解决方案

先逐层读实现并确认调用顺序，再补真实 Portal session、PipeWire frame、EIS sender、FD/metadata IPC、Python client 和 session-bound runtime。对包发现、Portal 授权、完整帧、输入 mapping、真实应用结果、calibration 分开报告。缺实现时先补代码，不以装包或加权限掩盖空实现；不加 `/dev/uinput`、input group、`CAP_SYS_ADMIN` 来替代 RemoteDesktop/EIS。

## 问题 2：把 Portal 接口可见或 Start 返回，当成屏幕已经可采集

### 问题现象

只读 `--probe` 返回 `PORTAL_INTERFACES_SUPPORTED`，版本和 device/source type 看起来齐全；用户授权后仍发生 `PORTAL_INVALID_STREAM`、PipeWire 错误或首帧超时。

### 根本原因

`GetAll` 属性和 D-Bus interface introspection 只证明服务暴露能力，不证明某个已授权 session 取得 monitor stream，更不证明该 stream 已进入 streaming 并产出完整、当前帧。Portal 的 Request.Response 与用户授权结果也必须检查。

### 解决方案

按同一 session 执行并记录：`RemoteDesktop.CreateSession` → `SelectDevices(POINTER)` → `ScreenCast.SelectSources(MONITOR)` → `RemoteDesktop.Start` 等待用户 Request response → `ScreenCast.OpenPipeWireRemote` → PipeWire 协商和首帧 → `ConnectToEIS`。EIS 只在 Start 成功后连接；EIS 建立后不能再混用 `NotifyPointer*`。任何一步未验证，readiness 都保持 false。

## 问题 3：在错误的 shell / 桌面 session 里排查 Portal

### 问题现象

容器、coding sandbox、普通 SSH shell 与图形登录终端得到不同的 D-Bus、Wayland、Portal 或 helper 结果。退出 `nv pytorch` 容器后，用户仍需确认 host 上的真实状态。

### 根本原因

Portal 授权属于当前图形登录用户的 D-Bus / Wayland session。容器可能没有该用户的 `DBUS_SESSION_BUS_ADDRESS`、`XDG_RUNTIME_DIR`、Wayland socket 或对应权限。coding sandbox 中的 `127.0.0.1` 也可能不是用户图形 shell 所在网络 namespace。

### 解决方案

Portal 授权探针和真实 input outcome 探针必须从 Jetson 的图形登录用户终端运行。明确区分容器/sandbox 与 host 的结果；在 host 上用 `XDG_SESSION_TYPE`、`WAYLAND_DISPLAY`、`XDG_RUNTIME_DIR`、`DBUS_SESSION_BUS_ADDRESS`、`loginctl session-status` 记录 session。不要把 sandbox 的 `SESSION_BUS_UNAVAILABLE` 归因于 host Portal，也不要把 host 成功推断成 sandbox 能访问本机服务。

## 问题 4：把不同 PipeWire 错误压成一个“Portal 失败”

### 问题现象

真机探针先后出现 `PORTAL_INVALID_STREAM`、`GEOMETRY_CHANGED`、`PIPEWIRE_DISCONNECTED`、`PIPEWIRE_STREAM_ERROR`、`PIPEWIRE_STREAM_ERROR_NO_INPUT_FORMAT`、`PIPEWIRE_FIRST_FRAME_TIMEOUT`。把 timeout 从 5 秒调到 15 秒后，输出耗时也正好变成 15 秒。

### 根本原因

这些代码对应不同阶段：无效/过期的 Portal stream、选中屏幕或几何变化、PipeWire core/stream 断开、格式协商无交集、没有首个可验证 buffer。延长 timeout 只延后返回；它不会修复格式、流状态或帧事件顺序。用户在 15 秒处看到相同错误，恰好证明当时是等满 timeout。

### 解决方案

保留明确的 `failure_phase` 和 `error_domain`，逐项检查 stream state、format、buffer、timestamp 和覆盖证明。`PIPEWIRE_STREAM_ERROR_NO_INPUT_FORMAT` 先排实际 Mutter/PipeWire 格式与 helper 构建版本；`PIPEWIRE_FIRST_FRAME_TIMEOUT` 先看流有没有 streaming 和完整 buffer。每轮只改一个变量；不要把“等得更久”写成修复。

## 问题 5：把桌面分享 UI 的 abort 图标当成 capture readiness

### 问题现象

用户勾选“允许远程交互”并选择 RTK 后，Wayland 任务栏出现类似浏览器截屏时的 abort 图标，且图标持续时间随探针变长。与此同时 JSON 仍报 PipeWire/EIS 错误。

### 根本原因

图标变化说明桌面分享授权流程至少进入可见状态，但不证明目标 stream 已协商格式、产生新帧、映射到 EIS region 或可输入。图标持续时间更长可能只是程序等更长 timeout。

### 解决方案

把授权 UI 当作一个状态观察点，而不是成功判据。只用探针的 Portal response、首个完整 frame、EIS region、映射证据和输入结果判断阶段。保留 abort/cancel 入口；测试时选择正确的 RTK monitor 和远程交互权限，不要根据图标猜 readiness。

## 问题 6：monitor 选择或几何变化导致旧 binding/crop 失效

### 问题现象

不同授权尝试会返回 `GEOMETRY_CHANGED`，或选择屏幕后 stream 内容、分辨率和预期不一致。选错“RTK”或授权时改变屏幕布局，会让同一探针在几何检查阶段失败。

### 根本原因

Portal 返回的 monitor stream 与 EIS logical region 必须是同一个受授权的屏幕。选择器、scale、分辨率、rotation 或 hotplug 变化都会让旧 binding/crop 不再可靠；几何不是由 screenshot width 猜出来的。

### 解决方案

把 Portal pixel size 与 EIS logical origin/size 作为两个独立实测值，授权后校验一致性。几何改变时增加 geometry version、撤销 binding、废弃旧 crop 并重新 observe。现场探针中选择 RTK；授权期间避免改显示设置。不能把上次 session 的 monitor 选择或 crop 重用于新授权。

## 问题 7：把 EIS mapping 的歧义误当作 Firefox 或 Chromium 输入权限问题

### 问题现象

用户曾观察到移动普通窗口和 Firefox 时返回不同的 `EIS_MAPPING_AMBIGUOUS`；随后两者又都返回 `EIS_MAPPING_MULTIPLE_DEVICES`，诊断进一步显示 `EIS_MAPPING_MULTIPLE_DEVICES_SAME_REGION`。结果随 session、窗口和设备公告变化。

### 根本原因

EIS 会公告多个 device/region。仅凭设备数量、截图像素尺寸或 Portal position 不能选定输入 region；多个 device 也可能共享相同 `mapping_id` 和完整 region。最初观测到的浏览器差异不足以证明 Firefox 或 Chromium 是根因，更不能据此加权限。

### 解决方案

按 `mapping_id`、region、完整 monitor coverage 和 absolute/button/scroll capability 收集只读诊断。只有同一区域证据完全一致时才允许选择候选设备；region 不同、覆盖不全或能力缺失时拒绝输入。binding 发布后设备失效立即撤销，不在运行中静默切换。窗口移动只作为对照实验，不作为 mapping 依据。

## 问题 8：Snap/Docker 的 nsfs 挂载是环境线索，不是桌面协议根因

### 问题现象

`findmnt --types nsfs` 曾显示 `/run/snapd/ns/cups.mnt`、`/run/docker/netns/default`，以及 `/run/snapd/ns/chromium.mnt`。`docker ps` 在退出容器后为空；停止 Docker service/socket 后 `default` 挂载仍存在。`fuser` 还显示 `NetworkManager` 使用与 `/proc/self/ns/net` 相同的 `net:[4026531840]`。

### 根本原因

已观察到的是服务退出后仍有 namespace mount；Docker 默认网络 namespace 与 host 当前 network namespace 相同，且 NetworkManager 仍在用。Chromium Snap 也有自己的 namespace 挂载。它们可以影响 sandbox 的 mount namespace / 文件访问排障，但这些信息不能证明 PipeWire/EIS 映射错误是由 Chromium、Docker 或网络造成。

### 解决方案

先停止相关服务，再用 `findmnt`、`readlink /proc/self/ns/net`、`fuser`、`docker ps` 确认对象与使用者。对已确认无人依赖且确实是 host 当前 namespace 的 Docker mount，只卸载精确路径 `/run/docker/netns/default`；若 busy 就停止，不用 `umount -l/-f`。Snap namespace 使用 snapd 提供的 `snap-discard-ns <snap>`，先正常关闭应用。不要删 Docker 数据目录，不要把环境清理与 Portal/EIS 代码修复混成同一因果链。

## 问题 9：bubblewrap `bwrap` 可运行，不代表 Codex sandbox 的文件系统无故障

### 问题现象

工作过程中遇到 sandbox 写入受阻，用户担心需要恢复环境或额外授予权限。用户在 host 上确认 `/usr/bin/bwrap`、bubblewrap `0.9.0` 存在，`bwrap --ro-bind / / -- /usr/bin/true` 返回 0；与此同时仍能看到 snap/docker 的 nsfs 挂载。

### 根本原因

简单 bwrap smoke test 只证明这个最小命令可执行，不覆盖 Codex 实际 sandbox 的所有 bind mount、mount namespace 与 workspace 写路径。反过来，当前证据也不足以确认这是 Codex `26.917.62051` 的产品缺陷：后来排查发现实际存在 stale nsfs mount 并被清理，但没有取得可复现的 Codex 内部失败 trace 来锁定因果。

### 解决方案

记录版本和可复现 host 命令，优先检查 mount 清单与精确 workspace 错误；只在有证据时修复 host namespace。现有证据支持“Codex sandbox 与 host 上残留的 mount namespace 状态发生了交互”这一可能性，不能写成已证实的 Codex sandbox bug。任何升级、改安全策略或额外 capability 都要先有明确失败证据。

## 问题 10：临时停服务后忘记恢复 host 环境

### 问题现象

排障期间用户执行过 `sudo snap stop cups`、`sudo systemctl stop docker.service docker.socket`，最后明确报告 Docker 尚未重新启动。停止是为清理 namespace mount，不是 Computer Use 的常规修复。

### 根本原因

环境清理操作改变了主机服务状态；如果只记录停止步骤而不记录恢复步骤，会让后续打印或容器工作出现看似新的故障。

### 解决方案

排障结束后按实际需要恢复：Docker 使用 `sudo systemctl start docker.socket docker.service`，CUPS 使用 `sudo snap start cups`；随后分别用 `systemctl is-active` / `snap services cups` 确认。恢复只影响被临时停掉的服务，不要为恢复服务而重新安装或删除数据。执行状态要在实际 host 上核对，不根据 sandbox 猜测。

## 问题 11：Tk `winfo_containing` 在 Wayland/XWayland 下造成假阴性

### 问题现象

输入探针间歇返回 `TEST_SURFACE_NOT_ON_SELECTED_MONITOR`，尽管 Portal 已授权并且用户看到绿色测试 surface；用户重复运行时有时成功、有时失败。

### 根本原因

旧预检查用 Tk/XWayland 的 `winfo_containing` 判断 pointer 下是否为测试窗，这不是 Wayland 合成桌面上的可靠可见性证据。它可能在真实窗口可见时给出假阴性。

### 解决方案

删除该窗口命中预检查，改为检查授权后新采集的 frame 是否在目标位置包含绿色测试 surface。只有图像证据成立才向测试窗发送输入；若不能证明 surface 在被选 monitor 上，仍 fail closed。用户后续连续三次验证成功，说明这类环境假阴性被排除，但不代表生产模型已校准。

## 问题 12：把 `input_events_sent` 当成真实应用成功或系统 ready

### 问题现象

隔离 input probe 返回 `input_events_sent: 4`、`down:1`、`up:1`、`wheel:1` 和 `input_outcome: verified_in_test_window`，但整体仍是 `ready:false`、`calibration:not_run`。有时前置 surface 检查又阻止事件发送。

### 根本原因

这些事件只证明 libei transport 到隔离测试窗并触发回调；它们不证明 VLM 找到了用户实际目标，也不证明目标应用完成了期望动作。libei 没有应用层点击 ACK，`ACTION_SENT` 更不能替代视觉结果验证。

### 解决方案

分开报告 Portal authorization、live frame、EIS mapping、test-window event、VLM calibration 和真实 Agent interaction。保持 `input_events_sent=0` 时 `not_run` 的语义，不补造状态。最终 acceptance 要观察目标应用产生预期变化，再测 Stop/revoke/hotplug 等故障矩阵。

## 问题 13：把全绿 CTest、`ninja: no work to do` 或 doctor 状态当成真机验收

### 问题现象

用户在 host 图形终端多次获得 CTest 8/8、随后 9/9 全通过，构建也显示 `ninja: no work to do`。live helper 仍连续暴露新的 PipeWire/EIS 错误；`doctor.py` 最初曾硬编码 `ready:false`。

### 根本原因

单元测试覆盖状态机、IPC、buffer 和 gating 的合成边界，不会自动授权 Portal、采集当前桌面、证明真实应用收到点击。编译通过只说明代码可生成；doctor 的固定 false 则缺乏分层证据，既不能报告真实进展，也不能无条件宣布成功。

### 解决方案

在真机输出里分别记录 discovery、authorization、frame、mapping、input outcome、calibration 和 end-to-end application effect。doctor 对未运行步骤显示 `not_run`，对已测步骤报告具体失败码；绝不把 fixture、stub 或 `ACTION_SENT` 升格为 live acceptance。

## 问题 14：把 capability 配置关闭误认为工作无法继续

### 问题现象

生产配置保持 `computer_use.enabled=false`、`allow_desktop_capture=false`、`allow_desktop_input=false`，用户担心是否应先打开全局配置才能调试。

### 根本原因

安全授权与实现 readiness 是两件事。全局打开会让未校准路径变成可调用路径；反过来，关闭默认配置不妨碍只读 helper 探针或使用独立测试进程验证当前 session。

### 解决方案

只在隔离探针进程中从 deep-copied config 创建短期 capability。生产默认保持关闭，直到 current fingerprint、重复校准、真实 Agent 目标选择和故障矩阵都通过。报告中说明 false 是设计的 fail-closed 状态，不用静态配置试探代替 live evidence。

## 问题 15：Stage‑1 的 `1000×1000` 坐标域被误当成正方形图片

### 问题现象

本地模型在 `1000×563` overview 上返回 `(100,400)`，脚本得到 observed ratio `(0.1,0.4)`。用户指出 monitor 是长方形，`1000×1000` 是 coordinate domain，不是把 `3840×2400` 截图变成方图。

### 根本原因

Stage‑1 两轴是分别归一化的 full-monitor ratio：`x/1000` 表示横向比例，`y/1000` 表示纵向比例；二者不要求等长物理距离。旧说明中把“1000 normalized reference length”传递成像素尺寸，或在文字里把 Stage‑1/Stage‑2 local domain 混为一谈，会让模型与实现误解画面比例。

### 解决方案

保留真实图像长宽比。若 1000×563 overview 上目标像素点是 `(px,py)`，Stage‑1 wire 坐标为 `(px*1000/1000, py*1000/563)`；因此目标 `(200,394)` 的预期大约是 `(200,700)`。反向绘制模型点时也按 `pixel_x=x*image_width/1000`、`pixel_y=y*image_height/1000`，不能把 y 直接当 overview raster 行号。

## 问题 16：Stage‑2 center crop 与 edge crop 的 normalized aspect 被写“歪”

### 问题现象

用户发现某版本把 Stage‑2 crop 固定为正方形，担心 v1.1→v1.2→v1.3 的坐标转换语义已经失真。全屏长方形 monitor 中，中心与边缘 crop 的 physical aspect、normalized local aspect 不总相同。

### 根本原因

Stage‑2 比例必须在 x/y 各自 monitor baseline 下比较。中心 zoom‑2 在 3840×2400 上对应 physical crop 1920×1200、normalized extent 500×500，raster 为 1000×1000；上边缘可能被 clip 为 normalized extent 500×260，physical crop 可是 1920×624，raster 应为 1000×520。若直接拿 raw crop pixel aspect 算 local domain，会把 3840:2400 屏幕误当成不同的 coordinate geometry；若短边强制为 1000，则又把 edge crop 拉伸变形。

### 解决方案

先按 monitor 宽/高分别归一化实际 integer crop，长轴 local domain 定为 1000，短轴按 clipped normalized aspect 得出；detail raster 同比例 resize，不 padding、不补 void、不强制正方形。inverse mapping 仍用 authoritative integer crop rect 的实际 width/height。已更新 `coordinates.py`、contracts、renderer、adapter 与文档，旧的强制方形解释明确标为 superseded。

---

## 问题 17：crop 的像素矩形、normalized extent 与 inverse transform 被混为一层

### 问题现象

讨论 500×500、500×260、1000×1000 时，读者容易把这些相对长度误解为 bitmap 的实际像素尺寸；边缘截图还可能被 padding 或双重 round，造成 detail 点位回不去。

### 根本原因

三个尺寸各有用途：物理 source crop 是 integer raster rect；local coordinate extent 是 x/y 分别按 source width/height 归一化的相对几何；detail image 是按配置长边 resize 的 raster。`floor(left/top)`、`ceil(right/bottom)` 会使 nominal crop 与最终整数 rect 有细微差异。

### 解决方案

始终保存并使用实际 `[x0,x1)×[y0,y1)` 作为 crop 几何权威。clip 到 monitor 边界并完全丢弃 void；不 padding。Stage‑2 local domain 根据该实际 rect 计算，raster resize 后画 grid。inverse transform 分别用 crop width/height，不从粗点和 zoom 再推导“理想 crop”。

---

## 问题 18：把 Stage‑1 模型偏差当成后端坐标缩放 bug

### 问题现象

直接 SGLang probe 的四个 known-target overview，基准提示与显式 fraction 提示输出不同程度的误差。最终 adapter 提示下结果为：case‑0 `(100,700)` 对预期 `(200,700)`；case‑1 `(875,200)` 对 `(800,200)`；case‑2 `(30,30)` 对 `(50,50)`；case‑3 `(500,10)` 对 `(500,19)`。

### 根本原因

同一 wire protocol 下有些输出接近归一化值，有些局部接近 raster 像素值，误差方向不一致，不能用一个全局 x/y scale 解释。基准 prompt 下 case‑0 的 `(100,400)` 让 zoom‑2 crop 在 1280×720 源帧中止于 y=468，漏掉 y=504 的已知 target（对应 1000×563 展示图中的约 y=394）；显式比例说明把 y 调到 700 后，四个建议 crop 都覆盖 target。四例 A/B 的最大轴误差从 0.30 降到 0.10，但 case‑0 x 仍差 0.10，case‑3 y 仍偏离 normalized 值，故不是“校准通过”。

### 解决方案

把 Stage‑1 prompt 改成容易理解的比例语言：x/y 各自取全图比例乘 1000，长宽比不改变两个轴的 0..1000 domain；保留 `image_pixel` 协议自己的原始像素 prompt。不要运行时猜测 convention 或按单个模型错误去变形 crop。离线 probe 必须输出目标比例、预测比例、每轴误差和 crop 是否覆盖目标；未通过重复 calibration 时 readiness 保持 false。

## 问题 19：直接调用 SGLang 不等于完成生产 Agent calibration

### 问题现象

探针直接向 `http://127.0.0.1:30000/v1/chat/completions` 发送 overview/detail 图片并强制 `inspect_region`/`interact_detail` tool call，能够测得模型输出；用户 host 上 `/v1/models` 能返回 Qwen3.6‑35B 模型。coding sandbox 内 curl 同一 localhost 却返回 connection refused。

### 根本原因

当前 direct probe 与普通 Vision Agent 的消息构造、Image preprocessing、历史上下文与 provider adapter 可能不同；operations 文档要求校准用同一 top-level Agent context、production renderer/grid/decoder/serving preprocessing，并且每例至少重复两次。sandbox 与 host localhost namespace 又是不同执行环境。direct API 是有用的提示词诊断，不是部署校准报告。

### 解决方案

用 direct probe 区分 prompt/coordinate hypothesis，但正式 calibration 在同一 top-level Vision Agent 里通过普通图片上传按生产路径测量；每个样例重复至少两次，记录解码后 global ratios，不给模型看 `samples.json` ground truth。fingerprint 要对应最终 prompt、renderer、preprocessing 与模型配置；remote/container 服务 revision 另行核验。

## 问题 20：模型坐标要投影回各自 Stage 图像，不能直接把数字画到 bitmap 上

### 问题现象

用户要求将 Stage‑1 图片与 local LLM rough point 合成，进入 Stage‑2 时也将 detail crop 与 final local point 合成供检查。若把 normalized `(x,y)` 直接当 raster pixel `(x,y)` 画出，非正方形 overview 会把纵坐标画错。

### 根本原因

Stage‑1 点属于独立 normalized axes；Stage‑2 点属于 crop-local wire domain。它们只有经过对应图像宽高和 protocol maximum 的投影，才能变成 display raster pixel。最新批量输出只包含 Stage‑1，没有真实 Stage‑2 final tool call；拿预生成 detail fixture 的预设点冒充本次 LLM 点会伪造 evidence。

### 解决方案

Stage‑1 overlay 用 `image_x=x*visible_width/1000`、`image_y=y*visible_height/1000`。本轮生成了四张原尺寸标注图和 contact sheet：红色是模型点，黄色是建议 crop 边界，青色是 known target center，位置在 `/tmp/computer-use-calibration/annotated/stage1/`。Stage‑2 若有真实输出，应按 stage2 `wire_max` 映射到 detail raster 后另存；当前没有 Stage‑2 output，不画虚构点。Stage‑2 probe 脚本若用于预生成 calibration crop，必须注明它只测 detail coordinate，不等于 live end-to-end crop。

## 问题 21：用一次四例结果生成“已通过”的 calibration report

### 问题现象

目前有四个不同位置的一次性模型输出，容易想直接填进 `samples.json` 并用宽松阈值通过；另有几次隔离 input test 成功，容易误当成完整 ready。

### 根本原因

部署 verifier 会重新计算误差/通过率，要求重复、多样 target、当前 fingerprint 与真实 monitor geometry；使用者选阈值也必须显式。`samples.json` 初始 `outputs` 是空列表，且离线 fixture 的 `desktop_geometry` 为 null。一次输出、人工常数或直接复制 ground truth 都不是 measurement。

### 解决方案

只填写模型实测输出经 decoder 转换后的 ratio；保留 failed report 的失败状态。至少满足 calibration 文档的重复样本、不同 target、当前 fingerprint 和 verified `desktop_geometry`，然后由 scorer 重算。测量未完成时不修改 config 的三个 false 开关，也不写 `passed:true`。

## 问题 22：把 X11/uinput/Sunshine/NVENC 线索牵连到 Wayland EIS

### 问题现象

用户和其他 AI 提出的旧方案里出现 X11、uinput、Sunshine/NVENC 等不同图形路径，容易把它们当成 Wayland Portal 输入失败的直接根因。

### 根本原因

X11/XTest、uinput、Sunshine capture/encoder 与 GNOME Wayland 的 RemoteDesktop portal、PipeWire monitor stream、libei/EIS 是不同 transport。共享同一台机器不构成因果。X11 backend 仍未实现，也不代表 Wayland EIS 不可用。

### 解决方案

按当前 session backend 和失败阶段排查。Wayland 使用 Portal authorization + PipeWire capture + EIS input；X11 需要独立的 XTest/XRandR 实现和测试，未实现就明确返回 `X11_BACKEND_UNIMPLEMENTED`。无证据时不加 uinput/capability，也不让 X11 workaround 改写 Wayland 坐标/权限模型。

## 问题 24：把已完成的输入误报为 uncertain，并阻断下一条 intent

### 问题现象与根因

同一 top-level Agent 第二条用户请求的 observe 返回 ACTION_DELIVERY_UNKNOWN；reobserve 成功后 inspect 又被 OBSERVE_REQUIRED 拒绝。JSONL 实际证明上一条输入为 ACTION_SENT、cleanup complete，并非 uncertain。bridge 把成功与失败都放进 terminal，成功没有错误码时却 fallback 到 ACTION_DELIVERY_UNKNOWN；terminal 只允许 reobserve，而 reobserve 后 bridge 为 recovered、backend 仍 terminal，两层同时禁止 inspect。

### 解决与教训

区分已完成与实际不确定。显式新 observe 可从 consumed terminal 开始；成功 ACTION_SENT 后的 reobserve 沿用 target/action，只有 fresh image 接受后才创建新 UUID intent、重置预算并允许 inspect。实际 uncertain 的 reobserve 只读，进一步输入必须显式新 observe，绝不重放旧 crop/action。失败捕获保持 terminal。诊断状态必须来自 receipt，不能用兜底错误虚构风险或应用结果。

## 问题 25：profile 初始化创建了未绑定 session 的模型，首轮图片省略没有提交

### 问题现象与根因

首轮 backend 有截图与动作日志，却没有 client delivery 记录；第二轮首次请求携带两张旧 trusted PNG、omitted 为零。profile 在 runtime context 非空时创建了新的 LocalLLMModel(session=None)，而创建 session 时只替换 runner 共用模型，遗漏该实例。下一轮 profile 又换了 memory wrapper；pending projection 仍绑定旧 memory，虽然 canonical ActionSteps 与图片对象没变，也无法绑定新请求。

### 解决与教训

session 建立后绑定专属 sessionless LocalLLMModel，保留 runtime context 和自定义非 Local 模型。普通推理序列化前，仅当 session/context、完整 eligible ActionStep/image 签名与待替换容器完全相同，才跨 memory wrapper 重建 pending candidate；不修改 canonical history。接受屏障之后才提交；Stop、Answer Now、compact、失败或 empty fallback 不消费 permission，旧 worker 不得提交新的候选。完整 wiring 比孤立 helper 正确更重要。

## 问题 26：把模型定位、坐标几何与图片送达混成一个问题

### 问题现象与根因

模型重复给出 detail 中点时，容易据此调整 backend 靶心规则或猜测旧图片。裁剪在边缘 clipping 后，detail 中点也不一定等于 Stage-1 rough point；方形 raster 的边长不能替代原始 source/crop 宽高。新提示词还曾直接加入画布尺寸，与只使用 normalized axes 的要求冲突。

### 解决与教训

backend 不识别应用靶心、不评判命中；只映射模型点并执行授权输入。以原始 clipped rect 分别反算 X/Y，resize 后才绘制网格；奇数 guide 无标签也仍是完整归一化间隔。用受限 JSONL 的 observation/frame/request、PNG digest/尺寸、provider prepared image count 与接受状态查送达，不能从模型点猜图片是否存在，也不能声称这些元数据证明服务内部预处理。模型可见提示与 SKILL 仅讲 normalized axes，不泄露实际像素尺寸；exact PNG 只由显式 debug 开关私有保存。
