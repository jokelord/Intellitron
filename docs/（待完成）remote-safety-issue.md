# Remote API Safety Issue

## 状态

- 类型：专题优化预留
- 当前动作：仅记录问题，不修改认证、监听地址或 CORS 代码
- 记录日期：2026-09-13
- 优先级：高；实际优先级取决于后端端口是否可被不可信主机访问

## 问题摘要

当前后端存在“配置项看起来支持 API key，但运行时没有真正校验”的问题。结合当前监听地址和 CORS 配置，如果 8090 端口可被其他主机访问，调用方可能在没有认证的情况下访问 Agent API，并进一步触发 Agent 的文件和命令工具。

这不是本次安全工具边界优化的实现范围。本文件仅作为日后的专题入口。

## 当前证据

1. 当前配置监听所有网卡：

   - config/config-server.yaml 中 server.host 为 0.0.0.0。
   - 后端启动脚本会将该配置传给 uvicorn。

2. 当前配置没有启用 API key：

   - server.api_key 为 null。
   - 代码会读取该字段，但当前代码搜索未发现 Authorization、X-API-Key、HTTPBearer 或等效认证中间件对请求进行校验。

3. 当前 CORS 为通配配置：

   - cors_origins 为 *。
   - backend/main.py 将通配值转换为允许任意来源的 CORS 配置。

4. Agent 功能当前启用：

   - agent.enabled 为 true。
   - basic_agent profile 拥有完整工具集合，其中包含文件写入、文件编辑和 shell 命令执行能力。

## 风险判断

若服务只绑定在可信、隔离的本机或管理网络，暴露面可能是可接受的部署选择；但这不能替代认证控制。当前 api_key 配置项会给运维人员造成“启用认证即可生效”的错误预期，因此至少存在配置语义与运行时行为不一致的问题。

若端口对不可信网络可达，风险链为：

    未认证 HTTP 调用
        -> Agent API
        -> basic_agent 工具集合
        -> 后端进程权限范围内的文件写入或 shell 执行

## 后续专题目标

后续专题应单独确定并实现以下事项：

- 明确 API key、Bearer token 或其他认证方式的协议和失败响应。
- 明确认证是否覆盖普通聊天、Agent、健康检查、SSE 和 session 管理接口。
- 明确监听地址的安全默认值，以及显式暴露到局域网或公网时的启动提示。
- 收紧 CORS 配置，区分浏览器前端来源和 API 客户端认证。
- 增加未认证、错误认证、SSE、预检请求和配置组合测试。
- 在文档中说明 api_key 配置项的真实生效条件，不允许出现“配置了但未校验”的状态。

## 本次明确不做

- 不修改 backend API 认证代码。
- 不修改监听地址、CORS 或启动脚本。
- 不在 Agent 工具安全优化 SPEC 中重新设计远程访问控制。
