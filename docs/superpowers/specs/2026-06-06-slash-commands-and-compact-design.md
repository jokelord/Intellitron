## 3. Non-Goals

- No per-turn LLM summarization. Compact is **event-triggered only** (manual user action or threshold breach). This is fully compatible with AGENTS.md trap #14, which forbids per-turn LLM summarization.
- No circuit breaker / retry logic for compact failures. Local single-model deployment means compact LLM call failure implies the inference backend (SGLang/vLLM) is down; the main request will fail identically. The reference implementation borrowed a cloud multi-model circuit breaker pattern that does not apply here.
- No persistence of `compaction_archive` across process restarts. Archive follows session lifecycle; if the session expires, the archive goes with it.
- No Qwen2VLImageProcessor precise image token counting. The v1 release of `/compact` (this spec) uses a 512 tokens/image heuristic; future enhancement may upgrade to precise Qwen2VLImageProcessor-based counting.
- No complex command argument syntax. The v1 release of `/compact` (this spec) supports `/compact` plus an optional trailing text that is passed as `custom_instructions`.
- No cross-session summary sharing.
- No persistent server-side chat session. Chat mode stays stateless (OpenAI compatible); compact is communicated via per-message metadata markers (see Section 6).
- No other slash commands beyond `/compact` in this iteration. Framework supports future additions.

## 4. Background and Inspiration

### 4.1 Reference implementation: `ref_src/services/compact/`

Located at `/home/zk/Project/LLM-deployment/ref_src/services/compact/`. Key files and ideas borrowed:

- `autoCompact.ts`: three-layer threshold buffer pattern (13k trigger / 20k warning / 3k hard ceiling), NO_TOOLS preamble/trailer, `<analysis>` draft + `<summary>` final block two-step method, 9-section fixed summary skeleton, automatic clean-up of old `TaskStep` history
- `prompt.ts`: the canonical 9-section skeleton (Primary Request / Key Technical Concepts / Files and Code Sections / Errors and Fixes / Problem Solving / All User Messages / Pending Tasks / Current Work / Optional Next Step), `<analysis>` and `<summary>` tag stripping post-processing, envelope template that wraps the cleaned summary into a single user message before re-injection

Key difference from the reference: the reference uses a cloud LLM provider where compact may use a separate cheap model. Our local deployment uses one model for both; we therefore drop the circuit breaker / retry / max-consecutive-failures concept.

### 4.2 v2 (prefix cache stability) compatibility

Per `2026-06-02-prefix-cache-stability-v2-design.md`:
- Stable prefix: `system_prompt` + `runtime_context` + tool schema (session-pinned, byte-stable)
- Dynamic tail: `TaskStep.task`, `ActionStep.model_output`, `ActionStep.tool_calls`, `ActionStep.observations` (append-only)
- Tier 2 audit fields (`route_receipt`, `handoff_ledger`) must NEVER enter the LLM prompt body
- Old sidecar fields (`working_memory`, `unresolved_items`, `tool_ledger`, `agent_contract`, `recent_visible_history`, `user_goal`) are deleted in v2 (prefix cache stability)

`/compact` is the v2 (prefix cache stability) spec's reserved extension path. v2 (prefix cache stability) §5.3 says: "If historical compression is ever needed, it must (1) freeze old history into an immutable snapshot, (2) append the new summary as an independent field, (3) have the LLM input consume only the latest version pointer". Our implementation:
1. Old `memory.steps` are snapshotted to `session.compaction_archive` (audit only, not in LLM input)
2. The summary is added as a new `TaskStep` at the head of `memory.steps` (dynamic tail append, not prefix-middle injection)
3. LLM input only consumes the new `memory.steps`; archive is never read by LLM code paths

2026-06-13 correction: compact does **not** write summary text into `runtime_context`, does not regenerate `runtime_context`, and does not change `_replace_agent_memory()` envelope semantics. However, agent-mode compact currently **does** replace `body_messages[0]` for the compact LLM call with a compact-specific summarizer system prompt. Therefore the old sentence "stable prefix is never touched by compact" is false for the compact LLM request shape. The stable prefix invariant still applies to normal post-compact agent/chat calls after memory replacement.

### 4.3 Unified timeline event protocol

Per AGENTS.md trap #15, all new behavior must first emit canonical timeline events, then project to UI. `compact_started`, `compact_delta`, `compact_completed`, `compact_failed` flow through the existing `timeline_event` SSE channel and are projected via `projectTimelineEvent` to the new `CompactSummaryPanel` component. No new top-level SSE event type is introduced.

## 5. Architecture Overview

### 5.1 Two coupled but cleanly separated modules

| Module | Scope | Why separated |
|---|---|---|
| **A. Slash command framework** | Frontend popup UI + command registry + keyboard nav | Future commands (e.g. `/clear`, `/export`) should be one-line registry additions |
| **B. `/compact` command** | Frontend panel UI + backend LLM call + agent/chat/cycle integration | The first concrete command; primary work of this spec |

### 5.2 Data flow — manual `/compact`

```
user types "/" → popup opens → user selects /compact → Enter
  → frontend calls POST /v1/compact/run (single endpoint, three modes)
    → CompactOrchestrator.run_compact(req)
      → yield SSE compact_started
      → collect messages (chat: from request body; agent/cycle: from session)
      → build compact prompt from yaml templates
      → llm_service.chat_stream_async(messages, no tools) stream
        → yield SSE compact_delta * N (raw chunks)
      → format_compact_summary (strip <analysis>, unwrap <summary>)
      → _apply_compaction: replace session.memory.steps (agent/cycle) or no-op (chat)
      → yield SSE compact_completed with cleaned text + metadata
  → frontend projectTimelineEvent → update messages + render CompactSummaryPanel
  → frontend setMessages: mark prior history isPreCompact=true, insert summary panel
```

### 5.3 Data flow — auto `/compact` (threshold triggered)

Same end state as manual, but the trigger is the threshold check at the request entry point:

- **Chat mode** (`/v1/chat/completions`): backend runs `filter_messages_for_llm()` first. For auto-compact, the final current user turn is excluded from the compact body when the last filtered message is a user message; compact summarizes prior history only, then the actual chat call receives `[summary_envelope, current_user]`. The same HTTP response streams `compact_*` events first, then the actual chat content chunks. Frontend sees one continuous stream.
- **Agent mode** (`/v1/agent/chat`): `AgentRunner.run_stream()` does the same check using `session.agent.write_memory_to_messages()`. If over, embeds `compact_*` SSE lines, then continues with the normal agent run.
- **Cycle mode** (`/v1/cycle/start`): `_execute_steps()` for-loop end (after `step_end` yield, before next `step_begin` for a `message` step) checks the threshold. If over, embeds `compact_*` as `timeline_event` lines into the cycle SSE stream, then continues the cycle.

In all three modes, auto-compact is **transparent to the frontend**: the slash command framework is unaware of the trigger; it just observes a `compact_started` event and renders the panel.

### 5.4 Cycle mode is the primary beneficiary

Cycle mode with `share_context=true` (default, see `CycleEditor.tsx:34`) accumulates a single `agent.memory.steps` across all message steps. The default `max_duration: 36_000` (10 hours) in `config-misc.yaml:267` is far longer than what the context can actually hold; with vision photos and tool-calling observations, the prompt can exceed 50% of the configured `max_context_length` after 20-30 message steps. Auto-compact between cycle steps is the practical mitigation.

## 6. Mode Integration

### 6.1 Chat mode — backend filter contract

`/v1/chat/completions` is stateless and OpenAI-compatible. To avoid duplicating compact logic on the frontend, we extend `ChatMessage` schema with an optional `metadata: Optional[Dict[str, Any]]` field. The frontend serializes each message with one of two markers:

- `metadata: {pre_compact: true}` — message was summarized out; backend must drop it
- `metadata: {compact_summary: true, summary_id: "compact-xxx"}` — this message is the summary; backend must replace it with a user-message envelope (preface + content + suffix from yaml)

Backend runs `filter_messages_for_llm(messages, config)` at request entry. This function:
1. Finds the last `metadata.compact_summary` message
2. Replaces it with a single user message containing `summary_envelope_preface + cleaned_summary + summary_envelope_suffix`
3. Drops all `metadata.pre_compact` messages
4. Falls back to current behavior if no markers are present (OpenAI compat preserved)

The `Message` type in `llm_service.py` is unchanged — `metadata` is stripped during ChatMessage → Message conversion because SGLang/vLLM HTTP does not need it. External OpenAI clients that don't send `metadata` continue to work unchanged.

### 6.2 Agent mode — session-scoped compact

`AgentSession.compaction_archive` accumulates a list of `{summary_id, timestamp, archived_steps, summary_text}` entries. Each `_replace_agent_memory()` call appends a new entry (immutable) and resets `session.agent.memory.steps` to a single `TaskStep` containing the summary envelope.

After compact:
- `session.agent.memory.steps = [TaskStep(task=envelope, task_images=None)]`
- `session.has_run = True` — see §18.1 (post-hoc 2026-06-06) for why the original spec said False and why that was wrong
- `session.current_agent_name = config.agent.entry_agent_name` (resets to `coordinator_1`)
- `session.active_agent = None` (forces `_build_profile_agent` reconstruction)
- `session.behavior_records` retains `route_receipt` and `handoff_ledger` as Tier 2 audit (not in LLM input)
- `session.runtime_context` is **not** regenerated (session-pinned invariant from v2 (prefix cache stability) §5.2)

### 6.3 Cycle mode — between-step check

Insertion point is `backend/cycle/executor.py` inside `_execute_steps()` for-loop, immediately after `step_end` is yielded and before the next iteration's `step_begin`. The check is gated on:
- `config.compact.enabled` and `config.compact.auto_trigger` are both true
- `share_context == True` (only meaningful when context is shared; `share_context=False` uses a fresh session per step)
- The completed step is `type=="message"` (wait and cycle steps don't add context)
- `self._agent_runner` is available and the agent session exists

The orchestrator's `compact_*` events are wrapped into the cycle's `timeline_event` SSE shape and yielded inline. The cycle continues to the next step after compact completes or fails.

### 7.3 Trigger rule (strict option A)

The popup is visible **only** when the first character of `input` is `/`. Any other position of `/` does not trigger. Detection function:

```ts
export function detectSlashCommand(input: string, cursorPos: number) {
  if (!input.startsWith('/')) return { active: false, query: '' };
  if (cursorPos > input.length) return { active: false, query: '' };
  const firstSpace = input.indexOf(' ');
  const queryEnd = firstSpace === -1 ? input.length : firstSpace;
  const query = input.slice(1, Math.min(cursorPos, queryEnd));
  return { active: true, query };
}
```

### 7.4 Keyboard navigation (textarea onKeyDown)

When popup is visible:
- `ArrowDown` / `ArrowUp`: move selectedIndex (with wrap-around), `preventDefault`
- `Enter` (without Shift): invoke selected command, `preventDefault`
- `Escape`: close popup, `preventDefault`
- `Tab`: complete selected command name into input (e.g. `/c` → `/compact `), close popup

When popup is hidden: existing `Enter → handleSend` path is unchanged.

### 7.5 handleSend interception

At the top of `handleSend`, before the chat/agent flow:


### 8.2 Token counting

`TokenCounter` is a process-wide singleton. First call loads `transformers.AutoTokenizer.from_pretrained(config.model.model_path, trust_remote_code=True)` and caches. If `config.model.model_path` changes, it rebuilds. `count_messages()` uses `tokenizer.apply_chat_template(messages, tokenize=True, add_generation_prompt=False)` to get real tokens including chat template special tokens (`<|im_start|>`, etc.). Image tokens are added separately via a heuristic (512 tokens/image for the v1 release of `/compact`).

### 8.3 Threshold computation

```python
def compute_threshold(config: AppConfig, backend: str) -> int:
    max_ctx = resolve_backend_context_length(config, backend) or config.model.max_context_length or 32000
    if config.compact.strategy == "performance":
        return int(max_ctx * config.compact.performance_ratio)
    elif config.compact.strategy == "utilization":
        return max_ctx - config.compact.utilization_summary_reserve - config.compact.utilization_buffer
    raise ValueError(f"Unknown strategy: {config.compact.strategy}")

def should_compact(token_count: int, threshold: int) -> bool:
    return token_count >= threshold
```

The `x` value (`performance_ratio`) is a single config field shared between SGLang and vLLM backends. The two strategies are mutually exclusive; selecting one disables the other. Default strategy is `performance`.

### 8.4 Compact prompt templates (yaml-driven)

The compact prompt lives in `config/config-agent-prompts.yaml` under a new top-level `compaction:` section. Following the reference implementation's structure but configured as yaml:

- `no_tools_preamble`: forces plain text output, no tool calls (structure: see `ref_src/services/compact/prompt.ts:19-26`)
- `main_prompt`: contains the 9-section summary skeleton. Sections are: Primary Request and Intent / Key Technical Concepts / Files and Code Sections / Errors and Fixes / Problem Solving / All User Messages / Pending Tasks / Current Work / Optional Next Step. Preceded by an `<analysis>` block instruction asking the model to think step by step before writing the final `<summary>` block.
- `no_tools_trailer`: final reminder for plain text output
- `custom_instructions_header`: separator for user-provided instructions (`/compact <args>`)
- `summary_envelope_preface` and `summary_envelope_suffix`: wraps the cleaned summary into a single user message before re-injection

The structure is identical to `ref_src/services/compact/prompt.ts`. The full Chinese text is filled in by the implementation phase; this spec only defines fields, types, and the borrowed structural patterns.

### 8.5 Post-processing

```python
ANALYSIS_BLOCK_RE = re.compile(r"<analysis>.*?</analysis>\s*", re.DOTALL | re.IGNORECASE)
SUMMARY_OPEN_RE = re.compile(r"<summary>\s*", re.IGNORECASE)
SUMMARY_CLOSE_RE = re.compile(r"\s*</summary>", re.IGNORECASE)

def format_compact_summary(raw: str) -> str:
    cleaned = ANALYSIS_BLOCK_RE.sub("", raw).strip()
    cleaned = SUMMARY_OPEN_RE.sub("Summary:\n", cleaned)
    cleaned = SUMMARY_CLOSE_RE.sub("", cleaned).strip()
    return cleaned
```

If `cleaned` is empty after stripping (model output only `<analysis>` with no `<summary>`, or empty response), the orchestrator emits `compact_failed(reason="empty_summary")`.

### 8.6 CompactOrchestrator

The orchestrator is a thin coordinator around `llm_service.chat_stream_async`. It does **not** go through the agent runner, smolagents, tools, or schemas. The compact LLM call is a direct, schema-less streaming call.

Sequence:
1. Yield `compact_started` with metadata (trigger, mode, original_tokens, threshold, strategy)
2. Collect messages based on mode (chat: from request body; agent/cycle: from session)
3. Build compact messages (preamble + main prompt + [user custom instructions] + body messages + trailer)
4. Stream from `llm.chat_stream_async`; yield each chunk as `compact_delta` with `partial=true`
5. Post-process: strip analysis, unwrap summary tags
6. Apply compaction based on mode (replace `memory.steps` for agent/cycle; no-op for chat since chat is frontend-driven)
7. Yield `compact_completed` with cleaned text and metadata (summary_tokens, messages_compacted, etc.)

Errors are caught at the appropriate boundary and translated to `compact_failed` with a granular `reason` (see Section 10).

### 8.7 Reset to entry agent

After compact (agent/cycle mode), the session is reset to `config.agent.entry_agent_name` (default `coordinator_1`). This forces the next user message through the routing decision again. Implementation:

- `session.has_run = True` — see §18.1 (post-hoc 2026-06-06) for why False was the original v1 spec and why it was wrong
- `session.current_agent_name = config.agent.entry_agent_name`
- `session.active_agent = None` so `_build_profile_agent` is invoked fresh
- `session.behavior_records` retains `route_receipt` and `handoff_ledger` (Tier 2 audit, never enters LLM input)

This matches ref_src's clean-break philosophy and avoids carrying stale handoff state into the new compact context.

### 8.8 `POST /v1/compact/run` endpoint

Single endpoint, accepts mode in request body:

```python
class CompactRunRequest(BaseModel):
    mode: Literal["chat", "agent", "cycle"]
    session_id: Optional[str] = None      # agent/cycle
    messages: Optional[list[ChatMessage]] = None  # chat
    custom_instructions: Optional[str] = None    # /compact <args>

@router.post("/compact/run")
async def run_compact(req, raw_request: Request):
    orchestrator = raw_request.app.state.compact_orchestrator
    async def stream():
        async for event in orchestrator.run_compact(CompactRequest(
            mode=req.mode,
            messages=[Message(role=m.role, content=m.content) for m in (req.messages or [])],
            session_id=req.session_id,
            trigger="manual",
            custom_instructions=req.custom_instructions,
        )):
            yield format_sse(event)
    return StreamingResponse(stream(), media_type="text/event-stream")
```

Auto-compact does **not** use this endpoint. Auto-compact embeds the orchestrator call directly into the request handlers of `/v1/chat/completions`, `/v1/agent/chat`, and `/v1/cycle/start`.

### 9.3 Timeline projection extension

```ts
  | { kind: 'chat_chunk'; ... }
  | { kind: 'dispatch_update'; ... }
```

### 9.4 Frontend state machine

In the `timeline_event` handler in each page, switch on `projection.kind`:

- `compact_started`: mark all existing messages with `isPreCompact: true`; append a new `bubbleKind: 'compact_summary'` placeholder with the same `id = summaryMessageId`. Track the set of message ids that were newly marked in this run (for precise rollback on failure).
- `compact_delta`: append `text` to the existing panel message whose `compactionBoundaryId === summaryMessageId`.
- `compact_completed`: replace panel `content` with the cleaned `text` (strip the `<analysis>` draft region); set `compactStatus='completed'`; merge `metadata` into `compactMetadata`.
- `compact_failed`: remove the placeholder; for the tracked id set, set `isPreCompact: false` (precise rollback, not affecting prior successful compacts); show error toast with `reason`.

### 9.5 CompactSummaryPanel rendering

Renders when `msg.bubbleKind === 'compact_summary'`. Visual design:

- Full-width container, amber-tinted background, distinct from chat bubbles (so it is unmistakably "background narration", not a chat message)
- Status bar at top: spinner during `streaming`; icon when `completed` or `failed`
- Header line: trigger source (manual / auto with strategy name), token count delta (e.g. "51k → 4.3k tokens")
- Body: streaming markdown text, blinking cursor while streaming
- Collapsible (the user can fold/unfold long summaries)
- Cancel button while streaming (calls `llmClient.stopChat(summaryMessageId)` or `stopAgent(sessionId)`)

### 9.6 Pre-compact message visual

Messages with `isPreCompact: true` render at `opacity-60` (or similar dimmed style) with a small "summarized" badge on hover. This makes the visual boundary between "active context" and "archived history" obvious without losing the conversation record.

### 9.7 Chat mode wire payload

Frontend does not filter its own messages for chat mode. It serializes each message with the appropriate marker:

```ts
const wireMessages = messages.map((m) => ({
  role: m.role,
  content: m.content,
  reasoning_content: m.reasoning_content,
  metadata: m.isPreCompact
    ? { pre_compact: true }
    : m.bubbleKind === 'compact_summary'
      ? { compact_summary: true, summary_id: m.compactionBoundaryId }
      : undefined,
}));
```

Backend `filter_messages_for_llm()` does the rest.

## 10. Error Handling

Compact failures are reported via `compact_failed` SSE events with a granular `reason` field for debugging. The user UX is a single "compression failed, please retry later" message plus the reason as detail. There is no automatic retry.

| Scenario | `reason` | Frontend | Auto-compact continuation |
|---|---|---|---|
| Tokenizer load failure at startup | (not reached) | Auto-compact never triggers; manual `/compact` returns 503 | n/a |
| LLM call fails (timeout / 503 / connection refused) | `llm_unreachable` | "Compression failed: inference backend unreachable" | Skip compact, continue with original request (likely also fails) |
| User aborts mid-stream | `aborted` | "Cancelled"; isPreCompact rolled back | Skip compact, continue |
| LLM output is empty or has no `<summary>` block | `empty_summary` | "Summary generation failed"; isPreCompact rolled back | Skip compact, continue |
| `_apply_compaction` fails (e.g. session deleted) | `apply_error` | "Compression apply failed"; isPreCompact rolled back | Skip compact, continue |
| `_collect_messages` fails (invalid session) | `collect_error` | "Compression request invalid"; isPreCompact rolled back | Skip compact, continue |
| LLM hits `max_summary_tokens` | (success) `compact_completed` with `truncated: true` | Panel shows summary + small "summary truncated" warning | Continue |
| Multiple `compact_summary` panels from successive compactions | n/a | Allowed; filter picks the most recent | n/a |

Rationale for the simple failure model: in local single-model deployment, if compact's LLM call fails, the same failure will hit the main request. No circuit breaker, retry, or partial-compact fallback would help. The compact panel simply displays the failure and the user can manually retry.

## 16. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| AutoTokenizer loading adds startup latency (~5-10s) | Lazy load: only build `TokenCounter` on first compact-related call, not at app startup |
| AutoTokenizer does not support the model path | Catch load error at startup; log; set `should_compact` to permanently return False; document in error message |
| Tokenizer estimates diverge significantly from real SGLang/vLLM token counts | Make the threshold ratio and reserve/buffer all configurable so users can tune per deployment; for the v1 release of `/compact`, the conservative default 0.5 in performance mode has wide safety margin |
| Compact LLM call returns content that fails to match `<summary>` regex | Caught by `empty_summary` failure path; treated as compact failure; isPreCompact rolled back |
| User marks pre_compact=true on a message but the corresponding compact_summary message is missing or out-of-order | `filter_messages_for_llm` is defensive: drops pre_compact messages regardless; if no compact_summary is found, returns the input unchanged minus pre_compact (graceful degradation) |
| User triggers `/compact` while agent is mid-tool-call | Manual `/compact` is disabled when `isLoading`; auto-compact checks happen only between turns; safe by design |
| Cycle mode auto-compact significantly slows down cycle | `cycle_min_steps_between_compacts` config allows tuning; default 0 = check every step, but the check itself is fast (token count is a few milliseconds) and compact only fires when threshold is actually crossed |
| SGLang/vLLM HTTP layer rejects the `metadata` field on ChatMessage | `metadata` is stripped during ChatMessage → Message conversion; SGLang/vLLM never sees it |
| Frontend message-types.ts unification reveals subtle existing differences | If during extraction we discover vision/text pages have meaningful type differences, we keep them as two extended types in the same file, sharing the base |

## 18. Postmortem — what v1 of this spec got wrong (2026-06-06)

> **Audience**: the next "not-in-the-loop" AI / engineer reading this spec for the first time. This section captures the spec-vs-implementation gaps that the bug-fix sequence uncovered. The full timeline lives in `/踩坑记录3.md`; the brief rules are in `AGENTS.md` traps #20–#25.
>
> The corrections are also pinned by regression tests in `tests/test_compact_*.py` and `frontend/src/lib/compact-body.test.mts`. If you change a section that has a correction below, **read the correction first** — the original text was a real failure mode, not a stylistic choice.

### 18.1 Spec-vs-implementation deltas (where the spec said X, reality forced Y)

| Section | Spec said | Actually required | Why |
|---|---|---|---|
| 5.2, 8.6 | Compact prompt is "1 system message containing everything" | **2-message `[system, user]` shape** | Qwen3 chat template's `multi_step_tool` check raises if no user message is present. The single-system design is incompatible with Qwen3. See `tests/test_compact_prompt_builder_template_compat.py`. |
| 6.2, 8.7 | `session.has_run = False` (next user message takes `reset=True` path) | **`session.has_run = True`** | smolagents' `Memory.reset()` is invoked on `reset=True` and silently wipes the envelope we just wrote. The agent then sees an empty history and produces "I don't remember" responses. The re-route is achieved by `current_agent_name` + `active_agent`, not by `has_run`. See `tests/test_compact_envelope_preserved_on_next_run.py`. |
| 8.8 | `POST /v1/compact/run` always uses `app.state.compact_orchestrator` | **Mode-based dispatch**: `mode="agent"` must route to `app.state.agent_runner.run_compact_for_session`, not the chat orchestrator | The chat orchestrator has no authority to mutate `session.agent.memory.steps`. Routing agent-mode requests through it produces a summary in the SSE stream but leaves the agent's memory untouched. See `tests/test_compact_agent_routes_to_runner.py`. |
| 9.7 | Each page builds the wire body inline | **Shared `buildCompactRequestBody` helper** | Two-page inline implementations drifted independently; both ended up hardcoding `mode: 'chat'`. The helper is a single source of truth for the `mode` field, derived from `settings.agentMode`. See `frontend/src/lib/compact-body.test.mts`. |
| 9.x (omitted from v1) | (No status badge / 🧪 button in spec) | These were added as **diagnostic UI** during the bug-fix sequence, then **removed 2026-06-08** once the chain stabilized | Removed because (a) the agent runner's own `[chat] pre-filter` log + SGLang's prompt_tokens log now provide enough surface for diagnosis, and (b) the visible status misled users into thinking "Compacted ✓" = the agent would now use the summary, when in fact the `has_run=True` invariant (above) is invisible to the UI. Status is now communicated through the `compact_summary` bubble and `compact_failed` panel only. |

### 18.2 Spec-level lessons (recurring patterns that the spec text should have caught)

1. **Test what the spec forbids, not what it allows.** The original v1 had no test asserting "Qwen3 chat template accepts this prompt". If it had, the single-system-message design would have been rejected at the unit-test stage, not in production.
2. **Test the full chain, not each unit.** Each unit in the v1 chain was tested in isolation: `_replace_agent_memory` was tested, `_run_basic_stream`'s reset behavior was tested, but the cross-unit interaction (compact writes envelope → next run wipes it) was not tested. The envelope was therefore lost at the integration boundary, and no test caught it.
3. **One flag with multiple meanings is a bug factory.** `session.has_run` carries three responsibilities (smolagents memory reset / routing reset / re-build of the active agent). When v1 of the spec said `has_run = False` for routing-reset, it unintentionally triggered a smolagents memory reset. **Future refactor**: split into three flags. For now, the docstring on `_replace_agent_memory` flags the overload.
4. **Cross-page UI sync must extend to wire-body sync.** Trap #1 (AGENTS.md) said "the compact summary bubble and slash command popup must be in sync between page.tsx and vision/page.tsx". The bug-fix sequence showed this rule must also cover **the wire request body** — two pages that each construct their own request body inline will drift. The helper pattern (`buildCompactRequestBody`) is mandatory, not optional.
5. **A flag named for one purpose is not free to be reused for another purpose**, even if the names seem related. "has_run" sounds like "routing has been run" but smolagents reads it as "memory has been populated, ok to reset". These are different semantically; the variable name does not bridge them.
6. **Mock tests must mirror the real code's field access pattern.** A test that uses `messages[0].get("role")` (dict access) for an LLM stub while the real `llm_service.chat()` uses `messages[0].role` (attribute access) will pass tests while the real code is broken. This bug was caught when the v1 orchestrator was fixed and the mock's dict access surfaced the inconsistency.

### 18.3 Spec-text anti-patterns to avoid in future slash-command / compact designs

- ❌ "Single system message containing instructions + body" → Qwen3 chat template rejects. Always produce ≥ 2 messages with at least one user row.
- ❌ "Reset the agent by clearing a single flag" → verify whether that flag has side effects in another layer (smolagents, here).
- ❌ "Inline wire body in each page" → always extract a shared helper.
- ❌ "Status badge is sufficient diagnostic UI" → bad if a flag overload can make the status green while the actual operation silently failed.
- ❌ "Mock LLM service that just records calls" → if your real LLM service uses attribute access, your mock must too.
- ❌ "Hardcoded mode field in wire body" → derive it from runtime context (`settings.agentMode`) via a shared helper, not from per-page inline code.

## 19. Post-hoc corrections (2026-06-07)

> **Why this section exists**: the v1 spec was written before the lifespan-wiring-ordering bug was discovered (post-hoc in 踩坑记录3.md §9 / AGENTS.md trap #24). The bug existed in the **original implementation** of the spec but was not called out in the spec because the spec was focused on functional behavior, not lifespan init order. Future readers and AI agents who follow this spec literally would re-introduce the bug. This section records the corrections so the spec stays accurate as a contract.

### 19.1 Lifespan wiring ordering (NEW REQUIREMENT)

**Add to Section 13.2 Modified files / `backend/main.py`**:

> **Ordering invariant** (mandatory): when wiring `app.state.compact_orchestrator` into `app.state.agent_runner`, the wiring block MUST execute **after** both the `CompactOrchestrator` instance and the `AgentRunner` instance are constructed. The original spec said "instantiate the orchestrator in `app.state`"; it did not call out that the wiring must come after both ends exist. If the wiring block is placed between the two `app.state` assignments, the `if A and B is not None: wire(A, B)` guard silently skips and auto-compact in agent mode never fires (manual `/compact` still works because `/v1/compact/run` reads `app.state.compact_orchestrator` directly, bypassing the agent runner). See 踩坑记录3.md §9 for the full failure mode.

**Add to Section 14.1 Backend acceptance criteria**:

> - [NEW] After `lifespan` startup, `app.state.agent_runner.compact_orchestrator is not None` and is the same object as `app.state.compact_orchestrator`. Pinned by `tests/test_main_lifespan_wiring.py::test_lifespan_wires_compact_orchestrator_into_agent_runner`.

### 19.2 Unit test coverage gap (NEW REQUIREMENT)

**Add to Section 14.1 Backend acceptance criteria**:

> - [NEW] The compact system has TWO independent execution paths:
>   1. **Manual path**: `POST /v1/compact/run` reads `app.state.compact_orchestrator` directly.
>   2. **Auto path**: `_should_auto_compact_session` in `agent_runner.py` reads `agent_runner.compact_orchestrator` (DI-injected).
>
>   Unit tests that mock `AgentRunner(..., compact_orchestrator=object())` cover the **logical contract** of path 2 but not the **lifespan wiring** that makes path 2 actually work. The original spec only required unit-level coverage. **Both paths MUST have at least one integration test that runs through `lifespan` startup**.

### 19.3 TokenCounter initialization (NEW REQUIREMENT)

**Add to Section 13.2 Modified files / `backend/main.py`**:

> **Initialization invariant** (mandatory): `TokenCounter.get(model_path=config.model.model_path)` MUST be called during lifespan startup, before any compact-related code path. The TokenCounter is a process-wide singleton; if it's not initialized, the multilingual char-based heuristic fallback is used, which undercounts CJK text by 3-4x (real tokenizers produce ~0.7-1.0 tokens/char for CJK; the old `len(content) // 4` heuristic produces ~0.25 tokens/char). This makes auto-compact never fire for Chinese conversations even when SGLang reports 30k+ full tokens. The v1 spec assumed `TokenCounter` would be lazily initialized on first use; the correct fix is eager initialization at startup. If `model_path` is missing or AutoTokenizer load fails, log a warning and continue with the heuristic fallback (degraded mode, not a startup-fatal error).

**Add to Section 14.1 Backend acceptance criteria**:

> - [NEW] `TokenCounter` is initialized during lifespan startup. `use_real_tokenizer == True` and `_model_path == config.model.model_path`. If initialization fails, `use_real_tokenizer == False` (heuristic fallback) AND a warning is logged. Token counts for CJK text are within 2x of the real tokenizer rate. Pinned by `tests/test_compact_tokenizer.py::test_token_count_heuristic_cjk_aware_does_not_undercount_chinese` and `test_token_count_real_tokenizer_handles_batch_encoding_return_type`.

### 19.4 Summary of post-hoc additions

| Section | What was missing | What this correction adds |
|--------|------------------|--------------------------|
| 13.2 / 14.1 | Wiring ordering invariant for `agent_runner.compact_orchestrator` | Explicit ordering requirement + lifespan integration test pin |
| 14.1 | Two-path test coverage (manual vs auto) | Both paths must have a lifespan integration test |
| 13.2 / 14.1 | Eager TokenCounter initialization at startup | Mandatory eager init + fallback policy + 2x CJK accuracy pin |

These corrections do not change the spec's functional behavior; they codify **non-functional invariants** (lifespan ordering, test coverage of multiple paths, tokenizer accuracy) that the original spec under-specified and that the v1 implementation got wrong. Future revisions of the implementation plan (`docs/superpowers/plans/2026-06-06-slash-commands-and-compact-plan.md`) should reference these corrections.
