### 24. GPTQ-Int4 Hybrid 模型 (Qwen3.5-35B-A3B) 的双重 dtype 冲突

**背景**: 部署 `Qwen3.5-35B-A3B-GPTQ-Int4` (VL 视觉版) 于 Jetson Thor (SGLang + sgl_kernel)。

---

#### 问题一：Mamba conv_states dtype 不匹配

**错误信息**:
```
RuntimeError: Expected conv_states_.scalar_type() == input_type to be true, but got false.
```
**调用栈**: `qwen3_5.py → linear_attn → hybrid_linear_attn_backend → causal_conv1d_fn → sgl_kernel/mamba.py`

**原因分析**:
- Qwen3.5-35B-A3B 是 **Hybrid 模型**（Transformer + Mamba/SSM 层混合架构）。
- sgl_kernel 的 `causal_conv1d_fwd` 算子要求 `conv_states`（KV cache 的一部分，以 bfloat16 分配）与输入 activation tensor 数据类型完全一致。


**解决方案**:
修改 `config/config.ini`：
```ini
# 千问3.5的Mamba hybrid架构只支持bfloat16，无法使用float16
dtype: bfloat16   # 从 float16 改为 bfloat16
```

---

#### 问题二：[bug] 【已在github上提了issue】GPTQ Marlin MoE scale dtype 与 activation dtype 不匹配

**错误信息**:
```
AssertionError: moe_wna16_marlin_gemm assumes hidden_states.dtype (torch.bfloat16) == w1_scale.dtype (torch.float16)
```
**调用栈**: `qwen3_5.py → qwen2_moe.py → fused_moe_triton/layer.py → gptq.py → moe_runner/runner.py → moe_runner/marlin.py → fused_marlin_moe.py`

**出现时机**: 问题一修复后，将 `dtype` 改为 `bfloat16`，CUDA Graph capture 阶段即触发此错误。

**原因分析**:
- GPTQ Int4 量化的 checkpoint 中，expert scale 张量（`w13_scales`/`w2_scales`）以 **float16** 存储（量化时固化的格式）。
- `dtype = bfloat16` 使 hidden_states activations 变为 **bfloat16**。
- `fused_marlin_moe.py` 第 86-91 行有硬断言：
  ```python
  assert hidden_states.dtype == w1_scale.dtype, \
      f"moe_wna16_marlin_gemm assumes hidden_states.dtype ({hidden_states.dtype}) == w1_scale.dtype ({w1_scale.dtype})"
  ```
  两者类型不同 → AssertionError 崩溃。
- 这是 Hybrid 架构要求（bfloat16）与 GPTQ 量化格式（float16 scales）之间的内在冲突，单纯修改 `config.ini` 无法解决，需要在 sglang 源码层面修复。

**解决方案（patch sglang 源码）**:
修改 `.sglang/lib/python3.12/site-packages/sglang/srt/layers/moe/moe_runner/marlin.py`，在调用 `fused_marlin_moe` 前将 scale 张量转为与 hidden_states 相同的 dtype：

```python
# 修改前
output = fused_marlin_moe(
    hidden_states=hidden_states,
    w1_scale=quant_info.w13_scales,
    w2_scale=quant_info.w2_scales,
    ...
)

# 修改后（在调用前插入 dtype cast）
w1_scale = quant_info.w13_scales.to(hidden_states.dtype)
w2_scale = quant_info.w2_scales.to(hidden_states.dtype)
output = fused_marlin_moe(
    hidden_states=hidden_states,
    w1_scale=w1_scale,
    w2_scale=w2_scale,
    ...
)
```

cast 精度损失说明：float16 → bfloat16 均为 16-bit 浮点，阶码位数不同但尾数精度相近，scale 转换的精度损失可忽略不计，不影响推理质量。

修改后需清除 `.pyc` 缓存：
```bash
find .sglang/lib/python3.12/site-packages/sglang/srt/layers/moe/moe_runner/__pycache__ -name "marlin*.pyc" -delete
```

**总结**：Hybrid (Attention+Mamba) + GPTQ-Int4 + bfloat16 三者叠加时，需要同时满足：
1. `*config-infer.yaml` 中 `dtype = bfloat16`（Mamba conv_states 要求）
2. Marlin MoE runner 中 scale 张量在传入前显式 cast 至 `hidden_states.dtype`（GPTQ scale float16 与 bfloat16 activation 不匹配的问题）

### 25 [Bug] 【已在github上提了issue】`InternVisionEncoder` CUDA graph path returns `tuple` instead of `BaseModelOutput` when `return_dict=None`, causing `AssertionError` in `RadioModel`


#### Background
When serving a multimodal VLM that uses the RADIO vision encoder (e.g., `NVIDIA-Nemotron-Nano-12B-v2-VL`) with the ViT CUDA graph feature enabled (`SGLANG_VIT_ENABLE_CUDA_GRAPH=1`) and `--mm-attention-backend triton_attn`, text-only requests succeed, but any request carrying an image causes the scheduler to crash with:

```
RuntimeError / AssertionError in radio.py line 464:
    assert isinstance(encoder_outputs, BaseModelOutput)
AssertionError
```

#### Root Cause Analysis

The bug is in `InternVisionEncoder.forward()` in `sglang/srt/models/internvl.py`.

The CUDA graph fast path checks `return_dict` before resolving its default value of `None`:

```python
# BUGGY CODE
def forward(self, inputs_embeds, output_hidden_states=None, return_dict=None):
    if self.enable_cg and (not output_hidden_states):
        hidden_states = inputs_embeds.to(...).contiguous()
        hidden_states = self.cuda_graph_runner.run(hidden_states)
        if not return_dict:           # ← BUG: `not None` evaluates to True
            return (hidden_states,)   # ← Always returns a raw tuple
        return BaseModelOutput(...)   # ← Dead code, never reached
```

`RadioInternVisionModel.forward()` calls `self.encoder.forward(inputs_embeds=hidden_states)` **without** passing `return_dict`, so it defaults to `None`. Because `not None` is `True` in Python, the branch always returns a plain `tuple`.

Immediately after, `RadioInternVisionModel.forward()` asserts:

```python
assert isinstance(encoder_outputs, BaseModelOutput)  # fails because it's a tuple
```

The non-CUDA-graph code path correctly resolves `return_dict` first:

```python
return_dict = return_dict if return_dict is not None else self.config.use_return_dict
```

but this resolution is **skipped** when the CUDA graph branch executes.

Text-only requests never invoke the vision encoder, which is why the bug only surfaces when an image is included in the request.

#### Solution

Resolve `return_dict=None` to `self.config.use_return_dict` **before** using it as a boolean, inside the CUDA graph fast path:

```python
# FIXED CODE
def forward(self, inputs_embeds, output_hidden_states=None, return_dict=None):
    if self.enable_cg and (not output_hidden_states):
        _return_dict = return_dict if return_dict is not None else self.config.use_return_dict
        hidden_states = inputs_embeds.to(...).contiguous()
        hidden_states = self.cuda_graph_runner.run(hidden_states)
        if not _return_dict:
            return (hidden_states,)
        return BaseModelOutput(last_hidden_state=hidden_states, hidden_states=None)
```

### 🪘 【MARK】29. Agent 流式思考框（Reasoning streaming）在网页端无法正确显示

#### 问题现象

在 Agent 模式下，模型输出正常，但网页前端的"思考框"（reasoning/thinking 展示区域）：
- 要么为空白，没有任何内容流入
- 要么把工具调用的 JSON（`<tool_call>...`）也混进思考框，显示成乱码

第二轮对话往往正常，第一轮或首次会话经常出现此问题。

#### 根本原因

**一条数据流，两种语义**：Qwen3-VL 在流式输出时会把 `reasoning_content`（思维链）和 `content`（最终答案/工具调用 JSON）分成两字段交替推送。但 smolagents 的 `generate_stream` 接口只接受单一 `ChatMessageStreamDelta`，没有区分推理流和内容流的字段。

如果直接把两者拼接成 `content` delta 推给 smolagents，就会产生两个后续问题：

1. **工具调用解析失败**：smolagents 在 `_step_stream` 里对 `chat_message.content` 做工具调用正则解析。`agglomerate_stream_deltas` 把 reasoning+content 全部拼成 `content`，工具调用 JSON 被淹没在一大段 reasoning 文字里，正则无论如何也匹配不出来 → 工具永远不会被执行 → 第一步必然退化为 `final_answer`。

2. **思考框内容与答案混用**：即使前端尝试区分两者，`content` 字段里的文本既有推理过程又有答案，无法准确切分，思考框和回答框的内容相互污染。

此外还有一个子问题：**首轮 VLM 推理容易触发"段落重复 loop"**，模型在生成工具调用前不断重复相同段落（约 130 字符块），SGLang 并不会自动停止，最终输出的是残缺 JSON，工具无法执行。

#### 解决方案

**核心策略：`generate_stream` 对外推 reasoning+content 混合流（维持前端思考框流式效果），对内用 `_last_stream_content` 单独追踪纯 content 部分（供工具调用解析）。**

具体分三层：

**层一：流式推送分离追踪**（`backend/agent/local_llm_model.py` · `generate_stream`）

```python
self._last_stream_content = ""    # 只追踪 content 部分，供工具解析
self._last_stream_reasoning = ""  # 追踪 reasoning 部分

for chunk in stream:
    reasoning = chunk.get("reasoning") or ""
    content   = chunk.get("content") or ""
    if reasoning:
        self._last_stream_reasoning += reasoning
        yield ChatMessageStreamDelta(content=reasoning)   # 推给前端思考框
    if content:
        self._last_stream_content += content
        yield ChatMessageStreamDelta(content=content)     # 推给前端内容区
```

**层二：`_step_stream` 覆盖还原**（`backend/agent/agent_runner.py` · `SmartToolCallingAgent._step_stream`）

`agglomerate_stream_deltas` 会把所有 delta 拼为 `chat_message.content = reasoning + content`（混合体）。在流结束后立即用 `_last_stream_content` 覆盖，确保工具调用解析基于纯 content：

```python
if _used_streaming and hasattr(self.model, '_last_stream_content'):
    chat_message.content = self.model._last_stream_content
    memory_step.model_output = chat_message.content
```

工具调用搜索按 content → reasoning → 完整拼接三路依次回退，确保不同模型的输出格式都能被捕获。

**层三：段落级重复检测 + 静默非流式回退**（`backend/agent/local_llm_model.py` · `generate_stream`）

旧的固定 200 字符窗口无法对齐 ~130 字符段落边界，导致段落重复 30+ 次不触发；且检测触发时可能恰在 JSON 内部截断，产生残缺 JSON。

新方案：
- **段落级检测**：以 `\n\n` 切割已生成文本，若最近 4 个段落仅有 ≤2 种不同内容则立即触发
- **JSON 块豁免**：统计 `{` 与 `}` 数量差，差值 > 0（在 JSON 对象内部）时跳过所有检测，允许 JSON arguments 里的合法重复数据
- **静默非流式回退**：检测到重复后，清空 `_last_stream_content`，用非流式（`stream=False`）重新生成干净响应，只写入 `_last_stream_content` 而不 yield 到 SSE，让 `_step_stream` 从干净结果解析工具调用

```python
# JSON 块豁免
_open_braces = _last_stream_content.count('{') - _last_stream_content.count('}')
if _open_braces > 0:
    continue

# 段落级检测
blocks = [b.strip() for b in combined.split('\n\n') if b.strip()]
if len(blocks) >= 4 and len(set(blocks[-4:])) <= 2:
    _repetition_detected = True
    break

# 静默回退
if _repetition_detected:
    self._last_stream_content = ""
    result = self.llm_service.chat(messages=llm_messages, stream=False, tools=None)
    self._last_stream_content = result.text or ""
    return  # 不 yield，让 _step_stream 从 _last_stream_content 解析
```

#### 效果

- 思考框流式显示正常，reasoning 实时滚动
- 工具调用在第一轮即可正常执行（不再退化为纯文本 final_answer）
- 段落重复 loop 触发后约 2–3 秒静默修正（原来需等待 25–30 秒乱码后才失败）

### 🪘 【MARK】30. 流式工具调用（tool_call_parser）陷阱与修复（诊断与实践）

#### 问题现象

在 Agent 的流式链路中，出现如下异常行为：
- 第一轮对话中模型虽产生了“动作/工具调用”形式的输出（例如提示里有“动作:”或 JSON 块），但后端未能识别并执行工具；
- 前端思考框（reasoning）显示大量重复段落或空白；
- 第二轮或重新发起请求时同样的提示又能被正确识别并执行（即有时“首轮失败、重试成功”）。

#### 根本原因

1. SGLang + Qwen3 系列在流式 + tool_call_parser 模式下，有两种输出语义并行：
    - `reasoning_content`（思考流）用于思维鏈路的增量输出；
    - `content`（答案/结构化调用）用于最终回答或 `<tool_call>` 块。  
    smolagents 的流式聚合 (`agglomerate_stream_deltas`) 往往把这两者合并成單一的 `chat_message.content`，导致语义混淆。

2. 如果在向 SGLang 发起流式请求时**沒有正确激活 `tool_call_parser`（也就是请求未带上 `tools` 定义或 parser 未被启用）**，模型会退回到按提示文本（如中文“动作:”示例）生成伪结构化文本，而不是产出可被 parser 识别的 `<tool_call>` 结构，后端的 `_parse_tool_calls_from_text` 无法识别这种自由文本格式，最终整段被当作纯文本处理。

3. SGLang 在某些组合下还会把 `<tool_call>` 块交給 parser 消費，但**不把解析后的 tool_calls 以 delta.tool_calls 回传**（见 AGENTS.md 陷阱 #3 的变体）。结果流式聚合出的 ChatMessage 只有 content，无 tool_calls，仍被当作纯文本。

4. 模型在准备工具调用前可能进入“段落重复 loop”（重复输出相同 100–200 字節塊），若截斷发生在 JSON 内部，会產生殘缺 JSON 導致解析失败。

#### 解决方案（工程实践）

1. 激活并传递 `tools` 给推理后端（首选方法）
    - 只要希望 SGLang 的 `tool_call_parser` 生效，流式/非流式请求中都应把 `tools`（工具 schema）传给服务端；不要用 `tools=None` 绕過 parser，除非你明确需要回避 parser 的已知流式 bug 并且有后备解析策略。

2. 后端多层次解析容错（已实现的防御策略）
    - 首先检查流式返回中的 `delta.tool_calls`（若有则直接使用）；
    - 如果没有，再在 `content` 中运行结构化解析正则（`_parse_tool_calls_from_text`）；
    - 如果仍未找到，则在 `reasoning` 中搜索（很多模型先把动作放在思考段）；
    - 最后回退到**一次非流式**完整生成并解析（`stream=False`），以获取干净且完整的 `<tool_call>`。

3. 对流式输出做严格追踪与分离（保证前端体验且不破坏工具解析）
    - 对外：继续把 reasoning 和 content 的每个 delta 推给前端，实现思考框的流式体验；
    - 对内：单独维护 `_last_stream_content`（仅收集 content 部分），在流结束后用其覆盖 `chat_message.content`，确保工具解析基于纯 content 而非 reasoning+content 混合体。

4. 段落级重复检测与 JSON 豁免
    - 增加段落级重复检测（以 `\n\n` 为分界），可快速捕捉模型循环输出相同段落的情形；
    - 在检测时对处于未闭合 JSON 对象（`{` > `}`）的情况跳過检测，避免把合法的 JSON arguments（如文件内容的大段重复文本）误判为无限循环；
    - 检测触发后静默回退到非流式生成，重置脏的流式缓存，再由后端解析并执行工具调用。

5. 可选：在需要绝对可靠的工具调用场景中优先使用非流式路径
    - 流式体验用于交互和进度感；但当工具调用必须精确触发且不能容忍任何解析误判时，优先用 `stream=False`。

6. 加强诊断日志和可视化
    - 在发送请求前打印/保存最终渲染的 system prompt（确认 VLM 指令和工具列表已包含）；
    - 保存 SGLang 接收到的消息结构与解码图片（`/tmp/sglang_debug/`），便于离线复现；
    - 在流式回退发生时记录触发原因（段落重复 / 窗口重复 / JSON 未閉合）。

#### 快速建议（checklist）

- 请求 SGLang 時 `tools` 参数：有需要则传入；谨慎使用 `tools=None`。
- 实现流式 content 与 reasoning 分离追踪（`_last_stream_content`）。
- 增加段落级重复检测并对 JSON 内部进行豁免。
- 在无法解析時回退到非流式并记录诊断信息。

上述策略已在本仓库 `backend/agent/local_llm_model.py` 与 `backend/agent/agent_runner.py` 中实现；若仍遇到首轮失败、重试成功的情形，可先检查是否为 SGLang 的已知流式 parser 行为（必要时重启推理服务作为应急措施，见第 27 条）。

### 31. **Agent 会话记忆丧失**: 
模型在连续对话中丧失记忆，忘记之前设置的变量值。

**根本原因**: 双重 Bug 导致每次请求都新建 Session 或清空历史。**Bug 1**: `agent.run()` 默认 `reset=True`，每次调用都执行 `memory.reset()` 清空 `memory.steps`。**Bug 2**: `done` 事件不携带 `session_id`，前端始终拿不到 UUID，下次请求传 `undefined`，后端每次都新建 Session。

**修复方法**: 1`agent.run()` 改为 `reset=False`；2 `done` 事件改为 `{'type': 'done', 'session_id': session.session_id}`。

### 32. Stop 按钮在第三轮及之后失效 + 流式内容不显示

#### 问题现象

1. **Stop 按钮不显示**：第一轮、第二轮正常，第三轮开始 Stop 按钮消失
2. **流式内容不显示**：推理完成后，界面仍显示"思考中..."，没有任何内容
3. **isLoading 状态卡死**：即使推理已完成，`isLoading` 状态仍未重置

#### 根本原因

**问题一：Session 的 aborted 标志未在复用时重置**

当用户发送第二轮及之后的对话时，后端会复用已存在的 `AgentSession`（因为 `session_id` 相同）。然而：
- 第一轮点击 Stop 时，`session.aborted = True`
- 第二轮开始时，`get_or_create_session()` 返回同一个 session，但 **没有重置 `aborted` 标志**
- Agent 刚启动就被判定为已中止，直接返回 `aborted` 事件，流式内容从未产生

```python
# 问题代码 (agent_runner.py)
def get_or_create_session(self, session_id, mode):
    if session_id:
        session = self.sessions.get(session_id)
        if session:
            return session  # ❌ 没有重置 aborted 标志
```

**问题二：前端缺少详细日志，难以定位问题**

早期版本缺少前端/后端通信日志，导致问题定位困难。

#### 解决方案

1. **在 `get_or_create_session()` 中重置会话状态**

```python
# 修复后 (agent_runner.py)
def get_or_create_session(self, session_id, mode):
    if session_id:
        session = self.sessions.get(session_id)
        if session:
            # 重置中止标志，允许会话继续
            session.aborted = False
            session.answer_now = False
            return session
```

2. **添加详细的前端日志**（便于后续问题排查）
   - 在 `api.ts` 的 SSE 事件处理中添加 `console.log` 打印所有事件类型
   - 在 `page.tsx` 的 `onStep`、`onContent`、`onComplete` 回调中添加日志
   - 确认事件是否到达前端、是否被正确解析

#### 诊断方法（供后续参考）

当遇到类似问题时，按以下顺序检查：

1. **检查后端日志**：看是否收到请求、是否触发 abort
2. **检查前端 SSE 事件**：在 `api.ts` 的 `switch` 前打印 `event.type`
3. **检查回调触发**：在 `onStep`/`onContent`/`onComplete` 中打印日志
4. **检查 Session 状态**：确认 `session.aborted` 在复用时是否被正确重置

关键日志关键词：
- `[API] Received SSE event: aborted` → 后端已标记中止，需检查 session 状态
- `[API] Received SSE event: done` → 正常结束
- `onStep received` / `onContent received` → 事件到达前端
- `onComplete called` → 流式结束回调触发

### 🪘 【MARK】33. smolagents `@tool` 装饰器 JSON Schema 生成失败

#### 问题现象

Agent 服务初始化失败，错误信息：
```
Cannot generate JSON schema for wrapper because the docstring has no description for the argument 'args'
```

#### 根本原因

smolagents 的 `@tool` 装饰器在**装饰时**（decoration time）就需要生成 JSON schema，而不是在运行时。这要求：
1. 被装饰的函数**必须**在装饰时就有完整的 docstring
2. docstring 必须在函数定义内部，而不是之后通过 `__doc__` 赋值
3. Args 中的参数名要用 `args` 和 `kwargs`（无 `*` 前缀）

#### 错误做法（已踩坑两次）

```python
# ❌ 错误1: 先定义函数，再赋值 __doc__
@tool
def wrapper(*args: tuple, **kwargs: dict) -> str:
    """简短 docstring"""
    return base_func(*args, **kwargs)

wrapper.__doc__ = """完整的 docstring"""  # 太晚了！@tool 已经装饰完了
```

```python
# ❌ 错误2: docstring 中用 *args 和 **kwargs
@tool
def wrapper(*args: tuple, **kwargs: dict) -> str:
    """错误示范

Args:
    *args: 这会失败  # ❌ smolagents 期望的是 "args" 不是 "*args"
    **kwargs: 这也会失败
"""
```

#### 正确做法

```python
# ✅ 正确: docstring 直接写在函数内部，且用 args/kwargs（无 *）
@tool
def wrapper(*args: tuple, **kwargs: dict) -> str:
    """Session-aware wrapper for {tool_name}.

Args:
    args: Positional arguments passed to the base function.
    kwargs: Keyword arguments passed to the base function. Includes: {params_str}
    check_abort: Optional callback to check if operation should be aborted (injected automatically).

Returns:
    str: Result from the base function or abort message.
"""
    session_id = current_session_context.get()
    # ... function body
```

#### 受影响的函数

- `backend/agent/agent_runner.py` 中的 `_make_session_aware_wrapper()`
- `backend/agent/agent_runner.py` 中的 `_create_tool_wrapper()`

#### 关键教训

smolagents `@tool` 装饰器的 schema 生成发生在**装饰时**，不是在运行时。任何在装饰后修改 `__doc__` 的尝试都会失败。务必在装饰前/装饰时就把完整的 docstring 写好。

### 34. Agent 工具获取 session_id 为 None —— `run_stream` 闭包变量与 `session.session_id` 不同步

#### 问题现象

Agent 调用 `load_images` 工具时，始终返回错误："错误: 无法获取当前会话 ID，图片加载失败"。
三种 session_id 获取机制（tool 属性注入、threading.local()、module-level dict）全部返回 None。

#### 根本原因

前端首次请求时 `session_id` 为 `null`，传入后端 `run_stream(session_id=None, ...)`。
`get_or_create_session(None)` 内部会生成新 UUID 并赋给 `session.session_id`，但 `run_stream` 的**局部变量** `session_id` 仍为 `None`。

嵌套函数 `_run_agent()` 通过闭包捕获的是外层 `run_stream` 的局部变量 `session_id`（即 `None`），而不是 `session.session_id`。因此 `current_session_context.set(None)` 存入的是 None，所有依赖 session_id 的工具全部失败。

```python
# 问题代码
async def run_stream(self, session_id: str, ...):
    session = self.get_or_create_session(session_id, mode)  # session.session_id = "uuid-xxx"
    agent = session.agent
    # session_id 仍为 None！
    
    def _run_agent():
        current_session_context.set(session_id)  # ← 存入 None
        ...
```

#### 解决方案

在 `get_or_create_session()` 之后立即同步局部变量：

```python
session = self.get_or_create_session(session_id, mode)
agent = session.agent
session_id = session.session_id  # ← 关键：同步为实际 UUID
```

同样的问题也存在于 `run_sync()` 方法中，需一并修复。

#### 教训

当函数参数可能为 None，且内部逻辑会生成替代值（存入其他对象属性）时，**必须将替代值回写到局部变量**，否则闭包/后续代码捕获的仍是原始 None。这类 bug 极难定位，因为所有中间机制（thread-local、dict、属性注入）看起来都"正确实现"了，但源头值就是 None。

### 35. VLM 视觉识别"投毒"问题：摄像头拍照模式后的 radix cache 污染（即便缩放至同一个max尺寸，但不同相机的图片长宽比可能不一致，导致CUDA GRAPH被“投毒”从而VLM无法读图）

#### 问题现象

1. 使用**摄像头拍照模式**（Vision 页面 → 摄像头拍照 → Agent 模式）完成一次正常对话后
2. 切换到 **Cycle 模式**（编程循环）尝试拍照识别
3. Cycle 的第一轮及后续所有轮次中，VLM 完全无法正确识别图片内容
4. 模型输出诸如"看到黑白相间的纹路"、"全黑的画面"等胡话
5. **关键特征**：纯文本对话（不带图片）完全正常，只有视觉识别能力被破坏

#### 根本原因分析

**临时解决方案**：禁用 `SGLANG_VIT_ENABLE_CUDA_GRAPH` 环境变量。

经过深入调查，发现问题与 SGLang 的以下机制相关：

1. **ViT CUDA Graph 机制**：`SGLANG_VIT_ENABLE_CUDA_GRAPH=1` 会启用 ViT CUDA Graph 优化
   - 脚本注释警告："要求每次传进来的图片分辨率都一样，否则会不断地进行 Graph Capture"
   - 摄像头拍照的图片分辨率预缩放到 1024px，而 Cycle 模式使用 OpenCV 原始相机分辨率（如 1280x720）
   - 不同分辨率 → CUDA Graph 捕获不同 → 可能导致 GPU 状态损坏

2. **投毒表现**：
   - 重启前端/后端服务**无效**（因为缓存还在 SGLang GPU 内存中）
   - 只有**重启 SGLang 服务并清空 GPU 显存**后才能恢复
   - 说明问题不是软件层面的缓存，而是 GPU 内存中的 ViT 状态被破坏

3. **临时解决方案**：禁用 ViT CUDA Graph

**注意**：我们曾尝试通过 `cache_salt` 参数（基于图片 SHA-256 哈希）来隔离不同图片的 radix cache，但这并不能解决问题。真正的根因是 ViT CUDA Graph 的状态损坏，而非 KV cache 复用。

#### 临时解决方案

编辑 `scripts/1_start_sglang.sh`，注释掉 ViT CUDA Graph 启用：

```bash
# VLM 启用 CUDA 图优化，激活ViTCudaGraphRunner，加速VLM首帧

### 36. Cycle 模式双击 Start 按钮发起多个请求

- 状态混乱
- 资源竞争

#### 解决方案

在 `frontend/src/components/CycleEditor.tsx` 中添加防抖机制：

const [isStarting, setIsStarting] = useState(false);

const handleStart = async () => {
  if (isStarting) return; // 防抖：防止双击发起多个请求
  setIsStarting(true);
  try {
    await onStart(steps, shareContext);

    // 短暂延迟后重置状态，避免快速连续点击

  }
};
```

按钮在 starting 状态下显示 "Starting..." 并禁用。

### 🪘 【MARK】39. Agent Cycle 第二轮"发疯" —— `write_memory_to_messages()` 中 `stripped.tool_calls = None` 导致孤立观察（Orphaned Observations）

#### 问题现象

在 Cycle 模式（编程循环）中，使用 `share_context=True`（共享上下文）：
1. **第一轮**正常：模型正确调用工具、返回结果
2. **第二轮**大概率"发疯"：模型要么不调用工具（出现各种幻觉），要么无限重复调用同一个工具

#### 根本原因

`SmartToolCallingAgent.write_memory_to_messages()`（`backend/agent/agent_runner.py`）在处理 `ActionStep` 时，错误地将 `tool_calls` 设为 `None`：

```python
# BUG 代码
elif isinstance(memory_step, ActionStep):
    stripped = copy(memory_step)
    stripped.tool_calls = None          # ← 问题根源！
    stripped.observations_images = None
    messages.extend(stripped.to_messages(summary_mode=summary_mode))
```

**`tool_calls = None` 的连锁效应**：

smolagents 的 `ActionStep.to_messages()`（`.sglang/.../smolagents/memory.py:92-150`）根据 `tool_calls` 是否存在来生成不同的消息：

| tool_calls 状态 | 生成的消息序列 |
|---|---|
| 存在 | ASSISTANT(思考) → TOOL_CALL(→ASSISTANT) → TOOL_RESPONSE(→USER) |
| `None` | ASSISTANT(思考，可能缺失) → TOOL_RESPONSE(→USER，**孤立！**) |

当 `tool_calls = None` 时，`TOOL_CALL` 消息缺失，`TOOL_RESPONSE` 变成孤立的 USER 消息。

更严重的情况：如果 `model_output` 也被 `_strip_tool_call_text` 清洗为 `None`（模型只输出了工具调用没有思考内容），`ASSISTANT` 消息也缺失，导致两个相邻的 `USER` 消息被 smolagents 的 `get_clean_message_list()`（`models.py:375-385`）**合并**：

```
# 灾难性消息合并
user: "New task:\n<第一轮问题>\nObservation:\n<工具输出>"
```

模型在第二轮看到的历史格式完全违反了预期的 action→observation 流程，导致"发疯"。

#### 对比 smolagents 父类原始行为

smolagents 父类 `MultiStepAgent.write_memory_to_messages()`（`agents.py:757-769`）**不会** strip `tool_calls`：

```python
# 父类原始实现（正确）
def write_memory_to_messages(self, summary_mode=False):
    messages = self.memory.system_prompt.to_messages(summary_mode=summary_mode)
    for memory_step in self.memory.steps:
        messages.extend(memory_step.to_messages(summary_mode=summary_mode))
    return messages
```

保留 `tool_calls` 时，`ActionStep.to_messages()` 会生成完整的 ASSISTANT → TOOL_CALL → TOOL_RESPONSE 序列。

#### 解决方案

删除 `stripped.tool_calls = None`，只保留 `stripped.observations_images = None`（后者确实需要剥离，因为它们是任务图片的副本会导致重复）：

```python
# 修复后
elif isinstance(memory_step, ActionStep):
    stripped = copy(memory_step)
    # 不能 strip tool_calls！否则破坏 action→observation 配对
    stripped.observations_images = None
    messages.extend(stripped.to_messages(summary_mode=summary_mode))
```

#### 教训

1. **覆写父类方法时，必须理解被覆写方法的完整行为**。`write_memory_to_messages()` 的原始实现保留 `tool_calls` 是有意为之的——它是消息序列完整性的关键。覆写时只应修改真正需要改变的部分（图片剥离），不应"顺手"清理看起来不需要的字段。

2. **smolagents 的消息角色转换机制**：`TOOL_CALL → ASSISTANT`、`TOOL_RESPONSE → USER`。当 `TOOL_CALL` 缺失时，`TOOL_RESPONSE`（→USER）会与前面的 USER 消息合并，破坏消息结构。这种隐式转换使得 bug 非常隐蔽。

3. **`get_clean_message_list()` 的合并行为**是合理的设计（防止连续相同角色的消息），但在 `tool_calls` 被错误移除时会加剧问题。

4. **多轮对话的消息序列完整性**：单轮对话中这个 bug 不会暴露（因为只有当前轮的历史被回放），只有在 `share_context=True` 的多轮场景中，历史 ActionStep 的消息格式才会影响后续轮次。

### 40. 多轮 Agent 对话到第三轮开始“降智” —— 历史 `Calling tools:` / `Observation:` 转录稿污染上下文

#### 问题现象

在 Agent 模式下进行连续多轮对话（尤其 `share_context=True`）时：

1. **第一轮**通常还比较正常，模型能按当前提供的 tool schema / JSON schema 调用工具
2. **第二轮、第三轮**开始明显变“笨”：
   - 不再稳定输出结构化 tool call
   - 开始模仿历史文本，输出 `### 第一步：...`、`Called the Read tool with the following input: ...`、`<path>...</path><content>...</content>` 之类的“工具转录稿”
   - 看起来像“模型 nerf / 降智 / 忘了 schema”，但第一轮又是正常的

#### 根本原因

这不是单纯的 prompt 不够强，而是**多轮记忆序列化方式本身在给模型错误示范**。

`SmartToolCallingAgent.write_memory_to_messages()` 旧实现会把**所有历史轮次的 `ActionStep` 全量回灌**到下一轮上下文中。

而 smolagents 的 `ActionStep.to_messages()`（`.sglang/.../smolagents/memory.py`）会把每一步转成显式文本：

```text
Calling tools:
[{"id": ..., "function": {"name": ..., "arguments": ...}}]

Observation:
...
```

也就是说，模型在第二轮、第三轮看到的并不只是“之前做过什么”，而是看到了大量旧的工具调用转录稿。对中等能力或较弱的 tool-calling 模型，这些历史文本会变成一种**负向 few-shot 示例**：

- 模型开始学习“历史里是这样写工具调用的”
- 进而模仿这些自然语言 / 转录格式
- 反而偏离当前请求里真正给出的 tool schema / JSON schema

这类问题与第 39 条不同：

- **第 39 条**：`tool_calls` 被错误移除，导致 action→observation 配对破坏，模型“发疯”
- **本条**：即便 action→observation 配对是完整的，**把历史轮次的完整工具轨迹无限回灌**本身也会污染后续轮次

#### 解决方案

修改 `backend/agent/agent_runner.py` 的 `write_memory_to_messages()`，采用**历史轮次去转录稿化、当前轮次保真**的策略：

1. **历史轮次**（最后一个 `TaskStep` 之前的所有轮次）保留“事实内容”，但不保留 tool-role 包装：
   - 用户任务（`TaskStep`）
   - 工具 `observations` 的文本内容本身
   - 该轮的最终助手答复（`is_final_answer=True` 的 `ActionStep`）

2. **历史轮次不再回灌**：
   - `TOOL_CALL` / `TOOL_RESPONSE` 角色
   - `Calling tools:`
   - `Observation:`
   - 容易被模型模仿的旧轮工具转录格式

3. **注意一个后续踩坑**：如果把历史轮次压缩得过头，只保留 final answer、却把 `observations` 也删掉，那么模型在下一轮就会丢失对“上一轮工具到底搜到了什么”的记忆。典型现象是：上一轮先调用 `search_and_fetch`，再调用 `wikipedia_search_and_fetch`，下一轮用户追问“wiki 之前 search_and_fetch 搜出来的文本你还记得吗？”，模型会老实回答“否”。

4. **因此正确做法不是**“全量工具轨迹” 和 “只留最终答案” 二选一，而是：
   - 保留 observation **内容本身**
   - 去掉 observation 的 tool-role 与固定前缀包装

5. **当前轮次**仍保留完整 `ActionStep` 序列，确保同一轮内多步工具推理能力不受影响

6. 兼容一种边角情况：有些最终答案路径下，最终文本可能只保存在 `action_output`，而 `model_output` 为空，因此历史压缩时需优先从 `action_output` 和 `model_output` 两处提取最终答案

核心修复思路示意：

```python
elif isinstance(memory_step, ActionStep):
    if i < last_task_idx:
        _append_assistant_text(_historical_observation_text(memory_step))
        _append_assistant_text(_historical_final_answer_text(memory_step))
        continue

    stripped = copy(memory_step)
    stripped.observations_images = None
    messages.extend(stripped.to_messages(summary_mode=summary_mode))
```

#### 为什么这是更 robust 的方案

相比继续堆 prompt、继续提醒模型“请务必按 JSON Schema 调工具”，从**消息序列化层切断污染源**更稳：

- prompt 只能“劝模型别学坏”
- 历史转录稿一旦进上下文，模型往往更容易模仿这些显式文本模式
- 真正可靠的做法是：**不要把历史轮次的工具转录稿再喂回去**

结论：对于多轮 tool-calling agent，**完整历史 != 高质量历史**，但**高质量历史也不等于只留 final answer**。历史轮次应该保留可追问的事实内容、去掉危险的工具转录格式；当前轮次才保留完整工具轨迹。

#### 回归测试

为避免此类问题再次出现，在 `tests/test_write_memory_tool_calls.py` 中新增回归测试，覆盖：

1. 历史轮次应保留 observation 内容和 final answer，但不保留 `TOOL_CALL / TOOL_RESPONSE`
2. 历史消息中不应再出现旧的 `Calling tools:` / `Observation:` 前缀文本
3. 当前轮次仍必须保留 `TOOL_CALL / TOOL_RESPONSE`
4. 历史多工具轮次中的多个 observation 内容都必须可被后续轮次追问
5. 当最终答案仅存在于 `action_output` 时，历史压缩也必须保留该答案

#### 教训

1. **多轮 Agent 的上下文治理比单轮更重要**。很多问题不是模型本身能力差，而是历史消息结构在持续误导模型。
2. **不要把工具运行日志当作高质量 few-shot 示例反复灌给模型**。对弱一点的模型，这几乎等于在教它输出“伪工具调用”。
3. **但也不要把历史 observation 内容一并删掉**。否则模型虽然不再模仿旧格式，却会失去对“上一轮工具搜到了什么”的可追问记忆。
4. **修 tool-calling 稳定性时，优先排查“历史消息长什么样”**，而不只是盯着 system prompt 或 parser。
5. **robust 的工程方案通常不是“再补一条提示词”**，而是从消息构造层面做“保留事实、删除危险格式”的精细化裁剪。

### 41. `exec_command` 继承后端 `.sglang` 环境，污染 agent 专属 `~/.agent` uv 环境

#### 问题现象

- Agent 通过 `exec_command` 执行 Python / uv / 外部命令时，本应使用 `~/.agent` 专属环境，但实际行为会偏向本仓库的 `.sglang` 环境
- 裸 `python` / `uv` 命令容易落到 `.sglang`
- 即使用绝对路径 `~/.agent/bin/python`，进程内部仍可能带着 `.sglang` 的环境变量，造成环境语义污染
- 直接尝试 `source ~/.agent/bin/activate` 还会报 `/bin/sh: 1: source: not found`

#### 根本原因

- 后端 uvicorn 是在 `scripts/2_start_backend.sh` 中先激活 `.sglang` 后启动的，因此后端进程天然继承：
  - `VIRTUAL_ENV=~/Project/LLM-deployment/.sglang`
  - `PATH` 以 `.sglang/bin` 开头
- 旧版 `exec_command` 直接 `subprocess.Popen(command, shell=True)`：
  - 默认走 `/bin/sh`
  - 完整继承后端进程环境
  - 不清理 `VIRTUAL_ENV` / `PYTHONHOME` / `PYTHONPATH` / `PATH`
- 因此：
  - 裸 `python` / `uv` 命令优先命中 `.sglang`
  - 即便显式执行 `~/.agent/bin/python`，`sys.executable` 虽然是 `.agent`，但 `VIRTUAL_ENV` / `PATH` 等运行时语义仍然是脏的

#### 解决方案

修改 `backend/tools/sys_ops.py`：

1. 清理继承的虚拟环境变量：
   - `VIRTUAL_ENV`
   - `UV_PROJECT_ENVIRONMENT`
   - `PYTHONHOME`
   - `PYTHONPATH`
2. 从 `PATH` 中剔除当前项目 `.sglang/bin` / `.venv/bin` 以及继承来的虚拟环境 `bin`
3. 将 `~/.agent/bin` 置于 `PATH` 最前面
4. 执行方式从 `shell=True` 改为 `/bin/bash -lc`
5. 显式 `export VIRTUAL_ENV=~/.agent`

#### 回归验证

- 新增 `tests/test_sys_ops.py`
- 验证 `exec_command`：
  1. 使用 `/bin/bash -lc`
  2. 会清理项目 `.sglang` 污染
  3. 默认 Python 环境落到 `~/.agent/bin/python`

#### 教训

1. **子进程环境污染往往来自“父进程是怎么启动的”**，不是某条命令本身写错了。
2. **显式绝对路径 != 环境彻底隔离**。二进制路径是对的，不代表 `VIRTUAL_ENV` / `PATH` / `PYTHON*` 语义也对。
3. **不要指望 `source` 激活虚拟环境**。`exec_command` 底层 shell 不应依赖交互式激活流程。

### 42. `playwright-cli: not found` —— 非交互 Bash 不会自动加载 NVM / Node PATH

#### 问题现象

- 用户在自己终端中可直接执行 `playwright-cli`
- Agent 经 `exec_command` 执行同样命令时返回：

```text
/bin/bash: 行 1: playwright-cli: 未找到命令
```

#### 根本原因

- `exec_command` 使用的是 `bash -lc` 非交互登录 shell
- 用户的 `~/.bashrc` 开头有：

```bash
case $- in
    *i*) ;;
      *) return;;
esac
```

- 非交互 shell 会在这里直接 `return`
- 而 NVM 初始化代码在 `~/.bashrc` 后半段：

```bash
export NVM_DIR="$HOME/.nvm"
[ -s "$NVM_DIR/nvm.sh" ] && . "$NVM_DIR/nvm.sh"
```

- 所以 `~/.nvm/versions/node/.../bin` 根本不会进入 PATH
- 进一步检查运行中的后端进程 `/proc/<pid>/environ` 也证实：其 `PATH` 中没有 NVM 目录

#### 解决方案

在 `backend/tools/sys_ops.py` 的 bash 包装器中显式加载 NVM：

```bash
export NVM_DIR="$HOME/.nvm"
[ -s "$NVM_DIR/nvm.sh" ] && . "$NVM_DIR/nvm.sh" >/dev/null 2>&1
```

这样即使后端启动时没带上 Node / NVM PATH，`exec_command` 运行 `playwright-cli` 前也会把它补齐。

#### 回归验证

- `tests/test_sys_ops.py` 增加断言：包装命令中必须包含 NVM 初始化语句
- 实测 `exec_command("playwright-cli --version")` 能正常返回版本号

#### 教训

1. **“我终端里能跑” 不代表 agent 子进程里也能跑**。交互式 shell、登录 shell、非交互 shell 的初始化链路是不同的。
2. **PATH 问题要看运行中进程的真实环境**，不要只看当前手工终端。
3. **修 Node/CLI 可执行文件找不到时，先检查 NVM/Volta/asdf 这类延迟初始化工具链**。

### 43. Playwright 多标签新闻页重复打开 —— 主因不是上下文被剥离，而是“多标签切换信号对本地模型不够显式”；绑定 session 时还要避免误用 `PLAYWRIGHT_CLI_SESSION`

#### 问题现象

- 让本地 LLM 打开一个新闻门户网站中的一篇新闻
- 第一次点击新闻标题后，observation 里的 `Open tabs` 已出现多个相同新闻页标签
- 但 `Page URL` / `(current)` 仍停留在门户页或列表页
- 模型后续继续重复调用 `playwright-cli click eXX`，导致同一新闻被多次新开标签页

#### 曾怀疑但已排除

- 曾怀疑是“同一对话中多个工具调用的过程中，上下文被 `write_memory_to_messages()` 剥离”
- 排查 `backend/agent/agent_runner.py` 后确认：
  - 当前轮次仍保留完整 `ActionStep`
  - `tool_calls` / `observations` 没有在同轮中被剥掉
- 因此这次问题**不是**第 39 / 40 条那类 memory 序列化问题

#### 更准确的根本原因（最终版）

1. **这次问题不是 memory / context 被剥离**
   - 排查 `backend/agent/agent_runner.py` 后确认：当前轮次仍保留完整 `ActionStep`、`tool_calls` 与 `observations`
   - 因此这次不属于第 39 / 40 条那类 `write_memory_to_messages()` 破坏 action→observation 配对的问题

2. **Observation 对本地小模型不够显式**
   - 从人的角度看，`Open tabs` + `Page URL` 已足够说明“点击成功了，只是新闻在新标签页打开”
   - 但对本地 LLM 来说，这类跨字段推理负担偏高
   - 模型更容易把“当前页没变”误判为“点击失败”，于是继续重复点击，而不是先 `tab-select`

3. **Playwright CLI 确实需要固定到同一个 session，但当前版本不能用 `PLAYWRIGHT_CLI_SESSION=<agent_uuid>` 来做**
   - 初版修复曾尝试向子进程注入：

```bash
PLAYWRIGHT_CLI_SESSION=<session_id>
```

   - 进一步读源码后发现，当前 `playwright-cli` 版本里这个环境变量有双重语义：
     - `registry.js` 用它当默认 session name
     - `session.js` 的 `startDaemon()` 又会把它当作 `--endpoint` 传给 `open`
   - 于是 `playwright-cli open ...` 会尝试去连接一个名为 `<session_id>` 的 endpoint/socket，最终报错：

```text
Error: connect ENOENT d16ad99c-213a-4e8c-9e1b-201d8cb04988
```

   - 所以真正的正确做法不是环境变量，而是**把所有 `playwright-cli` 命令显式改写为 `playwright-cli -s=<session_id> ...`**

#### 解决方案

修改 `backend/tools/sys_ops.py`：

1. 对 `playwright-cli` 命令显式注入 session flag，而不是设置环境变量：

```bash
playwright-cli -s=<session_id> open https://example.com --browser=chromium --headed
playwright-cli -s=<session_id> snapshot
playwright-cli -s=<session_id> click e26
```

2. 对 `playwright-cli click` / `dblclick` 的 observation 做最小增强：
   - 若检测到 `Open tabs` 中出现新标签页
   - 且 `Page URL` / `(current)` 仍停留在原门户页
   - 自动追加明确提示：
      - 优先执行 `playwright-cli tab-select <index>`
      - 必要时先 `playwright-cli tab-list`
      - 不要重复点击同一链接

3. 同步更新 `backend/skills/playwright-cli/instructions.md`：
   - 明确多标签特别规则
   - 看到新标签页时先切标签，不要重复 `click`
   - 同一会话应优先复用已有浏览器 session

#### 回归验证

- `tests/test_sys_ops.py` 增加验证：
  1. 不再向环境注入 `PLAYWRIGHT_CLI_SESSION`
  2. `playwright-cli open ...` 会被自动改写为 `playwright-cli -s=<session_id> open ...`
  3. 当 observation 呈现“新标签页已打开但 current 未切换”时，会自动追加 `tab-select` 提示
- 实测顺序验证通过：同一 `-s=session-id` 的 `open -> snapshot` 可以稳定复用同一浏览器 session

#### 教训

1. **不要默认本地小模型能从 `Open tabs + current page 不变` 自动推导出“下一步应切换标签页”**。
2. **对于外部浏览器工具，只靠 skill prompt 往往不够，必要时应直接增强 observation，使下一步动作更显式。**
3. **如果外部工具本身有 session 机制，必须和 agent session 显式绑定，但要先读清该工具版本对环境变量/参数的真实语义。**
4. **同名“session”能力在不同工具版本里不一定等价**：有的环境变量表示 session name，有的却会被解释为 endpoint / socket 路径。
5. **排查这类问题时，要先区分：是 memory 上下文坏了，还是 observation 虽在但对模型不够“可执行”。**
