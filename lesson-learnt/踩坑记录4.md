## -1. LLM 命名约定（贯穿全文档 + spec + commit message）

为避免歧义，本文及关联 spec / commit / AGENTS.md 用以下简称。**完整定义见 `docs/superpowers/specs/2026-06-12-post-compact-slim-system-prompt-design.md` §5.2**；这里是中文复述。

| 简称 | 含义 | 调用入口 | 跑的 prompt |
|------|------|----------|-------------|
| **LLM-A** | 用户最初的"读 50k 小说"那轮 chat 的 LLM | `/v1/agent/chat` turn 1 | `[system, user<50k 小说 + 总结请求>]` |
| **LLM-B** | auto-compact 触发的"压缩历史"专用 LLM | `CompactOrchestrator.run_compact`（不暴露 endpoint；被 `run_stream` 自动调） | 当前默认：只要有 `cache_first_body_messages` 就先尝试 cache-first `[上一轮真实 compactable LLM payload, user<自包含 compact-control at tail>]`；`source_token_budget` 只裁剪 reliable fallback；`reliable_position1` 仅在 `compact.reliable_fallback_enabled=true` 时启用，默认关闭 |
| **LLM-C** | compact 完成后回答用户 follow-up 的 LLM（"我觉得..."那条） | `/v1/agent/chat` turn 2（被 `run_stream` 调，走 coordinator_1 routing 之后） | 旧：`[system_full + tool_schemas + runtime_context + envelope + user_msg]`<br>新（slim）：`[system_slim - tool_schemas - runtime_context + envelope + user_msg]` |
| **LLM-D** | 用户与 LLM-C 的多轮后续 chat（同 session） | `/v1/agent/chat` turn 3+ | 完整 system（slim flag 已清，trap #28） |

**为什么这样命名**（用户原话，2026-06-12）：
> "1. LLM read the whole fiction of 40k tokens and then output something.
> 2. User send something without any explicit command of compact ...
> 3. Compact be triggered ...
> 4. ...
> 5. Send the full context with the previous whole history chats and compact instructions.
> 6. LLM output the summary ...
> 7. We deem the summary as a partial system prompt (appended to the current agent's) and then take it to a NEW context window ...
> 8. bind the user turn of "我觉得你把小说总结得不错呢" to the new context window of step 7. Then send the new context to sglang."

**LLM-A** = step 1（LLM 读 50k）；**LLM-B** = step 5-6（compact LLM）；**LLM-C** = step 7-8（新 context window 的 chat LLM）；**LLM-D** = 用户后续轮次。

**重要细节**：
- **LLM-B 早期跑 3+ min**（50k+ history 的 full prefill）曾被误认为不可压缩；2026-06-20 后的关键修正是：cache-first 必须始终先尝试，且必须复用上一轮真实 compactable LLM payload。曾经的“source 超预算就跳过 cache-first”是错误经验。真正的大根因之一是 agent/coordinator 切换导致 system prompt 从 token 0 开始变化，SGLang radix cache 无法复用后续大段文本。
- **LLM-C 跑 1+ min**（用户**不接受**）— 解法是 trap #28 slim system_prompt → 9 s。
- **LLM-C 走 coordinator_1 routing**（per user requirement trap #28）— routing 自身是另一次 LLM 调用（用 full system），不消耗 slim flag。

## 1. 用户原始报告

> *"I test the end-to-end in agent mode. While compacting, I notice that the sglang terminal showed `Decode batch, #running-req: 1, #full token: 41432, full token usage: 0.02, mamba num: 2, mamba usage: 0.00, cuda graph: True, gen throughput (token/s): 19.45, #queue-req: 0` for a long time, AND THAT IS NOT IN PREFILL STAGE. This is the most confusing stuff."*

> *"I strongly speculate that there are repeatitive (重复的) compact jobs in backend leading to the fact that the majority of time consumed are wasted, only the last compact (about 10% of duration) is working and shown in the compact UI."*

**关键症状 4 件套**：
1. SGLang 终端长时间显示 **`Decode batch`**（不是 Prefill batch）
2. `#running-req: 1`，即只有 1 个请求
3. **大量时间不出 content token**（compact UI 空白）
4. 即使是 decode 阶段，**`gen throughput` 也只有 19.45 token/s**（远低于正常的 80-150）

**用户的初始假设**：后端重复发了多个 compact LLM 调用，只有最后一个的输出被 UI 接收，前几个被丢弃。

## 2. 假说排查 + 否决

### 假说 1：后端发了多个 compact LLM 调用 — **否决**

审计全部 auto-compact 入口：

| 入口 | 文件:行 | 触发条件 |
|---|---|---|
| `run_stream` 内的 auto-compact | `agent_runner.py:4676-4678` | `_should_auto_compact_session()` True |
| cycle `_execute_steps` 预触发 | `cycle/executor.py:192-196` | share_context + i>0 + min_steps 节流通过 |
| `_generate_stream_response` chat 模式 | `api/chat.py:495-521` | `_should_auto_compact_chat()` True |
| `run_compact_for_session`（手动 /compact） | `agent_runner.py:4559-4634` / `api/compact.py:115` | 手动 |

**每一个**入口都创建**一个 transient `CompactOrchestrator`**（`agent_runner.py:4544-4549`），调用**一次** `chat_stream_async`，没有 retry 循环、没有并发。

**`_should_auto_compact_session`**（`agent_runner.py:4451-4477`）和 **`_should_auto_compact_chat`**（`api/chat.py:350-387`）都用 `compute_threshold + should_compact + TokenCounter` 的纯函数。Cycle 模式 + `min_steps=0` 下虽然会在 cycle 自身和 `run_stream` 各跑一次 tokenize，但**第一次** compact 把 `session.agent.memory.steps` 替换成 `[envelope]` 后，**第二次**的 tokenize 必然返回低值，**不会**触发第二次 LLM。

**结论**：假说 1 排除。每个 HTTP 请求最多 1 次 compact LLM 调用。

### 假说 2：后端 SSE 转发卡住、worker thread 死锁 — **否决**

`llm_service.py:1836-1893` 的 `chat_stream_async` 设计：
```python
def _worker():
    try:
        for chunk in generator:                  # 同步生成器在 worker 线程
            loop.call_soon_threadsafe(q.put_nowait, chunk)  # 跨线程投递
    except Exception as e:
        ...
    finally:
        loop.call_soon_threadsafe(q.put_nowait, None)
```

worker 线程是**纯 forwarder**（不做事），没有任何可能死锁或阻塞事件循环的地方。`call_soon_threadsafe` 非阻塞、asyncio.Queue 无限大。

`_stream_generate`（`llm_service.py:704-815`）的 `for chunk in response.iter_text()` 同步阻塞在 SGLang HTTP 响应的 socket read 上，**这是 SGLang 端在做事**（prefill / decode），不是 Python 端在卡。

### 假说 3：smolagents agent 状态泄漏、旧 memory 没被替换 — **否决**

- `_replace_agent_memory`（`agent_runner.py:4479-4513`）直接 `session.agent.memory.steps = [TaskStep(envelope)]`，替换成立。
- `session.has_run = True` 正确（防 smolagents reset，AGENTS.md trap #23）。
- 后续 `_run_coordinator_routing_stream` 重新读 `session.agent`，看到的就是新 memory。
- `LocalLLMModel`（`local_llm_model.py`）每次 `generate_stream` 都从 messages 重建 prompt，无缓存、无全局状态泄漏。
- `_activate_profile_agent` 在 compact 之后**不**被调用，所以不存在"用旧 agent 状态"的问题。

**结论**：假说 3 排除。`session.agent` Python 对象本身没换，但**它的 `memory.steps` 列表被原地替换**，smolagents 每次 `write_memory_to_messages()` 都读 `self.memory.steps`，所以下次 LLM 调用看到的就是新 memory。

### 假说 4：mamba state 分配失败、模型卡死 — **部分对，但不是 bug**

`mamba num: 2, mamba usage: 0.00` 看起来像 mamba 池没在工作。**实际**：mamba 池很大（被预分配），但只有 1 个 running request 占 2 个 slot，`2/大池` 比例四舍五入到 0.00。**这是数字显示的副作用，不是 bug**。

## 3. SGLang 终端日志的逐字段解读

这是最重要的章节。**每个字段的"看上去的"含义 vs "实际的"含义**：

| 字段 | 用户看到的值 | 误解 | 实际含义 |
|---|---|---|---|
| `Decode batch` | 一直显示 | "compact 没在 prefill 阶段" | SGLang 调度器每 `decode_log_interval` 个 forward 打印一次。chunked prefill 模式下，prefill 期间的每次 forward 也算"running batch 的一次 forward"，所以**显示成 Decode batch**。**不代表不在 prefill**。 |
| `#running-req: 1` | 1 | "只有 1 个请求" | 正确。当前 batch 只有 1 个 = compact LLM 调用。 |
| `#full token: 41432` | 41432 | "KV cache 用满了" | 这次请求当前占用的 attention KV slots。`41432 = ~40k`，**正是 compact prompt（整段 session memory + system + user）经过 tokenize 后的长度**。 |
| `full token usage: 0.02` | 2% | "KV cache 还很空" | **正确，但反过来说明 KV pool 总大小约 2M tokens**。`41432 / 2M = 2%`。**pool 巨大但被 mamba 抢走了大部分**。 |
| `mamba num: 2` | 2 | "mamba 几乎没用" | 1 个 running request 占 2 个 mamba slot（ping-pong 缓冲）。 |
| `mamba usage: 0.00` | 0% | "mamba 完全没工作" | `2 / 大池` 比例四舍五入到 0.00。 |
| `cuda graph: True` | True | "CUDA Graph 在跑，应该快" | 是的，但 prefill 阶段**走 cuda graph 之外的 fallback 路径**（prefill batch 不可重放，cuda graph 是给 decode 准备的）。 |
| `gen throughput: 19.45` | 19.45 tok/s | "极慢" | **正确**。但这 19.45 是过去若干 decode forward 的均值（包括 prefill 期间 0 token 的 forward），所以实际瞬时 throughput 在 prefill 阶段是 0。 |
| `#queue-req: 0` | 0 | "没有积压" | 正确。 |

**关键洞察**：
- SGLang 在 `enable_mixed_chunk=true`（默认）下，**chunked prefill 期间的每次 forward 都会被调度器 log 成"Decode batch"**。这是 SGLang 的实现细节，不是 status 错误。
- `full token: 41432` 实质是 compact prompt 的总长度（即 `_session_memory_to_messages` 把整段会话摊平后的 user 段），经过 SGLang 的 prompt tokenize 后的结果。

## 4. 真正的根因：SGLang mamba_full_memory_ratio=0.9 + 长 prompt 双重挤压

### 4.1 SGLang issue #25993 的背景

SGLang 自 PR #11679 起，`mamba_full_memory_ratio` 默认值从 0.2 改到 0.9。

代码计算逻辑（简化）：
```python
mamba_budget = total_rest_memory * ratio / (1 + ratio)
```

- `ratio = 0.9` → mamba 池 ≈ `0.9/1.9 ≈ 47.4%` 的 post-model 显存
- `ratio = 0.2` → mamba 池 ≈ `0.2/1.2 ≈ 16.7%` 的 post-model 显存

PR #11679 的意图是"给 mamba state 多留点空间，因为 mamba 池需要给 chunked prefill 的 checkpoint 也算配额"。但实测在长上下文（>32K）场景下，**KV cache 池被严重挤压**。SGLang 社区已经开 issue #25993 讨论这个权衡（https://github.com/sgl-project/sglang/issues/25993）。

### 4.2 用户的具体配置

`config/qwen3__5-config-infer.yaml` 里的相关键都是 `null`：
```yaml
sglang:
  mamba_full_memory_ratio: null   # ← SGLang 用默认 0.9
  max_mamba_cache_size: null
  chunked_prefill_size: null
```

加上模型是 35B GPTQ-Int4、`mem_fraction_static: 0.8`、`max_context_length: 242144`，结果就是：
- **mamba state pool 占 47% 剩余显存**（超大，但实际用得少 → `mamba usage: 0.00`）
- **attention KV pool 只剩 10% 剩余显存**（理论 `max_total_tokens` 很高，但实际可用容量被 mamba 抢走了大头）
- **compact prompt ~40K tokens**，要做 chunked prefill 5+ 次（`chunked_prefill_size: null` → SGLang 默认 8192）
- 每次 chunk prefill 在被挤压的 KV pool 里找空间，sglang 调度器反复推进，gen throughput 平均下来只有 19.45 tok/s

### 4.3 现象 → 根因的完整因果链

```
[1] Qwen3.5-35B-A3B 是 hybrid GDN (mamba+attention)
        │
        ▼
[2] SGLang mamba_full_memory_ratio 默认 0.9
        │   (本项目 YAML 写 null，触发 SGLang 默认值)
        │
        ▼
[3] mamba state pool 占 ~47% 剩余显存 → KV cache pool 显著缩水
        │
        ▼
[4] 用户 session memory 累计到 24k+ tokens → 触发 _should_auto_compact_session
        │
        ▼
[5] _run_compact_then_continue → CompactOrchestrator.run_compact
        │   _session_memory_to_messages 摊平整段对话到 user 段
        │   prompt 总长 ~40k tokens
        │
        ▼
[6] chat_stream_async → SGLang HTTP POST
        │   SGLang 看到 [system, user_40k] prompt
        │   触发 chunked prefill (5+ chunks, 每 chunk 8k)
        │
        ▼
[7] SGLang 调度器：每次 forward 都被打印成 "Decode batch"
        │   running batch seq_lens = 41432 (prefill 累计)
        │   gen throughput 平均下来只有 19.45 (因为 prefill 期间 0 token)
        │
        ▼
[8] 后端 _stream_generate 在 socket read 上阻塞（等 SGLang）
        │   不 yield → orchestrator 不 yield → 前端 compact UI 空白
        │
        ▼
[9] ~30s 后 prefill 完成，decode 开始，token 流出
        │   最后 10% 时长看到 compact UI 内容
```

**用户的"重复 compact job"误判来源**：长时间没看到 UI 出内容 → 以为系统在重做 → 最后 10% 终于看到 → 以为"只有最后那个是工作的"。

### 4.4 验证实验

**1 分钟就能验证的实验**：
1. 在 `config/qwen3__5-config-infer.yaml` 把 `mamba_full_memory_ratio: null` 改为 `mamba_full_memory_ratio: 0.5`
2. 重启 SGLang
3. 重跑 auto-compact

预期：compact UI 的"长时间空白期"从 90% 缩到 30% 以内。gen throughput 应该回到 50+。

**如果没改善**：进一步降 `chunked_prefill_size: 4096`，把 prefill 切得更碎但每次 forward 更轻。

## 5. "compact 是不是新建了 context window" 的设计 audit

用户在确认本节时强调：**"保证使用现有的上下文窗口进行压缩；而不是新建一个上下文窗口后，把需要被压缩的上下文复制到新的上下文窗口中 再进行压缩"**。

### 5.1 后端实际怎么走

`CompactOrchestrator.run_compact` 调用栈：
```
CompactOrchestrator.run_compact
  └─> LLMService.chat_stream_async         ← 单例，整个 app 唯一
        └─> SGLangProvider.generate(stream=True)   ← 同 SGLangProvider 实例
              └─> httpx.Client.post(http://SGLANG_HOST:PORT/v1/chat/completions)
```

- `LLMService` 是单例（`main.py` lifespan 启动一次）
- `SGLangProvider` 在 `LLMService._provider`，**所有** chat 路径（agent `run_stream`、chat.py auto-compact、手动 `/compact`）共享同一个 provider
- provider 的 `_stream_generate` 走 `http://SGLANG_HOST:SGLANG_PORT/v1/chat/completions`（SGLang 默认 port 30000）
- 整个项目**所有** LLM 调用都打到**同一个** SGLang GPU 进程，**同一份** KV cache pool + radix tree

### 5.2 我们**没**做哪些事

- ❌ 没有新建 `LLMService` / `provider` / 进程
- ❌ 没有把整段对话复制到一个独立的"compact context window" Python 对象
- ❌ 没有 bypass LLM service 自己重新实现 SGLang streaming
- ❌ 没有为 compact 调用单独的 GPU memory / 独立的 KV pool

### 5.3 re-prefill 的真实边界（2026-06-14 修订）

用户特别强调"不要新建 context window" — 这个目标**在概念层面是实现的**（compact 走的是同一条 SGLang 调用路径）。但 SGLang prefix cache 只在**请求 token 前缀 byte-equal**时复用，compact prompt 形状是否一致直接决定命中率。

旧 v1 的实际数据流是：

1. 之前 agent 的 N 个 turn 是 N 个独立的 OpenAI-style chat completion，**每个 turn 是一个 SGLang request**
2. N 个 turn 喂给 LLM 后，SGLang 的 KV cache 里存的是**每个 turn 自己的 prefix**
3. compact 把这 N 个 turn **拼成 1 个**单条 user message，发给 SGLang 做 1 个新的 request
4. 从 SGLang 视角，这是个**新 prefill**，prompt token 数 ≈ N 个 turn 的总长 ≈ 30k–40k
5. SGLang 的 radix tree 会尝试找公共前缀（system message 可能命中），但 user 段是连续大段，命中极少
6. **所以 GPU 必须 re-prefill 整段 user 段**（写入 KV cache）

**2026-06-20 修订**：这不是“完全无法优化”。如果 compact 请求保持上一轮真实 normal agent 请求的 system+history 前缀 byte-equal，只在 tail 追加内部 compact-control user message，SGLang radix cache 有机会跨请求命中该长前缀。若因为 prompt 形状、runtime_context、metadata filter、图片/工具历史编译、或 **coordinator_1 / basic_agent / coordinator_2 切换导致 system prompt 变化**，则从 token 0 起就分叉，后续大段工具返回文本也不能复用。

因此当前原则是三层：
- **第一优先**：cache-first prompt shape，最大化上一轮真实 normal request 与 compact request 的前缀等同性。
- **不要用 source budget 挡住 cache-first**：`source_token_budget` 不是 cache-first 准入门槛；超大 source 也必须先尝试 cache-first，否则 radix cache 复用没有意义。
- **可靠兜底是显式开关**：budgeted reliable fallback 只在 `compact.reliable_fallback_enabled=true` 时启用；项目默认关闭，让 cache-first 失败直接暴露，便于定位 prefix/cache/prompt 问题。

### 5.4 已落地的 audit 注释

为了防止未来工程师也踩同样的认知坑，已经在 `backend/compact/orchestrator.py:101` 附近添加了 ~35 行的 "Context reuse vs. new-context-window design audit" 注释，完整记录：
- 调用栈复用关系
- 明确"没做"的事
- 不可避免的 re-prefill 是为什么
- 真正影响 latency 的是 SGLang 长 prompt prefill + 可能被 mamba 池挤压的 KV cache 容量

### 5.5 v2 修复后（turn-shape prefix cache 复用，2026-06-11；2026-06-14 修订）

v1 的 prompt 形态（`build_compact_messages` 输出 `[system(compact 指令), user<整段历史>]`）导致 SGLang radix tree 在 root 就分叉——compact 调用与之前 chat 调用的 token 序列完全不同，**整段 prompt 都得重新 prefill**。

v2 最初（`build_compact_messages_v2` in `backend/compact/prompt_builder.py`）改成 turn-shape：

```
[compact LLM 调用的 messages 列表]
  [system (来自 agent 原始 memory.system_prompt)]   ← 1:1 复用之前 chat 调用的 system
  [user, assistant, user, assistant, ...]            ← 1:1 复用之前 chat 调用的 history turns
  [user <compact-instr>]                              ← 唯一分叉点 (~150-300 tokens)
```

- v2 初版的前 N-1 条 messages 与之前 chat 调用的 messages **byte-equal**（前提：调用方用 `session.agent.write_memory_to_messages()` 作为 agent 模式 source，用 `filtered` 作为 chat 模式 source）。
- 理想情况下 SGLang radix tree 在前 N-1 个 token 上匹配，复用对应的 attention KV 和 mamba state。
- 但该形状在 40k 上下文中暴露了 lost-in-the-middle：tail compact instruction 容易被忽略。
- 2026-06-20 当前默认快路径不是 `build_compact_messages_v2` 的 position-1 shape，而是无预算准入门槛的 `cache_first_tail_with_fallback`：只要有 cache-first source，就尝试 `[上一轮真实 compactable LLM payload, tail compact-control]`。`source_token_budget` 只裁剪 reliable fallback。reliable position-1 compact system 默认关闭，只有 `compact.reliable_fallback_enabled=true` 时才作为 correctness fallback。
- 完整 spec：`docs/superpowers/specs/2026-06-11-v2-compact-prompt-turn-shape-design.md`
- 完整 plan：`docs/superpowers/plans/2026-06-11-v2-compact-prompt-turn-shape-plan.md`
- 关键测试：`tests/test_compact_prompt_builder_v2_template_compat.py::test_v2_passes_qwen3_chat_template`（用真实 Qwen3 chat_template 渲染 v2 输出）

### 5.6 reliable fallback: instruction moved to position 1 (lost-in-the-middle at 40k context, 2026-06-11)

§5.5 的 v2 修复（turn-shape prefix cache 复用）解决了 SGLang 端 KV 命中问题，但暴露了一个**新**的 LLM 端问题：**lost-in-the-middle effect**。

**症状**：在 40k+ token 长上下文跑 `/tmp/fixed_compact_payload.json`（Chinese sci-fi Q&A 对话），LLM 输出了中文自由 markdown 总结：

```
### 对话内容总结
#### 1. 对话概况
[... 5-section 中文自由格式 markdown ...]
```

**完全忽略**了 YAML `main_prompt` 规定的 `<analysis>` + 9-section `<summary>` English 格式。SGLang 端 KV 命中正常（radix tree 复用前 N-1 个 token），但 LLM 在 40k 上下文里对**末尾 instruction** 的 attention 接近 0。

**根因**：lost-in-the-middle effect — LLM 注意力分布呈"两端强、中间弱"。40k token 上下文里，末尾追加的 instruction 收到的 attention 极弱，模型既没读到 instruction 的格式约束，也没读到 LANGUAGE LOCK 的英文要求，被对话主体的中文"吸过去"了。

**修复**（position-1 amendment）：把 instruction 从**末尾**挪到 **position 1**（system 之后第一条 user）。LLM 在 attention 强的头部看到 instruction，在 attention 强的尾部看到对话尾段——**两头都强**。2026-06-14 后它保留为 reliable fallback，而不是默认最快路径。

新 turn shape：

```
[compact LLM 调用的 messages 列表]
  [system (来自 agent 原始 memory.system_prompt)]   ← 1:1 复用 (byte-equal prefix cache anchor)
  [user <compact-instr>]                             ← 位置 1（**新位置**，lost-in-the-middle 修复）
  [user, assistant, user, assistant, ...]            ← 1:1 复用之前 chat 调用的 history turns
```

- `final[0]` = `body_messages[0]`（system，byte-equal）
- `final[1]` = 新插入的 user 消息（compact-instr + optional custom instructions）
- `final[2:]` = `body_messages[1:]`（byte-equal，history turns）
- `len(final) == len(body_messages) + 1`

**Trade-off**：position-1 在 index 1 处分叉，天然破坏长前缀 cache hit，因此只适合作为 correctness fallback。默认快路径应使用 tail compact-control + validation/fallback，而不是把 position-1 当作性能路径。

**YAML 措辞加固**（`config/config-agent-prompts.yaml::compaction::compact_user_instruction`）：
- **LANGUAGE LOCK**：写英文，无视对话语言
- **STRUCTURE LOCK**：当前为 summary-only，严格单个 9-section `<summary>`，禁止 reasoning/analysis block、`### / ####` Chinese headers / 自由分节 / `<summary>` 之前的前缀

**关联**：
- AGENTS.md trap #26（修订）：v2 builder 总体规则，承认 position-1 修订
- AGENTS.md trap #27（新增）：position-1 修订的 lost-in-the-middle 动因与 trade-off
- 完整 spec `§10` 修订：`docs/superpowers/specs/2026-06-11-v2-compact-prompt-turn-shape-design.md#10-position-1-修订`
- 关键回归测试（任一失败即视为 v2 设计破坏）：
  - `tests/test_compact_prompt_builder_v2.py::test_instruction_takes_precedence_over_tail_with_long_history`（60 消息 body，instruction 必须在 index 1）
  - `tests/test_compact_prompt_builder_v2.py::test_final_message_is_original_last_body_message`（末尾 = 最后一条原始 body 消息，**不是** instruction）
  - `tests/test_compact_prompt_builder_v2.py::test_history_after_instruction_is_byte_equal_to_body_tail`（`final[2:]` 与 `body_messages[1:]` byte-equal）
  - `tests/test_compact_prompt_builder_v2.py::test_system_message_preserved_byte_equal_at_index_zero`（`final[0]` 与 `body_messages[0]` byte-equal）
  - `tests/test_compact_prompt_builder_v2.py::test_language_lock_wording_present_in_instruction_content`（YAML 必须含 `LANGUAGE LOCK` + `English`）
  - `tests/test_compact_prompt_builder_v2.py::test_structure_lock_contains_all_nine_section_names`（YAML 必须含 `STRUCTURE LOCK` + 9 个 section 名称 + `<summary>`，且不能要求 `<analysis>`）

### 5.7 Post-compact slim system_prompt via ContextVar (2026-06-12, LLM-C 1+ min → 9 s)

**症状**：v2 compact 跑完后（3-4 min），用户发 follow-up "我觉得你把小说总结得不错呢"，LLM-C 仍然 1+ min 才有响应。用户预期 1 分钟内（"according to my experience"）。Compact LLM-A 3 min 是 prefill 物理限制，**可接受**；但 LLM-C 1+ min **不可接受**。

#### 5.7.1 LLM-C 慢的真实原因

LLM-C prefill 不是"3-5k tokens"（用户心理模型），而是 **5-10k+ tokens**：

| Component | Tokens | 备注 |
|---|---|---|
| `system_prompt`（含 tool schemas + agent-contract preamble） | 2-5k | session-pinned；若后续请求 token 前缀 byte-equal，SGLang radix cache 有机会复用 |
| `runtime_context`（时间 / 天气 / session info） | 50-200 | 每条 chat 都注入（`_inject_runtime_context`） |
| `TaskStep(task=envelope)`（preface + summary + suffix） | 2-3k | LLM-A 产出 |
| `coordinator_1` routing call（**额外一次 LLM 调用**） | 5-7k prefill | `_run_coordinator_routing_stream`，timeout 20s |
| new user msg | 10-50 | |

实测 1+ min（`session.has_run=True` 后第一条 chat 路由 + LLM-C 串行）。

#### 5.7.2 SGLang prefix cache 真实行为（2026-06-14 修订）

**修订结论**：旧说法“跨请求 0% cache / byte-equal 是伪命题”不准确。SGLang 的 radix cache 可以在同一服务进程内跨 OpenAI-style requests 复用**相同 token 前缀**。本项目用本地 smoke test 验证过：连续两次完全相同的小请求，第二次 latency 明显下降。

但是有 3 个限制：
- 只有**从 token 0 开始的公共前缀**能命中；中间插入 compact instruction、替换 system、注入不同 runtime_context、裁剪 source、图片重排等都会让后续大段历史不再是 prefix。agent 模式最危险的实际根因是 new-turn reset 到 `coordinator_1` 后再 compact：上一轮长文本由 `basic_agent` / `coordinator_2` 消费，但 compact source 变成 `coordinator_1` system prompt，prefix 从 token 0 起变化。
- SGLang terminal 的 `#cached-token` 只有在启动时加 `--enable-cache-report` 后，OpenAI usage 才会返回 `prompt_tokens_details.cached_tokens`，backend `[compact-diag]` 才能可靠显示。
- `source_token_budget` 只限制 reliable fallback source，不限制 cache-first 第一尝试。若想强制观察 cache-first 行为，应保持 `compact.reliable_fallback_enabled=false`。

因此当前判断方式：
- 若 `shape=cache_first_tail` 且 `cached_tokens_sglang` 高、SGLang terminal `#cached-token` 高：prefix cache 命中，最佳。
- 若 `shape=cache_first_tail` 且 `cached-token: 0`：优先查 cache-first source 是否来自 `last_compactable_llm_messages`，以及 system prompt 是否仍是上一轮长文本 agent 的 system。
- 若 `shape=reliable_position1` + `fallback_used=true`：只有在 `compact.reliable_fallback_enabled=true` 时才应出现；说明 cache-first validation 失败后进入 correctness fallback，查 `validation_reason`。
- 若 `compact_failed` 且 UI card 消失：这是当前前端投影行为，`compact_failed` 会删除 compact card 并回滚 pre-compact 标记；查 attempt=1 的 `validation_reason`。

#### 5.7.3 解法：slim system_prompt + ContextVar

**3 个改动**：

1. **Session flag** `first_post_compact_turn: bool`，在 `_replace_agent_memory`（line 4565）末尾设 `True`。
2. **`_slim_next_llm_call` ContextVar**（`backend/agent/local_llm_model.py:38`）：
   - `run_stream` 在 `_run_coordinator_routing_stream` **返回 route 之后**（line 4805-4807）`set(True)`，标记下一次 LLM 调用走 slim。
   - `LocalLLMModel._read_slim_flag`（line 170）`get()` 时消费：clear ContextVar + clear session flag，返回 True。
   - `_read_slim_flag` 关键设计：**session flag 单独不足以触发 slim**。routing 调用也走 `LocalLLMModel.__call__`，如果只看 session flag 会让 routing 也 slim，违反"保留 coordinator_1 routing"用户硬性要求。
3. **Slim 路径**：
   - `llm_service._inject_runtime_context`（`llm_service.py:80-92`）在 `slim=True` 时**直接 return messages**（跳过 runtime_context 注入）。
   - `LocalLLMModel.generate` / `generate_stream` 在 slim 时传 `tools=None`（剥 tool JSON schemas）。

#### 5.7.4 关键 gotcha：ContextVar 不跨 threading.Thread 传播

**第一次 E2E 失败**：`[llm-c-diag] slim_via_contextvar=False session_flag=True` —— ContextVar 在 worker thread 是默认 False，**没继承主线程 set 的值**。

**根因**：`_run_coordinator_routing_stream`、`_run_basic_stream`、`run_answer_now_stream` 三个地方都用 `threading.Thread(target=_stream_worker, daemon=True)` 跑 LLM 流。Python `ContextVar` **per-thread + per-async-task**，新线程**不继承**父线程的 ContextVar。

**修复**：所有 3 个地方用 `contextvars.copy_context().run(_stream_worker)` 包装：
```python
ctx = contextvars.copy_context()
stream_thread = threading.Thread(target=ctx.run, args=(_stream_worker,), daemon=True)
stream_thread.start()
```

**E2E 验证（修后）**：
```
[post-compact-diag] session_id=... first_post_compact_turn=True
[llm-c-diag] slim_consume slim_via_contextvar=False session_flag=True  ← coordinator_1 routing（slim=False，spec §2.1）
[llm-c-diag] slim_consume slim_via_contextvar=True  session_flag=True  ← LLM-C（slim=True）
```

- 第一次 `llm-c-diag`（routing）`slim_via_contextvar=False` — **保留 routing full system** ✓
- 第二次 `llm-c-diag`（LLM-C）`slim_via_contextvar=True` — **slim path 生效** ✓

|---|---|---|
| Turn 1: 50k sci-fi (LLM-A 读小说) | 4:37 | 4:37（不变，prefill 物理限制） |
| **Turn 2: "我觉得..." (routing + LLM-C)** | **1+ min timeout** | **9.18 s** ✓ |

#### 5.7.6 LLM-B compact 低延迟栈（2026-06-14）

2026-06-14 用户继续 E2E 发现：启用 cache-first 后体感仍慢，SGLang terminal 仍显示 compact prefill `#cached-token: 0`，`#new-token` 约 39k。后续修复不是单点，而是一组互相兜底的措施：

| 措施 | 作用 | 文件 |
|------|------|------|
| `prompt_shape: cache_first_tail_with_fallback` + `prompt_control_enabled: true` | normal chat/agent system prompt 预先包含稳定 compact-control 规则；compact 请求只在 tail 追加内部 user instruction，最大化 prefix byte-equal | `config/config-misc.yaml`, `compact/prompt_control.py`, `compact/prompt_plan.py` |
| `session.last_compactable_llm_messages` | agent compact cache-first 优先复用上一轮成功的非 `coordinator_1` normal LLM 调用的真实 payload（`actual llm_messages + assistant output`），避免 new-turn reset 到 `coordinator_1` 后 system prompt 变化破坏 prefix cache | `local_llm_model.py`, `agent_runner.py` |
| cache-first tail 指令自包含 | 不能只写 sentinel + “same 9 sections required by normal compact instruction”；cache-first 保留的是 normal agent system，不是 compact system。tail user instruction 必须自己列出 9 sections 和 `<summary>` 约束 | `compact/prompt_control.py`, `config-agent-prompts.yaml` |
| strict validation + optional reliable fallback | cache-first 输出若为空、过短、含 routing XML/tool markers 或缺 9 sections，会失败；只有 `compact.reliable_fallback_enabled=true` 时才 fallback 到 reliable position-1。项目默认 false，失败直接暴露 | `compact/validation.py`, `compact/orchestrator.py`, `config/config-misc.yaml` |
| `extra_body.chat_template_kwargs.enable_thinking: false` | compact 是内部 summarization，不需要 Qwen thinking；关闭后减少 reasoning decode token | `config/config-misc.yaml`, `llm_service.py:chat_stream_async`, `compact/orchestrator.py` |
| summary-only prompt | 不再要求 `<analysis>` block，只输出单个 `<summary>`，减少可见输出 token | `config/config-agent-prompts.yaml`, `tests/test_compact_prompt_speed_contract.py` |
| `max_summary_tokens` 降到交互型上限 | 防止 compact 在 summary decode 阶段跑 12k/20k tokens | `config/config-misc.yaml`, `CompactConfig` |
| `source_token_budget` | reliable fallback / cache miss latency 兜底时裁剪 compact source：保留 system、已有 compact summary、最近 tail，避免 fallback 再次 full prefill 39k+ | `compact/source_budget.py`, `compact/orchestrator.py` |
| `schedule_policy: lpm` | SGLang 调度层按 longest-prefix-match，提升同服务进程内 radix cache 命中机会 | `config/qwen3__5-config-infer.yaml`, `scripts/1_start_sglang.sh` |
| `enable_cache_report: true` + `--enable-cache-report` | 让 OpenAI usage 返回 `prompt_tokens_details.cached_tokens`，backend `[compact-diag]` 能和 SGLang terminal 对齐 | `config/qwen3__5-config-infer.yaml`, `backend/config.py`, `scripts/1_start_sglang.sh` |

**关于“compact 前是否清洗 context”**：
- Chat 模式：`api/chat.py` 先跑 `filter_messages_for_llm()`。只有前端发送 `metadata.pre_compact` / `metadata.compact_summary` 时，才会把 pre-compact 历史删掉并替换成 summary envelope；无 metadata 时是 no-op。之后 `escape_user_messages()` 只防 sentinel 注入，`ensure_compact_control_system_message()` 只给 system 加稳定控制 clause。
- Agent 模式：`SmartToolCallingAgent.write_memory_to_messages()` 本来就是 deterministic compiler。历史轮次会剥离旧图片、把旧工具轨迹压成文本、提取写/改文件工具产物、去掉成功回执；当前轮 ActionStep 保留 `tool_calls`/observations 配对，只剥 `observations_images`。这不是 compact 专属清洗，而是 normal agent 调用和 compact source 共用的消息形状来源。
- Compact orchestrator：`cache_first_tail` 第一尝试**不得**先跑 `trim_messages_to_token_budget()`。这一步会破坏与 normal request 的完整前缀等同性，因此不属于 prefix-cache 优化。
- 补充硬约束：`source_token_budget` 不能作用于 `cache_first_tail` 的第一尝试，也不能作为 cache-first 准入门槛。cache-first 的目标是最大化与上一轮真实 normal prompt 的前缀等同性；在第一尝试前裁剪或跳过都会主动放弃 radix cache 复用。预算裁剪只属于 reliable fallback。

**Hard rule for future AI**：不要擅自改 `compact.performance_ratio`。这是用户用于 E2E 触发阈值实验的旋钮；除非用户明确要求，否则不要为了“更早 compact”改 YAML ratio。加速 compact 应优先从 prompt shape、thinking off、summary-only、SGLang launch args、source budget 这些路径做。

**如何判断当前瓶颈**：
- `shape=cache_first_tail` + `cached_tokens_sglang` 高 + terminal `#cached-token` 高：prefix cache 命中。
- `shape=reliable_position1` 或 `fallback_used=true`：只有 `reliable_fallback_enabled=true` 时才应出现；cache-first validation 失败，正在走 correctness fallback；查 `validation_reason`。
- `compact_failed` + 无 UI compact card：fallback 默认关闭，cache-first 失败后前端删除 compact card；查 `attempt=1 shape=cache_first_tail validation_reason=...`。
- `#new-token` 又回到 30k/40k：优先查 `[compact-cache-first-source] origin=last_compactable_llm_messages` 是否出现、`agent_name` 是否为上一轮长文本 agent，而不是 `coordinator_1`。

### 5.7.7 2026-06-20 最终 cache-first 根因修正：system prompt 漂移 + tail 指令不自包含

这轮 E2E 的真实问题不是“source 太大所以应该跳过 cache-first”，而是两类 prefix/prompt 一致性问题叠加：

1. **变化的 system prompt 破坏 radix cache**：上一轮长文本通常由 `basic_agent` 或 `coordinator_2` 消费；下一轮 auto-compact 旧流程先 `prepare_session_for_new_turn()` reset 到 `coordinator_1`，再从当前 agent memory 重建 compact source。SGLang 只从 token 0 匹配 prefix，`basic_agent system` → `coordinator_1 system` 会让后续大段工具 Observation 也无法复用。修复是 `LocalLLMModel` 在成功的非 `coordinator_1`、非 slim normal LLM 调用后保存 `session.last_compactable_llm_messages = actual llm_messages + assistant output`；compact cache-first 优先用它，compact 成功后清空。
2. **cache-first tail user instruction 必须自包含**：旧版 `compact_control_user_instruction` 只追加 sentinel 和“same 9 sections required by normal compact instruction”。但 cache-first 保留的是 normal agent system prompt，不是 compact 专用 system prompt，因此模型可能根本没看到 N.1-N.9 细节，validation 失败后（fallback 默认关闭时）表现为没有 compact UI card、memory 不替换。修复是在 `build_compact_control_instruction()` 中直接列出完整 `<summary>` + 9 sections 约束。

最终规则：cache-first 不因 source size 被跳过；`source_token_budget` 只裁剪 reliable fallback；`reliable_position1` 默认关闭；失败时看 `attempt=1 shape=cache_first_tail validation_reason=...`。

### 5.8 Multi-compact chain preservation — PRIOR SUMMARY RULE（2026-06-12）

#### 5.8.1 症状

`session.agent.memory.steps` 第一次 compact 后变成 `[TaskStep(envelope)]`。后续用户继续聊天，session 长起来触发 **2nd** auto-compact。但 2nd compact 的 LLM-B **没有** 1st summary 的"保留 / drop"指令——LLM 自由 drop 1st summary 里的关键事实（如 "project uses FastAPI"），导致 multi-compact chain 上**早期信息永久丢失**。

#### 5.8.2 数据流审计（写代码前先做）

| 阶段 | 行为 | 文件:行 |
|------|------|---------|
| 1st compact 完 | `memory.steps = [TaskStep(envelope)]` | `agent_runner.py:4573` |
| 用户继续聊天 | `memory.steps = [TaskStep(envelope), TaskStep(user2), ActionStep, ...]` | smolagents 自动追加 |
| 2nd compact 触发 | `write_memory_to_messages()` 调 envelope TaskStep 的 `to_messages()` | `agent_runner.py:4623` |
| envelope `to_messages()` | **强制**渲染为 `role=USER` + 前缀 `"New task:\n"` | smolagents `memory.py:191-196` |
| 2nd compact LLM input | `[system, user<1st envelope>, user<2nd user msg>, ...]` | — |

**关键发现**：1st envelope **是** 2nd compact LLM input 的一部分，**但**被 smolagents 强制加了 `"New task:\n"` 前缀——LLM 看到的是 `"New task: This session is being continued from a previous conversation..."`，**没有 schema marker** 告诉它这是 summary 而不是真的新任务。

#### 5.8.3 lossy-on-lossy 风险

- **没有** "treat previous summary as source of truth" 指令 → LLM 自由 drop
- 9-section 的 "Current Work" / "Optional Next Step" 段（YAML `:440-442`）**明确偏向 recency**："do not start on tangential requests or really old requests that were already completed without confirming with the user first" → 1st summary 的旧事被鼓励 drop
- 2nd `_replace_agent_memory` 替换 `memory.steps = [TaskStep(2nd_envelope)]` → 1st envelope 从 LLM 可见 memory 永久消失（保留在 `compaction_archive` 但**不**被 read）
- "compaction_archive" 路径**不**是 fallback 来恢复 lost info（AGENTS.md trap #16 已明确为纯审计）

#### 5.8.4 解法 — PRIOR SUMMARY RULE

在 `config/config-agent-prompts.yaml::compaction::compact_user_instruction` 的 `**CONTENT RULE**` 段后加 **PRIOR SUMMARY RULE** 段。规则如下：

1. **保留 key facts** 在 4 个 9-section slots（`Key Technical Concepts` / `Files and Code Sections` / `Errors and fixes` / `Primary Request and Intent`），除非事实错误
2. **Migrate 已完成工作到 "Problem Solving"**（**不是**单纯 drop！这是 2026-06-12 用户澄清后的强约束）：
   1st summary 列在 "Pending Tasks" / "Current Work" / "Optional Next Step" 但后续 turns 已完成的任务，**必须**做这 3 件事：
   (a) **从 Pending / Optional Next Step 删除**（这 2 个 slot 只反映*当前*未完成项）
   (b) **在 section 5 "Problem Solving" 加一行 entry**，格式如 `Refactored foo via edit_file (completed in turns N-M)` —— 这是"该任务已完成"在 multi-compact 之间的**唯一持久记录**，下一轮 compact 在 Problem Solving 里读到它就不会重做
   (c) **更新 "Current Work"** 反映**下一个** in-progress 任务（或 "Awaiting user follow-up"）
3. **更新 user/assistant 历史**：合并 pre-summary + post-summary 全部 user messages（按时间序），不要默默 drop pre-summary
4. **保留 1st summary 提到但 post-summary turns 未矛盾的事实**（如 "project uses FastAPI"）原样

**强调永久性**：新 summary 是 pre-summary context 保留的**唯一**地方，LLM-C 只看新 summary，没捕获的事实**永久丢失**。

### 5.9 Bug 1 / 1.1 / 1.2: 终端重复 markdown 叠加（2026-06-12 / 2026-06-13）

#### 5.9.1 用户报告

> 后端 terminal 中，重复打印了多遍 LLM 的输出。

实际症状：用户测"压缩后是否真的收到摘要"的 prompt，LLM 跑进 50 步循环（post-slim 引起的），terminal 出现 50 份相同内容的快照（每份末尾多几行"让我如实回答这个问题" / "你说得对" / 等等）。

#### 5.9.2 根因

`_step_stream` 每次被 smolagents 主循环调用（一次 agent turn 可能 50+ steps）会创建一个新的 `with Live(...) as live:` 块。Rich 在 `with` 块退出时**冻结**当前 markdown 到 terminal 上一行 —— 50 steps = 50 份逐次增长的同一份 response 在 terminal 叠加。

直接代码路径：`backend/agent/agent_runner.py:1837`（修复前）的 `with Live("", console=self.logger.console, vertical_overflow="visible") as live:` 块在每次 `_step_stream` 调用时新建并关闭，关闭时 Rich 冻结当前内容到 terminal。

#### 5.9.3 第一版修复 — Live 块提升到 run 级别，删除 local fallback

1. `SmartToolCallingAgent.__init__` 加 `self._cli_live: Optional[Live] = None`
2. `_run_basic_stream` 在 `agent.run()` 之前创建唯一 Live 块赋给 `agent._cli_live`（coordinator_1 routing 跳过）
3. `_step_stream` 只在 `self._cli_live` 存在时复用 shared Live（无 `with` 块，只调 `shared_live.update()`）；**无 parent `_cli_live` 时不创建本地 Live，只 yield stream deltas**
4. `_run_basic_stream` 在 agent.run 结束（无论正常 / 异常）后用 `try/finally` 关闭 Live 并清 `agent._cli_live = None`

第一版 Bug 1 修复仍保留“无 parent Live 时建本地 Live”的 fallback。用户 2026-06-13 实测发现 terminal 仍有重复输出：直接 `_step_stream` 路径或未被 `_run_basic_stream` parent 包裹的路径仍会每 step 创建/关闭一个 `Live`，所以 fallback 本身就是回归点。

#### 5.9.3.1 第二版仍不够 — run-level Live 也会被 backend logs 打断

用户 2026-06-13 再次报告 backend terminal 仍重复：

```text
... Live 流式显示 reasoning/content ...
2026-06-13 ... generate_stream 完成 ...
Final answer: ...
[Step 1: ...]
... 完整 reasoning/content 再出现一次 ...
```

这说明问题不只是“每 step 一个 Live”。即使只有 run-level Live，backend 普通 logger（`backend.agent.local_llm_model` / `backend.agent.agent_runner`）和 smolagents `Final answer` / `Monitor.update_metrics` 在 Live 活跃期间插入输出，也会让 Rich 重新 render / 退出时冻结最终画面，terminal scrollback 里仍留下“流式内容 + 日志 + 最终完整内容”的重复。

#### 5.9.3.2 最终修复 — backend SSE path 不创建 Live

最终 invariant：**Web UI SSE 流式与 backend terminal rendering 解耦**。

1. `_run_basic_stream` 是 backend SSE/web path，只负责把 delta 推给浏览器；**不得创建 `rich.Live`**。
2. `SmartToolCallingAgent.__init__` 保留 `self._cli_live = None`，只作为未来专用 CLI runner 的 parent Live hook。
3. `_step_stream` 只在 `self._cli_live` 已由外部 parent 设置时复用它；无 parent 时只 yield `ChatMessageStreamDelta`，不做 terminal rendering。
4. `coordinator_1` routing 路径同样不创建 Live。

这样 backend terminal 只保留普通日志 / smolagents final step 输出，不再 token 级刷新模型正文；Web UI 仍通过 SSE 真流式显示。

#### 5.9.4 Hard contract

`tests/test_agent_session_context.py` 的 hard contracts：
- `test_run_basic_stream_does_not_create_backend_cli_live` —— backend SSE basic_agent 路径不构造 `Live`，`agent._cli_live` 保持 None
- `test_run_basic_stream_skips_live_for_coordinator_routing` —— `_cli_stream_source="coordinator_1"` 时 Live 构造计数 = 0
- `test_run_basic_stream_releases_live_on_agent_exception` —— `agent.run()` 抛异常时 backend SSE 仍不构造 `Live`
- `test_run_basic_stream_streams_sse_without_backend_live` —— 不创建 backend Live 不影响 SSE content 输出
- `test_step_stream_without_parent_live_does_not_create_per_step_live` —— 直接调用 `_step_stream` 且无 parent `_cli_live` 时 Live 构造计数 = 0

#### 5.9.5 回归风险

未来 refactor 若在 `_run_basic_stream` 重新创建 Live、把 Live 创建挪回 `_step_stream` 内部、保留 local fallback、或 routing 路径也开始创建 Live，bug 会**静默**复现（用户看到 terminal 异常但不知道是哪个 commit 引入的）。**关键 invariant**：backend SSE path 不做 terminal Live rendering；`_step_stream` 不能自己创建 `Live`；只有未来专用 CLI runner 可以显式设置 parent `_cli_live`。

这是一个涉及多个技术细节的问题集，包括配置参数、版本兼容性、硬件适配和部署流程。为了确保答案的准确性和时效性，我需要切换到 basic_agent 来查阅 ms-swift 的最新官方文档和相关技术资料。

[{"id":"call_0","type":"agent","function":{"name":"switch_agent","arguments":"basic_agent"}}]
```

#### 5.11.2 根因

`frontend/src/app/page.tsx:511` 和 `frontend/src/app/vision/page.tsx:491` 的 `onStep` (dispatch step) 和 `onTimelineEvent` (agent_switched) handler 之前用 `!agentRun.executionAssistantMessageId` guard：
```typescript
if (step.step_type === 'dispatch' && step.dispatch_kind === 'secondary_handoff') {
  if (!agentRun.executionAssistantMessageId) {  // ← Bug: 只在第一次开新 bubble
    setMessages((prev) => [...]);
  }
}
```

直接链路：
1. `getActiveTrackedAssistantMessageId` (`frontend/src/lib/dispatch-message.ts:367`) 优先级 `executionAssistantMessageId` > `projectedAssistantMessageIds[last]` > `assistantMessageId`
2. `backend/agent/agent_runner.py:3578` `use_chat_bubble_timeline = session.current_agent_name == "coordinator_2"` —— basic_agent 运行时是 False
3. basic_agent 走 `agent_step: thought` 路径（`backend/agent/agent_runner.py:3966-3974`）—— **没有** `message_id`，**不**创建新 projected bubble
4. 因此 basic_agent text 落到 active bubble = `executionAssistantMessageId` 那个 execution buffer
5. 第二次 handoff 没换 `executionAssistantMessageId`，所以 basic_agent 进了 coordinator_2 的 buffer

#### 5.11.3 第一版修复（错误过度）

第一版修复只解决了一半：确实让第二次 handoff 不再复用旧 execution buffer，但把 `onStep` (dispatch step) 和 `onTimelineEvent` (`agent_switched`) 两条路径都改成“每次都开新 bubble”。

backend 事件顺序是：`dispatch_step` → `agent_switched`。所以同一个 handoff 被开了两个 bubble：
- 第一个由 dispatch step 创建，只显示 dispatch/“思考中...”
- 第二个由 `agent_switched` 创建，basic_agent 文本最终流式输出在这个第二个 bubble

这就是用户 2026-06-13 报告的“修了一半”：agent 切换成功了，但多出一个一直思考中的空 bubble。

#### 5.11.4 正确修复 — dispatch 开，agent_switched 消费/兜底

(1) `frontend/src/app/page.tsx` / `vision/page.tsx` 的 `onStep` handler 收到 `step_type === 'dispatch' && dispatch_kind === 'secondary_handoff'` 时开新 execution bubble，并标记 pending：
```typescript
const previousExecutionId = agentRun.executionAssistantMessageId;
const newExecutionId = generateId();
agentRun.executionAssistantMessageId = newExecutionId;
agentRun.secondaryHandoffExecutionBubblePendingAgentSwitch = true;
setMessages((prev) => {
  const retracted = retractTrackedAssistantTailText(prev, ...);
  const retired = previousExecutionId
    ? finalizeTrackedAssistantMessage(retracted, previousExecutionId)  // ← 标 isStreaming: false
    : retracted;
  return [...retired, { id: newExecutionId, ..., bubbleKind: 'execution' }];
});
```

(2) 随后的 `agent_switched` from `coordinator_2` 若看到 `agentRun.secondaryHandoffExecutionBubblePendingAgentSwitch === true`，只消费该 flag 并做幂等 tail retraction，不再 `generateId()`：
```typescript
if (agentRun.secondaryHandoffExecutionBubblePendingAgentSwitch) {
  agentRun.secondaryHandoffExecutionBubblePendingAgentSwitch = false;
  setMessages((prev) => retractTrackedAssistantTailText(prev, ...));
} else {
  // fallback: 若没有 dispatch step 先到，agent_switched 自己开 bubble
  const newExecutionId = generateId();
  ...
}
```

(3) `frontend/src/app/vision/page.tsx` 同步改（AGENTS.md trap #1 同步规则）。

关键设计选择：**一个 logical handoff 只允许一个 bubble owner**。dispatch step 是主路径 owner；`agent_switched` 只是确认/兜底。

#### 5.11.5 Hard contract

`frontend/src/lib/timeline-projection.test.mts` 的 hard contracts：
- `'Bug 3 regression: text and vision pages open a fresh execution bubble for EVERY secondary handoff, not just the first'` —— 锁 (a) `if (step.step_type === 'dispatch' && step.dispatch_kind === 'secondary_handoff') { if (!agentRun.executionAssistantMessageId)` 不存在（用 `\s*` 紧贴 brace 排除 comment 中的字符串）；(b) `previousExecutionId` + `finalizeTrackedAssistantMessage` + `newExecutionId = generateId()` 三段连在一起；(c) text/vision 两页都满足
- `'Bug 3 regression: agent_switched from coordinator_2 consumes the dispatch-created bubble instead of opening a duplicate one'` —— 锁 `secondaryHandoffExecutionBubblePendingAgentSwitch` 初始化、dispatch path 设置 true、agent_switched path 消费 false、且 `newExecutionId = generateId()` 只能出现在 fallback branch

#### 5.11.6 回归风险

未来有两种容易复发的错：
- 重新加回 `!agentRun.executionAssistantMessageId` guard：第二次 handoff 又不开 bubble，basic_agent 输出混进 coordinator_2 execution buffer
- 让 dispatch 和 agent_switched 都无条件开 bubble：同一个 handoff 出现两个 bubble，第一个永远“思考中...”，第二个输出正文

**正确 invariant**：dispatch step 开 bubble 并设置 pending flag；agent_switched 消费 pending flag，不开第二个 bubble；只有缺少 dispatch-created bubble 时才兜底开 bubble。text 与 vision 两页必须**同时**改（AGENTS.md trap #1）。

### 5.12 Bug 4: Stop 后下一轮 `search_and_fetch` 触发 `free(): invalid pointer` / segfault（2026-06-13）

#### 5.12.1 用户报告

用户停止一次 agent run 后立刻发起新请求，新请求调用 `search_and_fetch`：

```
search_and_fetch(query="《循环》弗诺·文奇 翁法罗斯 星穹铁道 对比", ...)
free(): invalid pointer
scripts/2_start_backend.sh: 第 487 行： ... 段错误 (核心已转储) python3 -m uvicorn backend.main:app ...
```

这是 native crash，不是 Python exception；`try/except` 捕不到。

#### 5.12.2 根因链路

有两个独立但叠加的竞态：

1. `_run_basic_stream` 的 run scope owner 错了。

   前端 stop 流程可能先关闭 SSE fetch，再调用 `/v1/agent/stop`。关闭 SSE 会触发 async generator 的 `finally`。旧代码在这里执行：

   ```python
   finally:
       session.finish_run(run_scope_id)
   ```

   但 `_run_agent` worker thread 可能仍在工具调用里，尤其是 `search_and_fetch` 内部的 fetch worker 仍在 `curl_cffi`/libcurl native call。过早 `finish_run` 会：

   - 把 `session.run_in_progress` 设回 `False`，新一轮请求可进入
   - 清理 `run_abort_manager` scope，新一轮与旧工具线程共享/重叠的边界变模糊
   - 让旧 native fetch worker 和新一轮搜索并发重叠

2. `search_and_fetch` 的 executor shutdown 不等 running worker。

   旧代码在 timeout/abort 后：

   ```python
   executor.shutdown(wait=False, cancel_futures=True)
   ```

   `cancel_futures=True` 只能取消尚未开始的任务；已经进入 `curl_cffi` request 的 worker 仍会继续跑。tool function 已经 return，但 native worker 还活着，下一轮再进 search 更容易触发 libcurl/curl_cffi 内存破坏。

#### 5.12.3 修复

1. `_run_basic_stream` 的 run scope 由 worker thread 拥有。

   `_run_agent` 的 `finally` 中调用：

   ```python
   session.finish_run(run_scope_id)
   ```

   async generator 的 `finally` 不再释放 run scope。SSE stream 关闭只表示浏览器不再接收事件，不代表 agent/tool worker 已退出。

2. `search_and_fetch` timeout/abort 后等待 running fetch worker 收尾。

   ```python
   executor.shutdown(wait=True, cancel_futures=True)
   ```

   这会牺牲一点 stop/timeout 返回速度，但保证 tool return 前没有旧 running fetch worker 留在后台。

#### 5.12.4 Hard contract

- `tests/test_agent_session_context.py::test_run_basic_stream_generator_close_keeps_run_busy_until_worker_exits`：关闭 SSE generator 后，只要 `_run_agent` worker 还没退出，`session.run_in_progress` 必须仍是 `True`，`active_run_scope_ids` 不能被清空；worker 退出后才变回 `False`。
- `tests/test_search_and_fetch.py::test_executor_shutdown_waits_for_fetch_workers_after_timeout_or_abort`：timeout/abort 后 `search_and_fetch` 必须等待已经运行中的 fetch worker 完成；不能用 `wait=False` 留后台 worker。

#### 5.12.5 回归风险

未来如果把 `session.finish_run(run_scope_id)` 挪回 `_run_basic_stream` async generator 的 `finally`，或者把 `search_and_fetch` 的 executor shutdown 改回 `wait=False`，stop 后下一轮请求就可能再次与旧 `curl_cffi`/libcurl worker 重叠，重新触发 `free(): invalid pointer` / segfault。

关键 invariant：**run scope 生命周期必须覆盖真实 worker 生命周期，不是 SSE 连接生命周期；tool function return 前必须等 native fetch worker 收尾。**

## 7. 未来排障 checklist

### 7.1 症状：auto-compact 长时间不出 token

按顺序排查：
1. **先看 SGLang 终端**：
   - 如果是连续的 `Prefill batch` 很久没有 `Decode batch`，那 SGLang 还在 prefill，等就好
   - 如果 `Decode batch, #running-req: 1, #full token: <X>` 持续，`X` 跟 compact prompt 长度匹配 → 100% 是 prefill 主导的延迟，不是 bug
2. **看 `full token usage` 和 `mamba usage`**：
   - 如果 `full token usage` 接近 1.0 且 `gen throughput` 接近 0 → KV 池爆了，需要降 `mamba_full_memory_ratio`
   - 如果 `full token usage` < 0.1 且 `gen throughput` 接近 0 → mamba 池过度挤压 KV，需要降 `mamba_full_memory_ratio`
3. **看后端日志的 `[compact] prompt[0] role=system content_len=...`**：
   - `content_len` > 30k → 确认是大 prompt 主导
4. **调整 SGLang 参数顺序**：
   - 优先：`mamba_full_memory_ratio: 0.5`（影响最大）
   - 然后：`chunked_prefill_size: 4096`（让 prefill 切小）
   - 最后：`max_summary_tokens: 4000`（config-misc.yaml，让 generation 阶段也更快）
5. **不要**改动后端代码。compact 链路本身没有 bug。

### 7.2 症状：auto-compact 永远不触发

1. 看 `_should_auto_compact_session()` 的返回值（DEBUG 日志）
2. 看 `performance_ratio: 0.1` × `max_context_length: 242144` = 24214 阈值
3. 看 `TokenCounter` 加载的真实 tokenizer（必须来自 model_path）
4. 看 `compact.enabled: true` 和 `compact.auto_trigger: true` 在 `config-misc.yaml`

### 7.3 症状：auto-compact 完成后下次 chat token 数没下降

1. 看 `session.compaction_archive` 是否有 1 条记录
2. 看 `session.agent.memory.steps` 是否变成 `[TaskStep(envelope)]`（不是 step 列表）
3. 看后端日志的 `final_messages: {N} msgs` 在 compact 之后是否变成 1 条或 2 条
4. 这是 post-compact context-not-shrinking bug（详见踩坑记录3 #21, #22, #23）

## 8. 一句话教训

> **"Decode batch" 长时间显示 + gen throughput 极低 + UI 空白 ≠ 后端 bug**。
> 它是 SGLang 在被 mamba 池挤压的 KV cache 里做长 prompt prefill 的**正确行为**。
> 看症状时，**第一步**是读懂 SGLang 终端日志的每个字段，**第二步**是查 SGLang upstream 是否有同类 issue，**最后**才回头查后端代码。
