## [踩坑记录5]：Android Chrome 远程访问前端，发送后永远“思考中...”

> 写给下一个不知道这段历史的 AI / 工程师。
> 本文记录一次远程手机访问问题：页面能打开、初始化 API 正常，但点击发送后没有回复，只显示“思考中...”。
>
> **写作日期**：2026-06-21
> **涉及页面**：`frontend/src/app/vision/page.tsx` 为主，`frontend/src/app/page.tsx` 同步维护
> **最终根因一句话**：Android Chrome 通过 `http://192.168.2.54:3000` 访问时属于非安全上下文，`crypto.randomUUID()` 不可用；前端在创建 agent session id 时抛错，导致真正的 `POST /v1/agent/chat` 根本没有发出。

---

### 0. 适用范围

本文适用于以下症状：

- PC/服务器本机访问正常或后端健康检查正常
- 手机浏览器能打开 `http://<LAN_IP>:3000`
- 页面初始化时 `/health`、`/config` 正常
- 点击发送后 UI 出现“思考中...”，但没有最终文本
- 前端 terminal 看不到 `POST /v1/agent/chat` 或 `POST /v1/chat/completions`

特别注意：本次真实发生在 `/vision` 页面，因为当前模型配置为 vision 后前端会自动跳转 `/vision`。不要只排查 `/` text 页面。

---

### 1. 原始症状

用户报告：

> Android Chrome 可以打开 `http://192.168.2.54:3000`，页面可见。但发送消息后没有任何回复，只弹出“思考中...”。

同时 Next dev server 还出现 warning：

```text
Cross origin request detected from 192.168.2.54 to /_next/* resource.
In a future major version of Next.js, you will need to explicitly configure "allowedDevOrigins" in next.config to allow this.
```

这个 warning 不是最终根因，但它提示了一个事实：当前是 LAN 远程访问 Next dev server，需要按远程浏览器场景设计。

---

### 2. 第一轮误判：以为是后端 API 地址 / CORS / 端口问题

最开始的合理怀疑是：手机浏览器拿到的前端 JS 仍然请求 `localhost`，而手机上的 `localhost` 指向手机自己，不是 Jetson/服务器。

排查发现：

- `config/config-server.yaml` 后端端口是 `8090`
- 后端监听 `0.0.0.0:8090`
- CORS 默认是 `*`
- `frontend/src/lib/api.ts` 已有把 loopback backend 改写到当前浏览器 hostname 的逻辑
- 但 `frontend/next.config.js` 默认曾写成 `http://localhost:8080`，和后端 `8090` 不一致

修过的问题：

- `next.config.js` 默认 API base 从 `http://localhost:8080` 改为 `http://localhost:8090`
- 加测试锁住默认端口

这个修复是正确的，但**不是最终根因**。用户重启后仍不行。

教训：

- “页面能打开但发送无响应”确实常见于 API base URL 错误，但不能停在猜测。
- 必须验证点击发送后是否真的有 `POST` 到后端，而不是只看初始化 `GET /health`、`GET /config`。

---

### 3. 第二轮架构修正：改成同源 Next 代理

为了让远程手机访问更稳，改了前端请求路径：

- 浏览器默认请求同源 `/api/backend/...`
- Next route handler 在服务器侧转发到本机后端 `http://127.0.0.1:8090` 或配置的 backend URL
- 手机只需要访问 `:3000`，不再需要直连 `:8090`

新增文件：

- `frontend/src/app/api/backend/[...path]/route.ts`
- `frontend/src/lib/backend-proxy-route.test.mts`

同时配置 Next dev warning：

- `frontend/next.config.js` 支持 `NEXT_ALLOWED_DEV_ORIGINS`
- `scripts/3_start_frontend.sh` 自动从 `hostname -I` 注入 LAN IP

这也是正确的防御性改造，但仍不是最终根因。

关键证据：

```text
[backend-proxy] -> GET http://localhost:8090/health
[backend-proxy] <- GET http://localhost:8090/health 200
[backend-proxy] -> GET http://localhost:8090/config
[backend-proxy] <- GET http://localhost:8090/config 200
```

只有初始化 GET，没有发送时的 POST。

教训：

- 如果只有 `GET /health` / `GET /config`，说明页面初始化链路正常，但不能证明发送链路正常。
- Next 代理解决的是“浏览器如何到后端”的问题；如果浏览器代码在 fetch 前抛错，代理永远看不到 POST。

---

### 4. 第三轮关键诊断：没有手机 console，就把浏览器端日志打回服务器

用户无法打开 Android Chrome console，不能提供浏览器异常。

当时的临时解决方法：新增一个极轻量 debug endpoint，让浏览器用同源请求把关键检查点发回 Next terminal：

- `frontend/src/app/api/client-debug/route.ts`
- `frontend/src/lib/api.ts::emitClientDebug()`

**注意**：这只是排障脚手架，不是长期架构。根因确认并修复后，相关 endpoint 和调用已移除，避免额外 POST、日志噪声，以及 LAN 内任意请求刷日志的风险。以后如需复用这种方法，应临时加、定位后删，或做成显式开关。

关键打点：

- `vision.handleSend.start`
- `vision.handleSend.agent.beforeStream`
- `llmClient.agentChatStream.fetch.start`
- `llmClient.agentChatStream.fetch.ok`
- `vision.handleSend.catch`

最终用户贴出的 decisive evidence：

```text
[client-debug] {"event":"vision.handleSend.agent.beforeStream","data":{"textLength":2,"imageCount":0}}
[client-debug] {"event":"vision.handleSend.catch","data":{"message":"crypto.randomUUID is not a function"}}
[client-debug] {"event":"vision.handleSend.start","data":{"hasText":true,"imageCount":0,"isLoading":false,"agentMode":true,"connectionStatus":"connected"}}
```

这说明：

1. 按钮点击和 `handleSend` 已经进入
2. 已进入 agent 分支
3. 但在调用 `llmClient.agentChatStream()` 前抛错
4. 真正的 `POST /v1/agent/chat` 没有发出

---

### 5. 真正根因：非安全上下文下 `crypto.randomUUID()` 不可用

出错代码原来在 text 和 vision 两页都有：

```ts
const effectiveSessionId = agentSessionId ?? `agent-${crypto.randomUUID()}`;
```

Android Chrome 访问：

```text
http://192.168.2.54:3000
```

这不是 HTTPS，也不是 `localhost`，属于非安全上下文。部分 Web Crypto API 在这种上下文不可用，`crypto.randomUUID()` 抛：

```text
crypto.randomUUID is not a function
```

为什么 UI 会卡在“思考中...”：

1. `handleSend()` 先创建用户消息和 assistant streaming 占位
2. UI 已显示“思考中..."
3. 随后生成 agent session id 时抛错
4. `catch` 执行，但当时错误展示不够明显
5. 没有任何 `POST /v1/agent/chat`

---

### 6. 最终修复

新增跨浏览器 session id helper：

- `frontend/src/lib/session-id.ts`
- `frontend/src/lib/session-id.test.mts`

规则：

1. 优先用 `crypto.randomUUID()`
2. 不可用时用 `crypto.getRandomValues()` 手动生成 UUID v4 形态
3. 再不可用时 fallback 到 `Date.now()` + `Math.random()`

核心接口：

```ts
createAgentSessionId()
```

替换两页：

- `frontend/src/app/page.tsx`
- `frontend/src/app/vision/page.tsx`

从：

```ts
const effectiveSessionId = agentSessionId ?? `agent-${crypto.randomUUID()}`;
```

改为：

```ts
const effectiveSessionId = agentSessionId ?? createAgentSessionId();
```

用户在临时 debug 打点仍存在时验证成功，日志为：

```text
[client-debug] {"event":"vision.handleSend.start",...}
[client-debug] {"event":"vision.handleSend.agent.beforeStream",...}
[client-debug] {"event":"llmClient.agentChatStream.fetch.start","data":{"baseUrl":"/api/backend",...}}
[backend-proxy] -> POST http://localhost:8090/v1/agent/chat
[backend-proxy] <- POST http://localhost:8090/v1/agent/chat 200 after 54ms
[client-debug] {"event":"llmClient.agentChatStream.fetch.ok",...}
```

### 7. 防御性改动清单

本次保留下来的防御性改动是有价值的：

1. **同源代理**：远程浏览器默认走 `/api/backend`，避免手机直连后端端口和 CORS 问题。
2. **代理错误响应**：Next 代理连接后端失败时返回可见 `502 { error: "backend_proxy_failed" }`，而不是让异常冒泡成不清晰的失败。
3. **可选代理日志**：`BACKEND_PROXY_LOG=1` 时输出 `[backend-proxy] ->` / `<-` 成功日志；失败日志默认保留。
4. **Next allowedDevOrigins**：避免未来 Next dev server 对 LAN origin 更严格时出问题。
5. **session id helper**：禁止页面直接调用 `crypto.randomUUID()`。

本次已移除的过度/临时改动：

1. `/api/client-debug` endpoint
2. `emitClientDebug()`
3. text / vision 页面里的 `*.handleSend.*` debug 打点
4. `llmClient.*.fetch.*` debug 打点

---

### 8. 未来排障 checklist

遇到“远程手机能打开页面但发送后卡住”，按这个顺序查：

1. 前端 terminal 是否有 `GET /api/backend/health` 和 `GET /api/backend/config`
2. 临时设置 `BACKEND_PROXY_LOG=1` 重启前端，点击发送后看是否有 `[backend-proxy] -> POST .../v1/agent/chat` 或 `.../v1/chat/completions`
3. 是否有 `[backend-proxy] <- POST ... 200`
4. 如果没有 POST，但 UI 已出现“思考中...”，优先怀疑浏览器端在 fetch 前抛错；本次是 `crypto.randomUUID is not a function`
5. 无手机 console 时，可临时加 `/api/client-debug` 式同源回传打点，定位后删除或改成显式开关

判断：

- 没有 proxy POST：按钮/页面逻辑/fetch 前异常/旧 JS bundle
- 有 proxy POST 但没有 200：Next 代理或后端流问题
- 有 proxy 200 但 UI 仍卡：浏览器 SSE 消费或 React 渲染问题

---

### 9. 一句话教训

不要在面向远程手机浏览器的代码里直接假设 `crypto.randomUUID()` 可用；不要只看初始化 GET 成功就认为发送链路正常。没有手机 console 时，可以临时把浏览器端关键检查点打回服务器 terminal，但定位后应删除或显式开关化，避免把排障脚手架变成长期噪声和攻击面。

## 10. Qwen3.5 + vLLM 容器链路复盘（2026-07）

### 症状与根因

- **没有流式显示**：vLLM 0.17.1/Qwen3 返回的 SSE 推理字段是 `delta.reasoning`，后端只读取 `reasoning_content`，导致 thinking-only chunk 被丢弃。`backend/llm_service.py` 应兼容两个字段，并保留 `data:` 的 SSE 解析。
- **停止后请求仍在跑、Running 越积越多**：浏览器断开没有关闭上游 HTTP 流，且旧按钮只调用 SGLang 的 `/abort_request`；vLLM 没有被取消。必须记录 request id、在取消时关闭上游 response，并按 provider 分流停止逻辑。vLLM 的 `Running` 表示仍存活的请求，不等于模型重复加载。
- **“卡住十分钟”**：流式开启后确认是 Qwen thinking 自身陷入循环，不是传输层；流式输出有助于区分模型行为与前后端故障。
- **首帧冷启动慢、后续很快**：首次请求触发 Triton/编译内核和空的 prefix cache；后续请求命中编译缓存/自动 prefix caching。它不是单纯的前端缓冲问题（上游 issue #37175）。本次不采用手动预热或 A/B 参数试验。
- **容器偶发启动失败**：vLLM 会按 `gpu_memory_utilization` 检查启动时空闲显存；其他进程占用时会直接报错。先清理残留进程并核对显存，再决定是否调整参数。

### 已验证的做法

- `chat_stream_async` 使用后台 worker + async queue，并在取消时关闭上游流；SSE 响应设置 `Cache-Control: no-cache`、`X-Accel-Buffering: no` 等，避免代理缓冲。
- 启动脚本必须把 YAML 的 `max_num_seqs`、`max_num_batched_tokens` 显式传给 vLLM，避免配置静默回退到默认值。
- `docker --rm` 每次重启都要持久化编译缓存：挂载 `/root/.cache/vllm`、`/root/.triton`、`/tmp/torchinductor_root`，并按镜像 tag 隔离宿主机目录；缓存只能来自可信目录。持久化缓存可减少重新编译，但不会保存进程内 CUDA graph 状态。
- NGC 镜像统一使用 `nvcr.io/nvidia/vllm:26.06-py3`，启动前用 `/v1/models` 获取实际 model id，并检查 `vllm.__version__`。量化参数必须匹配 checkpoint（`compressed-tensors`、`modelopt_fp4` 等不可混用）；`--enforce-eager` 仅用于诊断。

### 工程经验

- 对协议字段做别名归一化，并为 reasoning、SSE、取消链路补回归测试；修改后至少执行 `bash -n`、YAML 解析、`py_compile` 和定向测试。
- 区分“代码/协议已验证”和“真实 Docker/GPU 已验证”；没有运行环境时不要宣称完成运行时测试。

## 11. Qwen3.6 Heretic NVFP4 图片输入输出 `!!!!`（2026-07-11）

### 症状与根因

- 纯文本正常；任意图片输入后模型持续输出 `!!!!`，直到 `max_tokens` 或人工停止。
- vLLM 0.22.1 启动日志有 167 条 `Parameter visual.* not found in params_dict, skip loading`。这不是前端或 SSE 伪造的字符，而是未加载视觉塔后的模型真实输出。
- 旧 checkpoint 的 333 个视觉 tensor key 为 `model.language_model.visual.*`；`Qwen3_5MoeForConditionalGeneration` 期望同级的 `model.visual.*`。模型发布方随后也明确记录了这个已知问题及相同症状。

### 正确修复

1. safetensors 的 tensor `data_offsets` 相对数据区，不依赖 header 的绝对长度；可只重写 header 中的 333 个 key，再逐字节流式复制数据区。
2. 使用 `scripts/repair_qwen36_vision_safetensors.py` 创建新模型目录。脚本拒绝原地覆盖、拒绝 key 冲突，并临时文件写完后原子替换输出。
3. 输出目录的 `model.safetensors` 是独立普通文件；`config.json`、tokenizer 等伴随文件也必须是实际副本，而不是指向宿主机 HF cache 的绝对软链接。容器只挂载该输出目录时，绝对软链接会在容器内失效。
4. 修复后用 safetensors 检查必须得到 `model.visual.* = 333` 且 `model.language_model.visual.* = 0`；启动日志必须无 `Parameter visual.* ... skip loading`。本次端到端图片识别已由用户验证成功。

### 启动器选择

- `scripts/1b_start_vllm_container_with_snapshots.sh` 只适用于 Hugging Face cache 布局：要求 `snapshots/<revision>`、`blobs/`，并验证 snapshot 软链接都落在 `blobs/` 内。普通模型目录会在启动前被拒绝。
- 修复后的独立普通模型目录必须用 `bash scripts/1c_start_vllm_container.sh`，它将整个模型目录挂载为容器内 `/model` 并传递 `--model /model`。
- 旧 snapshot 与修复目录不存在运行时依赖关系。确认图片端到端正常后，可删除首次错误生成的 `qwen36-heretic-nvfp4-vision-fixed`；是否删除原始 HF cache 则取决于是否需要保留旧权重回退。

## 12. Read File v7：OCR 启动锁、UMA 门槛、CUDA 上限与 Agent E2E（2026-07-27）

### 原始症状

- 第二次运行 `scripts/2_start_OCR_LM.sh` 时，即使 `127.0.0.1:30001` 上已有健康且 attestation 匹配的 PaddleOCR 服务，仍等待 `logs/paddleocr-start.lock`，约 900 秒后报启动锁超时。
- Agent 读取 171 KiB、4 页 PDF 时反复返回 `MEMORY_RESERVE: available UMA is below the configured main LLM reserve`；模型随后错误尝试 `document_mode="text"`，又触发 `INVALID_DOCUMENT_MODE`，并出现一次格式错误的重试 transcript。
- OCR 与 FastAPI 重启后，后端 `/config` 一度显示 `active_backend=null`，Agent 无法调用真实 SGLang。

### 根因一：启动锁被错误持有到服务退出

- 旧脚本在健康复用检查之前获取 `flock`，随后在 `wait "$OCR_PID"` 期间一直保持 FD 9，导致“启动序列化锁”变成“服务生命周期锁”。
- 只把 unlock 移到 canary 后仍不足以处理当前已运行的旧脚本，因为旧进程仍持有锁；必须先做锁前严格复用检查，再在取得锁后复查，关闭并发启动竞态。
- 锁前复用不能无视正在停止的 owned child。最终增加 `${OCR_START_LOCK}.stopping` 标记：退出清理先标记 stopping，并在启动锁内完成 TERM-only 停止；后来的 launcher 看到标记后跳过无锁复用。

### 启动锁修复

1. 健康、attestation/config/model/process identity 全匹配时，锁前直接复用并返回 0。
2. 首次检查失败才等待有界启动锁；取得锁后再次检查，避免重复启动。
3. 新服务通过 readiness、canary 并写完 attestation 后释放锁，再进入长期 `wait`。
4. intentional shutdown 写 stopping 标记并序列化停止，保留“不复用正在退出的 child”契约。
5. 行为测试覆盖“旧 launcher 仍持锁时快速复用”“锁内 double-check”“canary 后锁可获取”“停止中的 child 不可复用”。

### 根因二：64 GiB 配置被错误理解并在稳态重复计算

- `main_llm_memory_reserve_gb` 的实现只是比较 `psutil.virtual_memory().available`；它不为 OCR 或主 LLM 分配内存，也不是 OCR 上限。
- 当时 Thor 总内存约 122.8 GiB，SGLang 与 OCR 已常驻后 available 约 47.5 GiB。继续要求 available ≥ 64 GiB，会把已经驻留在 SGLang 静态池中的主 LLM 占用重复计算，导致所有未缓存视觉文档在进入 PDF/OCR 前被确定性拒绝。
- 用同一 PDF、只临时把门槛改为 32 GiB 后，完整 PaddleOCR 路径成功返回 80 行，证明 PDF、OCR 服务和客户端均正常，阻塞点只有 admission gate。
- 最终按用户要求将独立的文档任务可用 UMA 底线设为 YAML 可调 16 GiB。错误文案改为 `document-processing floor`，避免继续把它误称为模型分配。

### 根因三：准入门槛不是 OCR CUDA 硬上限

- 降低 available-UMA floor 只会放宽任务准入，不能保证 OCR 模型最多使用多少 CUDA/UMA。
- PaddleX CLI 没有 memory-limit 参数。Jetson Thor 上 cgroup 也不能单独限制 CUDA：实测 `MemoryMax=1G` 的 transient service 仍可分配并触碰 2 GiB CUDA，而 systemd 只记录约 1.3 MiB 峰值。因此 cgroup-only 是“假上限”。
- 实测旧 OCR 在 distorted PDF 请求中的峰值约为 GPU 6.1 GiB、RSS 3.1 GiB，低于用户要求的 16 GiB CUDA ceiling。

### OCR CUDA 上限的正确实现

1. `config/config-server.yaml` 增加 `ocr.cuda_memory_limit_gb: 16`；`config/config-misc.yaml` 的 `main_llm_memory_reserve_gb: 16` 是另一项独立配置。
2. 新增项目自有 `scripts/paddle_ocr_service.py`，在导入 PaddleX 前调用 `torch.cuda.set_per_process_memory_fraction(limit_bytes / device_total)`，随后在同一 PID 内进入官方 `paddlex.__main__.console_entry()`；不修改第三方源码，也不预分配 16 GiB。
3. wrapper 原子写入 PID、limit bytes、device total 和 allocator fraction。canary/reuse 必须校验该报告与 listener PID、expected YAML value 及 attestation 一致。
4. 旧 attestation 没有 memory-limit evidence 时禁止静默复用；变更上限后必须显式重启 OCR。
5. 实机重启后 OCR PID `97179` 的 fraction 为约 `0.1302679`，`nvidia-smi` 在最终验证时为 `6086 MiB`，低于 16 GiB；SGLang 未重启。

### 根因四：本机 inference HTTP 客户端继承 SOCKS 代理

- FastAPI 重启后虽然启动脚本已探测到 SGLang，但 `backend/llm_service.py` 创建 `httpx.Client` 时默认 `trust_env=True`。
- 环境存在 `ALL_PROXY=socks5h://127.0.0.1:10808`，httpx 在真正请求 loopback 前就因缺少 `socksio` 初始化失败，后端降级为 mock，表现为 `model_loaded=false`、`active_backend=null`。
- OCR client 早已使用 `trust_env=False`，本地 inference provider 没有保持同样规则。修复后 SGLang、vLLM、container provider 的 health/sync/stream/abort 客户端统一禁用环境代理；外部网络工具不受影响。

### `document_mode` 与工具解析的教训

- Read File v7 规定 PDF 统一走视觉解析，`document_mode` 只允许 `auto` 或 `distorted`，不存在 `text` 模式。不能为了模型的一次错误重试恢复“文本 PDF”分支。
- 原 docstring 只写默认 `auto`，模型看不到完整约束。改用 `Literal["auto", "distorted"]` 后，LLM tool schema 生成 enum，并补充明确描述。
- malformed tool transcript 应继续返回精确 parser observation，让模型自行纠正；不能为了个别错误输出无限扩展智能兜底。修复首个真实资源错误后，模型无需进入连续错误重试。

### 最终验证与工程经验

- 定向回归：`149 passed, 2 skipped`；Shell 语法与 Python compileall 通过。
- OCR attestation、allocator report、listener process 三者 PID/limit 完全一致；OCR health 为 healthy，后端 `/config` 返回 `active_backend=sglang`。
- 原 PDF 的真实 `/v1/agent/chat` 非流式 E2E 返回 HTTP 200，模型实际调用 `read_file`，observation 包含 `Jetson Thor` 与 `PCN213501`，最终答案正确总结新旧料号；无 `MEMORY_RESERVE`、`INVALID_DOCUMENT_MODE` 或 tool failure。
- 排障顺序应是：先确认工具是否真正执行及首个确定性错误；再单变量绕过 admission 验证下游；最后才调整配置。模型后续的错误参数和 transcript 常是首个基础设施失败引发的二次症状。
- 对重要资源参数必须区分“准入底线”“allocator ceiling”“当前实测占用”，三者不可混称；上限必须沿 YAML → launcher → runtime evidence → attestation 全链路生效。

## 13. PaddleOCR-VL 1.6 + 独立 SGLang 后端全链路复盘（2026-07-28/29）

> 本节覆盖上下文压缩前后的完整排障。当前契约为：PaddleX API `8118`、OCR SGLang `30002`；纯 Transformers launcher 为 `scripts/2b_start_OCR_LM.sh`，SGLang launcher 暂为 `scripts/2_start_OCR_LM_with_SGLang_backend.sh`。旧章节中的 `30001` 和 `scripts/2_start_OCR_LM.sh` 仅是历史状态，不再是当前操作指引。

### 13.1 两套 Python 环境不能混用

- **简述**：PaddleX Pipeline 与 OCR SGLang 必须同时运行，但依赖栈不同。
- **根因**：`.paddle-ocr` 负责 PaddleX/CV Pipeline，`.sglang` 负责 SGLang/VLM；交叉安装容易破坏 CUDA、Transformers 或推理依赖，修改第三方源码还会制造不可复现状态。
- **解决方案**：launcher 分别调用两套环境；依赖按包名检查、版本只记诊断；所有兼容处理放在项目配置、脚本或 adapter 中。

### 13.2 端口相同不代表 backend 正确

- **简述**：`8118` 健康、`30002` 可访问，仍不能证明 PaddleX 正在使用目标 OCR SGLang。
- **根因**：端口只能证明 listener 存在，不能证明模型名、配置 hash、进程身份或实际 remote VLM 流量匹配；猜测 provider 容易把错误 listener 当成健康服务。
- **解决方案**：attestation 同时记录 mode、配置/manifest hash、PID/start ticks/boot ID/executable/listener 和 served model；健康检查按 active mode 校验，不探测或管理 `30001`。

### 13.3 Readiness 不能用固定 sleep

- **简述**：Thor 首次加载、内核编译和 CUDA graph capture 时间波动大，固定等待会误判启动失败。
- **根因**：模型加载完成、HTTP listener 出现和 `/health` ready 是不同阶段；短 sleep 在冷启动时不够，长 sleep 又掩盖提前退出。
- **解决方案**：使用 deadline polling；每轮同时检查 child 是否存活、目标 endpoint 是否 ready，超时或提前退出时保留精确日志和 exit status。

### 13.4 Canary 必须证明请求真正经过 remote VLM

- **简述**：仅验证 PaddleX 返回 200，无法排除 local fallback、错误模型或伪健康。
- **根因**：Pipeline API 成功不等于 `/v1/chat/completions` 被目标 SGLang 处理；单看端口和响应文本缺少因果证据。
- **解决方案**：canary 前后检查 16 GiB 可用 UMA floor、比较 SGLang request counter，并要求日志出现同一 request ID 的 `Receive/Finish` 配对；canary 与 preflight 使用同一图片和校验文本。

### 13.5 Launcher 清理不能只盯父 PID

- **简述**：leader 可能在 identity capture 前或 cleanup 前退出，descendant 还可能忽略 TERM。
- **根因**：仅保存父 PID 会遗漏 setsid 进程组成员；PID 还可能复用，盲杀会误伤其他服务。
- **解决方案**：记录 PGID/SID、boot ID、start ticks、executable 和 command hash；fallback 只信任已观察的 `PID:start_ticks` member，按 TERM、等待、必要时 KILL 的顺序清理，并确认 listener 消失。

### 13.6 Loopback 请求继承代理会在联网前失败

- **简述**：PaddleX 曾因 `socksio` 缺失启动失败，后端也曾因此降级为 mock。
- **根因**：环境中的 `ALL_PROXY/HTTP_PROXY/HTTPS_PROXY` 被 httpx/OpenAI client 继承；即使目标是 `127.0.0.1`，客户端也可能先初始化 SOCKS transport。
- **解决方案**：所有本地 health、sync、stream、abort 客户端使用 `trust_env=False`；PaddleX child 启动前移除大小写代理变量，外部网络工具保持原配置。

### 13.7 Thor `sm_110a` 不能交给 Triton 内置旧 PTXAS

- **简述**：OCR SGLang 启动时出现 `ptxas-blackwell fatal: Value 'sm_110a' is not defined`。
- **根因**：Triton 内置 CUDA 12.9 `ptxas-blackwell` 不识别 Thor 的 `sm_110a`，普通 `TRITON_PTXAS_PATH` 还不足以覆盖 Blackwell 专用路径。
- **解决方案**：同时设置 `TRITON_PTXAS_PATH`、`TRITON_PTXAS_BLACKWELL_PATH` 指向 `patch/ptxas_wrapper.sh`，并设置 `TORCH_CUDA_ARCH_LIST=11.0a`；以真实 CUDA graph capture 成功为验收。

### 13.8 Warning 与 fatal 必须分级

- **简述**：启动日志包含 rope key、token id、audio backend、`min_pixels/max_pixels` 等 warning，容易与真正启动失败混为一谈。
- **根因**：兼容性 warning 不一定影响 OCR 主路径；真正阻塞来自 traceback、scheduler exception、child exit、HTTP 5xx 或 PTXAS fatal。
- **解决方案**：先按“可观测 warning / 功能降级 / fatal”分类，再用真实 canary 判断；不要为了消除无害 warning 修改第三方依赖。

### 13.9 PaddleX Pipeline 默认 4096 输出 token 会截断密集表格

- **简述**：真实 PDF 中多个 table crop 固定以 `finish_reason=length, completion_tokens=4096` 结束。
- **根因**：Pipeline 层在 `max_new_tokens` 未指定时覆盖为 4096；截断的 HTML 表格可能无法闭合，后处理会产生空或不完整 block。
- **解决方案**：项目请求显式发送可配置的 `maxNewTokens=8192`，并拒绝 bool、非整数和非正值；该值缓解截断，但不能保证所有超长表格完整。

### 13.10 提高 token 上限不是空 Markdown 的完整解释

- **简述**：从 4096 提高到 8192 后，整本 PDF 的 Page 21 仍为空，但单独处理物理第 21 页却正常。
- **根因**：部分 4096 截断是真问题；Page 21/24 的空值则来自另一机制：`mergeTables/restructurePages` 把续表内容合并到前页，并主动清空当前 table block。
- **解决方案**：用单页复现和 PaddleX 源码交叉验证，不继续盲目加 token；将“生成截断”和“合法跨页合并”作为两类独立状态处理。

### 13.11 空 Markdown 不能一律视为 OCR 失败

- **简述**：严格 parser 报 `PaddleX page 21 has empty markdown.text`，但前一页已包含合并后的长表格。
- **根因**：PaddleX `merge_tables_across_pages()` 会设置 `prev_block.content=merged_html`、`curr_block.content=""`，并通过 global group 标记续表归属。
- **解决方案**：仅当所有非 ignored block 都是空 table，且每个 `global_group_id` 确实引用更早页面已出现的 `global_block_id` 时接受；debug 输出 merge notice，其他空页仍报错。

### 13.12 只检查 `global_group_id < global_block_id` 会接受伪 provenance

- **简述**：初版 merge 判定只要求 group ID 数值更小，伪造或损坏响应也可能被当作合法续表。
- **根因**：数值顺序不证明引用对象真实存在；unknown、same-page 或 future ID 都不构成跨页合并证据。
- **解决方案**：parser 按页面维护 prior `global_block_id` 集合；当前页处理完成后才加入集合，并为 unknown、same-page、future ID 增加负向回归。

### 13.13 38 页 PDF 只返回 32 页不是 restructure 合并页数

- **简述**：真实 PDF 有 38 个物理页，PaddleX 却稳定返回 32 个 `layoutParsingResults`。
- **根因**：`Serving.extra.max_num_input_imgs=32` 是输入页上限；服务静默只处理前 32 页。`restructurePages` 保持结果 slot，不会把 38 页压成 32 页。
- **解决方案**：保留 32 页内存护栏；parser 对 `dataInfo.numPages`、known chunk count 和返回数量做一致性校验，禁止把截断响应当成功。

### 13.14 独立 chunk 会破坏跨边界表格

- **简述**：把 38 页拆成 32+6 后分别输出，页 32/33 的跨页表格无法全局合并。
- **根因**：每个 chunk 内独立 `restructurePages=true` 会提前封闭局部上下文，后续无法恢复跨 chunk 的 table group。
- **解决方案**：每个 chunk 以 `restructurePages=false` 串行调用 `/layout-parsing`，收集全部有序 `prunedResult`，最后一次调用官方 `/restructure-pages` 完成全局 merge/relevel。

### 13.15 Raw chunk 与 final response 不能使用同一质量校验

- **简述**：初版 chunk 流程在全局 restructure 前就调用最终 Markdown parser，合法 raw page 可能被提前拒绝。
- **根因**：raw 阶段的职责是验证 envelope、errorCode、reported/returned page count 和 page 结构；最终 Markdown 可能要等全局 table merge 后才成立。
- **解决方案**：拆分结构校验与最终 Markdown 校验；raw chunk 只提取 `prunedResult`/markdown images，最终 `/restructure-pages` 响应才执行空页和质量规则。

### 13.16 服务端 `errorMsg` 不应原样回显

- **简述**：早期 debug client 把 PaddleX `errorMsg` 直接写入 stderr。
- **根因**：该字段由上游控制，可能包含内部响应细节、路径或文档片段；“错误可操作”不等于“回显全部上游文本”。
- **解决方案**：错误只报告安全的 endpoint、HTTP 状态或 errorCode；不打印 Base64、完整 JSON、内部 response 和任意上游 errorMsg。

### 13.17 Poppler chunk 必须保证页序、清理和无 shell 注入

- **简述**：debug client 需要拆分任意本地 PDF，但不能新增 Python PDF 依赖或遗留临时文件。
- **根因**：shell 字符串拼接会引入路径注入；异常路径若不清理，会积累单页 PDF；页名排序错误会打乱全局顺序。
- **解决方案**：使用 `pdfseparate/pdfunite` 参数数组、零填充页名和 `TemporaryDirectory`；覆盖 33 页 32+1 顺序、缺失 executable、第二 chunk 失败不 restructure 及异常清理测试。


### 13.19 文档 stale reference 也会造成真实故障

- **简述**：部分 active 文档仍指向旧 `30001` 或不存在的 `scripts/2_start_backend.sh`。
- **根因**：功能迁移时只改运行代码，没有同步 operational docs；用户照文档执行会访问错误端口或直接命令失败。
- **解决方案**：active docs 使用 PaddleX `8118`、OCR SGLang `30002`、backend `scripts/3_start_backend.sh`；历史设计若保留旧值，必须明确其历史属性。

### 13.20 自动化通过不能替代真实长文档 smoke

- **简述**：fake HTTP tests 能验证协议和错误边界，但不能证明 Thor 上 38 页 PDF、真实模型和全局 restructure 可用。
- **根因**：真实链路还包含 Poppler、PaddleX CV/layout、数百个 VLM crop、SGLang CUDA kernel 和长输出；这些无法由 unit test 模拟。
- **解决方案**：最终同时要求定向回归、compileall、`bash -n`、真实 38 页 exit 0、恰好 38 个 page heading、Page 21/24 merge notice、Page 38 完整，以及新日志无 traceback/scheduler exception/5xx。

### 13.21 `finish_reason=length` 是质量风险，不是硬件结论

- **简述**：最终 38 页 smoke 成功，但仍有少量 crop 跑满 8192，且个别页面出现重复或退化文本。
- **根因**：密集表格或模型生成退化可能耗尽输出预算；仅凭 length 或文本异常不能推出 GPU、KV cache 或硬件损坏。
- **解决方案**：把 length 记录为 OCR 质量/截断风险，结合具体 page/crop 再评估；只有独立硬件、scheduler 或 cache 证据时才能归因底层故障。

### 13.22 最有效的排障顺序

- **简述**：本次先后出现 proxy、PTXAS、token 截断、合法 merge、32 页 cap 等多个独立问题，单一猜测无法解释全部症状。
- **根因**：后一个可见错误常由前一个基础设施失败触发；把所有异常归为“模型坏了”或“服务没启动”会反复走错方向。
- **解决方案**：按“进程/端口身份 → readiness → remote canary → HTTP/JSON → page count → block provenance → 模型质量”逐层收窄；每个假设必须用日志、单页复现、源码契约或 RED/GREEN 测试证伪/证实。

## 14. SGLang / FlashInfer NVFP4 缓存失效重编译与全局 OOM（2026-08-02）

### 14.1 问题背景与环境

- 平台为 NVIDIA Jetson Thor，CPU 与 GPU 共用约 122 GiB UMA；事故发生时系统没有 Swap。这里没有传统独显上“主存还有很多、显存单独耗尽”的硬边界，CUDA 编译器、SGLang 模型/KV 静态池、桌面和 VS Code 都竞争同一份物理内存。
- 当前推理环境使用 FlashInfer 0.6.12、SM110a、SGLang 和 NVFP4/FlashInfer Cutlass MoE。过去约一个月中，FlashInfer 已编译缓存一直可复用，第二次及后续启动不再出现首次编译的高内存尖峰。
- 2026-08-02 启动时日志再次出现：

  ```text
  Running FlashInfer autotune with cache:
  ~/.cache/sglang/flashinfer/autotune/0.6.12/sm110/5e78b81a54a57909/rank_tp0_pp0_dp0.json
  ```

- 第一次重编译导致整机 OOM/死机。重启后将 SGLang `max_context_length` 降至 8192、`mem_fraction_static` 降至 0.29，再从 VS Code terminal 启动；模型加载及编译过程中 VS Code 突然闪退。

### 14.2 问题现象与直接证据

1. **VS Code 闪退不是 Electron 自身随机崩溃。** 当前 boot 的 kernel journal 在 `2026-08-02 15:14:11` 明确记录：

   ```text
   cicc invoked oom-killer
   oom-kill: constraint=CONSTRAINT_NONE ... global_oom ... task=code
   Out of memory: Killed process 18935 (code)
   app-code-18866.scope: Failed with result 'oom-kill'
   ```

   VS Code renderer 被杀后，主进程继续报告 renderer/network/GPU process 消失，最终整个窗口退出，所以用户看到的是“VS Code 闪崩”。

2. **OOM 时并行编译规模极大。** 同一份 kernel process table 中存在一个 `ninja`、大量 `nvcc`，以及约 18 个同时工作的 `cicc`。多个 `cicc` 的 RSS 分别约为 1.0–1.8 GiB，且还在增长；同时 SGLang scheduler、模型权重/KV 静态池、桌面和 VS Code 已经常驻 UMA。

3. **内核选中 VS Code 不代表 VS Code 是最大内存源。** Linux OOM Killer 综合内存占用、进程/内存组、`oom_score_adj` 等选择牺牲者。日志中多个 VS Code 子进程的 `oom_score_adj` 为 100–300，而编译进程为 100；最终 renderer 更容易被选中。真正制造瞬时压力的是大量并行 CUDA compiler，加上已经驻留的推理服务。

4. **当时没有 Swap 作为缓冲。** `free -h` 显示 `Swap: 0B`。一旦 UMA 不能满足新的匿名页申请，内核只能回收 page cache 或进入 OOM，而不能把低活跃桌面页临时换出。Swap 不是编译容量的替代品，而且在 NVMe 上可能造成严重抖动；是否创建 Swap 应单独评估并由用户决定，不能把它当作本问题的主修复。

### 14.3 两种“FlashInfer 缓存”不能混为一谈

本次日志展示的是 autotune cache，但真正昂贵的 CUDA JIT 产物在另一棵目录中：

| 类型 | 本机路径 | 事故时大小 | 作用 |
|---|---|---:|---|
| SGLang/FlashInfer autotune | `~/.cache/sglang/flashinfer/autotune/0.6.12/.../*.json` | 整个 `~/.cache/sglang` 约 56 KiB | 保存已测得的 tactic/rank 选择，不包含大型编译目标 |
| FlashInfer JIT | `~/.cache/flashinfer/0.6.12/110a/{generated,cached_ops}` | 0.6.12 约 378 MiB；全版本约 1.0 GiB | 保存生成源码、Ninja 状态、`.o` 和最终 `.so`，NVFP4/MoE 重编译的主体 |
| Torch extensions | `~/.cache/torch_extensions` | 约 5.1 MiB | SGLang/PyTorch C++ extension |
| Triton | `~/.triton/cache` | 约 242 MiB | Triton JIT kernel 缓存 |
| CUDA driver | `~/.nv/ComputeCache` | 约 27 MiB | CUDA driver compute cache |
| DeepGEMM | `~/.cache/deep_gemm` | 很小，且当前禁用 JIT | DeepGEMM 相关缓存 |

只备份日志中那一个 JSON，不能固化 NVFP4 的 FlashInfer 编译结果。完整固化必须覆盖至少 FlashInfer JIT 与 SGLang autotune；为避免其他启动阶段重新 JIT，管理脚本同时覆盖 Torch、Triton、CUDA 和 DeepGEMM 缓存。

### 14.4 缓存是否因重启损坏或“过期”

检查结果不支持“重启把成功文件弄坏”或“一个月 TTL 自动过期”的假设：

- 日志中指定的 `rank_tp0_pp0_dp0.json` 存在、非空，Python JSON 完整解析成功；metadata 与 FlashInfer 0.6.12、CUDA 13.0、NVIDIA Thor 匹配。
- 当前 0.6.12 的所有已存在 `.so` 均非零且通过 ELF header 校验。关键 `fused_moe_100.so` 约 106 MiB，mtime 为 2026-07-14；这份旧的完整动态库没有因 reboot 被截断。
- 2026-08-02 新增/更新了很多 `.o`，但最终 `.so` 没有更新，符合“重编译进行到一半后 OOM 中断”的状态。`tmp/*.lock` 和空 `flashinfer_jit.log` 本身不能证明损坏；FileLock 文件长期存在是正常现象，锁状态由内核持有，不应只因看到零字节 `.lock` 就删除全部缓存。
- 对构建目录运行 `ninja -n -d explain`（dry-run，不编译）后，Ninja 明确给出两类失效原因：
  1. 多个目标的 `command line changed`，说明当前 CUDA/编译参数或环境和记录该对象时不同；
  2. 多个旧 `.o` 比 `/usr/include/stdc-predef.h` 更早，系统头文件更新时间使依赖图按规则判为 dirty。
- 另有部分目标明确显示 `output ... doesn't exist`，对应前一次 OOM 中断时尚未完成的对象。

因此，**reboot 只是时间上发生在两次启动之间，不是缓存失效的根因**。更合理的因果链是：系统头文件或编译命令变化 → Ninja 正常判定一批目标需要重建 → 默认高并发 CUDA 编译 → Thor UMA 全局 OOM。FlashInfer 的目录中也没有观察到“使用满一个月后按 TTL 删除 JIT”的证据。

### 14.5 根本原因

#### 根因一：Ninja 依赖/命令签名变化触发合法重编译

FlashInfer 缓存不是“只要 `.so` 文件还在就永远加载”。它保留 `build.ninja`、`.ninja_deps`、`.ninja_log` 和具体目标；如果输入头文件 mtime、生成源码、CUDA 工具链或命令行发生变化，Ninja 会重建受影响目标。这是一种正确性保护，不应通过伪造时间戳或强行加载旧 `.so` 来绕过。

#### 根因二：没有限制 PyTorch C++ extension 的 Ninja worker 数

PyTorch `torch.utils.cpp_extension` 默认让 Ninja 自行决定 worker 数；Ninja 通常按 CPU 数量启动多个任务。PyTorch 官方实现明确支持环境变量 `MAX_JOBS=N` 控制 worker。旧 `scripts/1a_start_sglang.sh` 没有设置 `MAX_JOBS`，因此 FlashInfer 的大规模 MoE 构建同时启动大量 `nvcc/cicc`。

`TRITON_NUM_COMPILE_THREADS` 只控制 Triton 自身编译线程，不能替代 `MAX_JOBS`。旧脚本还把 `TRITON_NUM_COMPILE_THREADS` 导出为空值，因此两条编译路径都缺少可靠的低内存约束。

#### 根因三：降低 context/KV 静态池只能释放基线，不能限制编译并发

将 `max_context_length` 和 `mem_fraction_static` 调低是正确的应急措施，它减少模型/KV cache 常驻基线；但若仍同时运行十几个每个占 1 GiB 以上的 `cicc`，释放出的几十 GiB 仍可能瞬间被吃完。必须同时控制“模型常驻基线”和“编译 worker 数”，二者不是互相替代关系。

### 14.6 OOM Killer 是什么，能不能关闭

- OOM Killer 是 Linux 内核在内存无法满足分配、回收又无进展时的最后保护机制。它的目的不是限制某个程序，而是快速释放内存，让内核和剩余系统继续运行。
- 本机事故后的相关 sysctl 为：`vm.overcommit_memory=0`、`vm.panic_on_oom=0`、`vm.oom_kill_allocating_task=0`，属于由内核综合选择牺牲者的常规行为。
- Linux 没有适合日常运行的、安全的“全局关闭 OOM Killer”开关。把 `vm.panic_on_oom=1` 打开只是可能把杀单个进程改成 kernel panic/重启；它不是关闭内存不足，也不会让失败的分配成功。
- 可以给单个进程设置 `oom_score_adj=-1000` 使其不被 OOM Killer 选择，但通常需要相应权限，而且只会把牺牲者换成 SGLang、桌面、SSH 或其他进程。若关键进程全被豁免，系统更可能卡死或 panic。
- cgroup/systemd 内存上限可以约束部分 CPU anonymous/file memory，但在 Jetson UMA 上不能假设它能准确限制全部 CUDA allocation；项目已经实测过 CUDA 分配不会被简单的 `MemoryMax` 当作可靠硬上限。因此不能用 cgroup-only 代替编译并发控制。
- **本事故不应该关闭或规避 OOM Killer。** 应在进入 OOM 之前把峰值压下来，并保留 OOM Killer 作为最后安全网。

### 14.7 最终解决方案

#### 1. 把编译并发纳入 YAML → launcher 生效链路

当前 NVFP4 infer YAML 增加：

```yaml
sglang:
  max_context_length: 8192
  mem_fraction_static: 0.29
  compile_max_jobs: 1
  triton_num_compile_threads: 1
```

`scripts/1a_start_sglang.sh` 解析并校验两个正整数，然后导出：

```bash
export MAX_JOBS=1
export TRITON_NUM_COMPILE_THREADS=1
```

单线程会让冷编译明显变慢，但避免十几个 `cicc` 同时制造几十 GiB 尖峰。启动日志会打印实际缓存路径和两个并发值，不能只相信 YAML 已修改而不看 launcher 输出。

#### 2. 显式固定所有编译缓存到持久化 home

launcher 现在显式设置并保持外部 override：

```text
FLASHINFER_WORKSPACE_BASE=$HOME
SGLANG_CACHE_DIR=$HOME/.cache/sglang
TORCH_EXTENSIONS_DIR=$HOME/.cache/torch_extensions
TRITON_CACHE_DIR=$HOME/.triton/cache
CUDA_CACHE_PATH=$HOME/.nv/ComputeCache
SGLANG_DG_CACHE_DIR=$HOME/.cache/deep_gemm
```

这样从 VS Code terminal、普通 shell 或其他入口启动时使用相同路径，避免因 `HOME`、临时目录或入口环境漂移造成无意义 cache miss。若主动修改 `SGLANG_COMPILE_CACHE_BASE`，应预期新路径第一次启动会重新编译。

#### 3. 提供可恢复的缓存管理脚本

新增 `scripts/manage_sglang_compile_cache.sh`：

```bash
# 查看路径、大小、mtime 和相关进程
scripts/manage_sglang_compile_cache.sh status

# 校验 autotune JSON、ELF，并用 ninja -n 检查 dirty/pending 目标
scripts/manage_sglang_compile_cache.sh verify

# 固化全部相关缓存；单线程 zstd 压缩并写 SHA-256
scripts/manage_sglang_compile_cache.sh snapshot <name>

# 让当前 FlashInfer 版本从零编译；只移入隔离区，不立即永久删除
scripts/manage_sglang_compile_cache.sh clear --scope flashinfer-current --yes

# 校验并恢复已固化快照；当前缓存也先移入隔离区
scripts/manage_sglang_compile_cache.sh restore <name> --yes

# 新缓存确认可用后，才永久删除指定隔离区
scripts/manage_sglang_compile_cache.sh purge-quarantine <quarantine-name> --yes
```

所有 destructive 操作都要求 `--yes`，并在检测到 SGLang、Ninja、NVCC 或 CICC 进程时拒绝执行。默认 `clear` 是同文件系统 rename 到隔离区，可恢复且不会在删除大目录时额外制造 I/O 风险。

#### 4. 在真实清理前创建独立快照

已创建：

```text
~/.local/share/llm-deployment/sglang-cache-snapshots/pre_recompile_20260802
```

该目录位于 `.local/share`，不在常规 `.cache` 清理范围内。快照覆盖 FlashInfer、SGLang、Torch extensions、Triton、CUDA compute 和 DeepGEMM；原始缓存约 1.3 GiB，zstd 单线程压缩后约 209 MiB，六个 archive 的 SHA-256 全部通过。

#### 5. 没有损坏证据时优先续编，不要习惯性清空

本次已经成功生成了很多新 `.o`。Ninja 能从中断点继续，只重做 dirty/missing 目标。直接清空会丢掉这些进度，并保证完整经历一次最慢的冷编译。因此默认操作应为：

```bash
cd /home/zk/Project/LLM-deployment
scripts/manage_sglang_compile_cache.sh verify
scripts/1a_start_sglang.sh
```

确认启动日志显示 `MAX_JOBS: 1`、Triton 为 1 thread 后，允许它低并发续编。只有 JSON/ELF 校验失败、生成目录与当前版本明显不匹配，或低并发续编仍反复报确定性构建错误时，才执行 `clear --scope flashinfer-current --yes` 从零重建。

### 14.8 验证结果与后续注意事项

- `bash -n scripts/manage_sglang_compile_cache.sh scripts/1a_start_sglang.sh` 通过。
- 缓存管理脚本的临时目录 round-trip 覆盖 snapshot → clear/quarantine → SHA-256 restore，新增定向测试结果为 `2 passed`。
- 真实快照六个 archive 的 SHA-256 全部为 `OK`。
- 当前 autotune JSON 和已有 `.so` 格式正常；Ninja dry-run 仍报告当前 0.6.12 有待编译目标，其中 `fused_moe_100` 构建包含 267 个步骤。因此下一次启动仍会编译，这是预期行为，不应误判为新缓存再次丢失。
- 编译成功后应再次执行 `verify` 并创建一个新的 `known-good` 快照；`pre_recompile_20260802` 是事故后、续编前的恢复点，不应冒充“所有 Ninja target 均 up-to-date”的最终快照。
- SGLang/FlashInfer/CUDA/PyTorch 升级、CUDA 路径或 flags 变化、系统开发头文件更新都可能使缓存合法失效。缓存“固化”保证可恢复，不代表可以安全绕过 ABI/依赖变化强制复用。
- 若未来再次看到 UI 闪退，先查 `journalctl -b -k` 的 OOM 证据和同时间的 `nvcc/cicc` 数量，再检查 `MAX_JOBS` 实际值；不要先删除缓存，也不要先归因 VS Code、GPU 硬件或“缓存过期”。
