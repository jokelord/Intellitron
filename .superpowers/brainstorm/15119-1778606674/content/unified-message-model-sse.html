Section 3: SSE 协议与前端投影规则

目标：在不为每个新 agent 发明一套新前端协议的前提下，让 coordinator_2 像普通聊天一样流式显示，让任务调度卡片真正持续滚动。

Protocol Principle
协议分层
底层：canonical timeline event
中层：SSE transport event
上层：前端 projection reducer（决定渲染到卡片、聊天气泡、agent steps）
Recommended SSE Event Families

1. timeline_event

统一承载 canonical timeline 的原子事件。

前端 reducer 统一消费，未来新增 agent 不再加新顶层协议。

2. content

保留现有兼容层，用于最终 assistant 内容或普通聊天流。

但内部逐步改为由 timeline_event 驱动。

3. done / error / aborted

继续保留生命周期终态事件，避免破坏现有客户端收尾逻辑。

Example Timeline Events
建议事件载荷形状
{
  "type": "timeline_event",
  "event": {
    "kind": "routing_delta",
    "source": "coordinator_1",
    "turn_id": "...",
    "message_id": "routing-card-1",
    "text": "正在分析这个请求更适合哪一类 agent...",
    "partial": true,
    "timestamp": 1778600000
  }
}

{
  "type": "timeline_event",
  "event": {
    "kind": "message_delta",
    "source": "coordinator_2",
    "turn_id": "...",
    "message_id": "assistant-msg-42",
    "text": "我们先从这个方程的边界条件开始...",
    "partial": true,
    "display": "chat_bubble"
  }
}

{
  "type": "timeline_event",
  "event": {
    "kind": "tool_call_started",
    "source": "basic_agent",
    "tool_name": "read_file",
    "message_id": "agent-step-99"
  }
}
关键不是字段名字必须完全一致，而是统一：同类事件必须走同类结构，不再按 agent 各自发明格式。
Frontend Projection Rules
Dispatch Card Projection
消费 routing_started / routing_delta / routing_decision / routing_timeout_fallback
文本使用最新 SSE 内容持续更新
视觉上使用持续滚动文本 + 持续扫光，而不是一次性动画
Chat Bubble Projection
消费 message_started / message_delta / message_completed
若 source=coordinator_2，直接渲染成 assistant 聊天气泡
未来其他“可见型 agent”也复用同一规则
Why Dispatch Card Currently Fails

这次要避免的问题

  • 只做 CSS 动画，不做真实 SSE 绑定
  • 文本只替换一次，然后动画空转
  • 前端收到的是 burst 更新，而不是连续 timeline_event

正确目标

  • 后端持续发出 routing_delta
  • 前端 reducer 持续合并为当前 dispatch text
  • 卡片视觉层持续滚动，且内容持续变化
Compatibility Strategy
渐进迁移
短期保留现有 agent_step / content 兼容消费；中期让前端主逻辑切到 timeline_event reducer；长期以 timeline 为唯一真相来源。
