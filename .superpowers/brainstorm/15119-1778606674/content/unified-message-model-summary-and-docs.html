Section 5: 摘要策略、编译成本与文档交付

重点回答：旧 turn 的摘要由谁生成、何时生成、如何避免每轮都让主 LLM 重新提炼；并把 AGENTS.md 与根目录备忘纳入正式交付。

Key Decision
不让主 LLM 每轮都做摘要
错误做法：每轮开始前，让当前主模型把历史 turn 全部重新提炼一遍。
推荐做法：摘要尽可能由代码和结构化编译器生成；只有少数真正需要“语义压缩”的地方，才引入异步/低频/可缓存的摘要任务。
Three Summary Producers

1. Deterministic Compiler (Recommended)

由代码直接从 timeline / behavior records 生成摘要字段。

适合：route receipt、handoff ledger、tool ledger、未完成事项、resolved status。

2. Event-Triggered Distiller

仅在 turn 关闭、agent 切换、窗口压力超过阈值时触发一次摘要。

适合：长篇 coordinator_2 推理的阶段性压缩。

3. Background Cheap Summarizer

如果 deterministic compiler 不够，再使用低优先级、低频、可缓存的小模型或后台摘要器。

不允许阻塞主链路首帧与 agent handoff。

Recommended Policy By Tier
Recent Unfinished Turns
中高保真保留，但不做“每轮重新摘要”。
通过 working memory / unresolved items / latest handoff record 增量维护。
也就是说：是“持续更新结构化状态”，不是“每轮全文压缩一次”。
Old Resolved Turns
在 turn 结束并降级为历史后，只摘要一次并缓存。
默认由 deterministic compiler 生成 turn summary skeleton。
若需要更强语义压缩，再异步补一个 distillation summary，但绝不每轮重算。
What Can Be Generated Without LLM

完全可由代码生成

  • route receipt
  • turn 是否 resolved / unresolved
  • agent handoff ledger
  • tool call / observation ledger
  • 最近一次用户目标
  • fallback 原因与时间戳

可能需要语义蒸馏的少数内容

  • 极长 coordinator_2 推理中“真正关键的中间结论”
  • 超长多轮对话中“最终结论演化轨迹”
  • 用户多次追问后，旧复杂 turn 的高层语义压缩
ROI Rule
只有在“降级为旧历史”时才值得做摘要
摘要不是 per-turn startup cost，而是 turn lifecycle 的一个低频、可缓存、可延迟执行的 compaction step。也就是：turn 关闭或窗口压力命中阈值时做，而不是每轮进模型前都做。
Recommended Implementation Boundary
首版建议
Phase 1：全部用 deterministic compiler，先不引入 LLM 摘要器。
Phase 2：仅对超长 resolved turns 增加异步 distiller，且结果缓存、版本化。
Phase 3：如果 future agents 增多，再考虑 agent-specific semantic compaction。
