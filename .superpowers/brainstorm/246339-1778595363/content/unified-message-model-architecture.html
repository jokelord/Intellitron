Section 1: 统一消息模型架构

核心目标：同一份 canonical timeline，同时服务于“用户可见流式体验”和“LLM 高质量上下文管理”，两者解耦但不分裂。

Core Idea
Single Canonical Timeline, Dual Projections
用户输入
text / vision
coordinator_1
极速 LLM 路由
Canonical Timeline
统一事件日志
可见消息层
Web UI / CLI
Agent 行为层
上下文精细管理
不再直接把“前端看到什么”和“LLM 吃到什么”绑死在同一份原始 message 上，而是先落到统一事件时间线，再分别投影成两层。
Routing + Execution Flow
Visible Message Layer
任务调度卡片：展示 coordinator_1 的全量流式推理
若选中 coordinator_2：其 reasoning/content 直接进入聊天气泡流式展示
若选中 basic_agent：继续显示 tool / observation / thought 等 agent UI
若 coordinator_1 超时 10s：卡片显示 fallback，并立即切 basic_agent
Agent Behavior Layer
把 coordinator_1 的原始流，整理成“清洁路由记录”写入上下文
为每个 agent 维护独立、整洁、可摘要的行为上下文
coordinator_2 可继续切换到 basic_agent / future agents
最终给模型看的不是 UI 噪音，而是结构化历史与精简行为记录
Agent Roles

coordinator_1

只负责极速选路。提示词极简。必须作出 agent 选择。

10 秒内若未作出选择，system fallback 到 basic_agent。

coordinator_2

复杂推理 agent。其推理像“非 agent 模式”一样流式出现在聊天气泡。

必要时可继续切换到 basic_agent / future agents。

basic_agent / future agents

负责工具调用、文件操作、浏览器、搜索、以及未来扩展职能。

都通过统一 timeline 接入，而不是各自发明一套显示/上下文协议。

Harness Engineering Rule

用户层

  • 消息整洁
  • 必须流式
  • 有明确“没死机”的反馈
  • dispatch 卡片持续滚动，而不是只闪一次

模型层

  • 不直接喂 UI 装饰文本
  • 不直接喂前端拼接后的嘈杂消息
  • 只喂结构化且可摘要的行为历史
  • 让上下文窗口保持清晰、精炼、可追踪

coordinator_1 的全量推理继续显示在“任务调度卡片”；coordinator_2 的全量推理显示在普通聊天气泡。二者都来自同一 canonical timeline，但投影方式不同。
