Coordinator 提速方案对比

目标：保留 coordinator 的 LLM 智能判断，同时显著缩短 basic_agent 首个思考框出现时间，并修复任务调度卡片的持续流式反馈。

Current Pain

1. 路由阶段过长

coordinator 会长时间输出推理文本，甚至复述 prompt，自身就消耗 1-3 分钟。

2. 用户能看到流，但真正可执行阶段来得太晚

即使前端有 dispatch 流式，basic_agent 的首个真正思考框还是来得很晚，主观体验仍然像“卡住”。

3. 任务调度卡片不是持续滚动

当前扫光/文本滚动没有和真实 SSE 节奏绑定，视觉反馈不足，且容易只变化一次。

Options
A

Prompt 约束型提速

继续用大模型 coordinator，但强约束 routing prompt：极短内部推理、禁止复述系统提示、只输出 route decision + 少量理由。

优点：改动最小。

缺点：对本地模型约束力有限，最容易被“prompt 复述”击穿。

B

双阶段 coordinator

同样保留 LLM 判断，但拆成：极速 routing prompt 决策 + 真正执行 agent。coordinator 专门做分类，不承担长篇思考。

优点：仍由 LLM 判断，且最符合你要保留 coordinator 的要求。

缺点：需要重构 coordinator prompt、流式策略和 handoff 时序。

C

LLM coordinator + 路由护栏

保留 coordinator LLM，但在外层加入“硬护栏”：路由 token 上限、路由超时、提示词摘要化、复述检测、提前切换 basic_agent。

优点：最适合本地模型，能从多个层面卡住 3 分钟 prompt 复述。

缺点：实现复杂度中等，需要改后端流、提示词和前端状态展现。

Recommended
推荐组合：B + C

为什么推荐

  • 保留 coordinator 的 LLM 智能判断，不退化为纯规则路由。
  • 通过“专职 routing prompt”把 coordinator 从长篇思考 agent，收缩成极速分类 agent。
  • 再用 token/time/复述护栏兜底，避免本地模型复述系统提示词。
  • 前端任务调度卡片改成真正持续滚动的 SSE 呈现，而不是只做一次动画。
  • 后端 CLI 若无法做到平滑流式，就降级为节流聚合输出，避免一 token 一行。

主要代价

  • 需要同时调整 backend routing、frontend dispatch card、CLI streaming 输出。
  • 需要定义什么叫“复述提示词”以及命中后如何提前切换或中止。
  • 需要重新校准 coordinator prompt，避免把太多指令直接暴露给模型重复消耗。
Visual Summary
Current
用户提问 → coordinator 长篇推理/复述 prompt → 很久之后才 handoff → basic_agent 首帧
Target
