Option B 细化：双阶段 Coordinator

你已选择保留 LLM 路由判断，但把系统拆成 coordinator_1（极速路由）和 coordinator_2（复杂但可继续切换的推理 agent）。

Shared Requirements

coordinator_1

提示词极简；必须输出动作调用；在 misc yaml 中配置 timeout=10s。

超时回退

10 秒内未选择任何 agent，则系统直接把请求交给 basic_agent，跳过 coordinator_1 和 coordinator_2。

coordinator_2

若被选中，需要像非 agent 模式一样，把完整推理过程直接 SSE 流式展示在聊天气泡中；并允许二次切换到 basic_agent 或未来 agent。

Variants
1

最小改动版

coordinator_1 仍走现有 agent routing 流，但 prompt 极简化、强制只输出 switch_agent。

coordinator_2 复用现有 agent 模式，但前端把它的 thought 直接映射到普通聊天气泡体验。

优点：动得最少。

缺点：历史 agent SSE 结构会比较绕，聊天气泡与 agent thought 语义会混在一起。

2

显式双通道版

coordinator_1 继续使用路由 SSE；一旦选中 coordinator_2，系统转入“direct chat-style streaming channel”。

coordinator_2 的推理和正文像非 agent 模式一样直接流入聊天气泡；若它二次切换，再切回 agent 流。

优点：体验最贴近你的要求。

缺点：状态机更复杂，需要定义 UI 如何从 dispatch → chat bubble → agent mode 平滑切换。

3

统一消息模型版

把 coordinator_2、basic_agent、未来 agent 的流式消息统一抽象成“可见消息层”和“agent 行为层”两层。

coordinator_2 只是显示为聊天气泡，但底层仍可继续切换 agent。

优点：长期最干净，未来可扩展到更多 agent。

缺点：这轮设计/实现成本最高。

Recommendation
推荐：Variant 2

理由

  • 最贴合你的产品要求：coordinator_2 要像非 agent 模式一样直接流式显示在聊天气泡。
  • 保留 coordinator_2 二次切换能力，不会把复杂推导错误限制死。
  • coordinator_1 与 coordinator_2 职责边界最清楚：一个负责极速选路，一个负责复杂推理或继续切换。

代价

  • 需要定义新的前端状态转换：dispatch card、聊天气泡、agent steps 之间如何无缝接力。
  • 需要后端支持“10 秒未切换则自动 basic_agent fallback”的中途打断控制。
Flow
Success Path
user → coordinator_1 流式路由 → 10 秒内切到 coordinator_2 / basic_agent → 对应 agent 接管输出
Timeout Path
user → coordinator_1 流式路由但 10 秒未选路 → system fallback → basic_agent 直接接管
